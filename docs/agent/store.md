> Sibling docs live in `docs/agent/`; the index is in the root `AGENTS.md`.

## Store, feeds, backup

- **`Settings` schema-versioned.** `SCHEMA` in `src/lib/store.ts` bumps when a stored value changes _meaning_, not shape (→ `2` when `clock: "24h"` stopped meaning noon-at-top face). Stale schema resets settings to defaults, keeps events.

- **One validator, three readers.** `recur.ts` owns what a legal rule is: RFC range tables, `readRecurrence`, unknown → `Recurrence`. `backup.readRecurrence` (untrusted JSON), `store.hydrateEvents` (fields a blob predates), `ics.readRecurrence` (RRULE strings) — three _jobs_, shared rules; left to themselves they disagreed: backup clamped `interval` at 999, ics had no ceiling, the store range-checked nothing. Two keepers: **the exdate/rdate lists are read before the frequency**, an RDATE-only series being real (`repeats()` says so) and a bare `NEVER` for `repeat: "never"` losing every date a producer named on a `.json` round trip; and `hydrateEvents` keeps its identity fast path — asks _shape_, hands the rule over only when shape is wrong.

- **Store hydration lazy, at first `subscribe`**, not module scope. `load()` and `write()` swallow `localStorage` errors on purpose (private mode / quota must not brick the app) — but both `notify(…, "error")`: silent failure is indistinguishable from success, and that is how a day's events disappear. `load()` is sharper, starting the app **empty**, exactly what a first run looks like: the notice is the only thing telling them apart. `readFeeds` is the one silent catch, and says why — a corrupt payload is a cache miss the next pull replaces.

- **Every action derives from `fresh()`, never the module `snapshot`.** `fresh()` re-reads the blob when another tab wrote since we last looked; the in-memory snapshot loses that tab's events wholesale before its `storage` event lands.

- **Undo in-memory and session-scoped**, cleared on an inbound `storage` event _only when the base actually moved_: undoing onto a base another tab moved past resurrects what it deleted, but a background tab's **feed pull** writes the same key and used to cost the foreground tab all sixty steps — a loss the user can't attribute to anything they did. `baseSignature()` compares events + calendars minus their `feed` + settings. `undo`/`redo` carry today's `feeds` across, not recorded ones: a feed is a live mirror, never part of an undo step. `commit(next, false)` opts out of history — settings and feed pulls do.

- **A feed payload never shares the blob.** One `circal.feed.<id>` key each, budgeted: `FEED_BUDGET` (2M stored characters) split equally between subscriptions, re-divided every pull. Inside `circal.v1` a mirrored calendar is unbounded and competes with your own events for one ~5MB origin quota: one fat subscription made every later save fail. Quota is per origin — also why the cap is a shared total, not "1MB each" five times over. Over budget `trimFeed` keeps recurring events first (a rule is bytes describing years), then nearest today; the meta line says `1,228/4,000 cached`, a refused `setItem` drops the key and says `Not cached — no room`, both under twenty characters since that line is one `.label` wide and truncates. Legacy inline `feeds` migration runs in `hydrate()` — shared by `load()` and `fresh()`, either can see a blob first — rewriting the blob immediately, so it happens once. Deliberately **not** a `SCHEMA` bump: a bump resets settings, and where a payload is stored is not something a setting means.

- **`feedCache` is not a droppable optimisation.** `fresh()` runs on every action and re-reads every feed key; without the id → `{ raw, events }` map one 300-event subscription re-parses on every nudge of an arc. It also lets `sameFeeds` tell a change from a re-read, so `fresh()` won't hand React a new snapshot for nothing.

- **`seed()` only runs when no stored blob exists**, anchors on today's local midnight.

- **The backup nudge — why a data-safety setting defaults on.** `localStorage` is the only copy, "Clear site data" erases it without asking, and the macOS app and every Chromium browser answer with a live mirror; Safari and Firefox have no File System Access API, no way to hold a file handle: noticing no backup in a long time is the only answer they get. Hence `settings.backupNudge` **on** where `remind` is off: a reminder is a convenience somebody opts into, a warning about losing everything is not, and a prompt defaulting to off is one nobody meets. Interval from `BACKUP_INTERVALS` (7/14/30/60/90 days, **30** default, strays pinned by `sane()` like every enumerated setting). `backupDue(lastBackup, intervalDays, now)` in `backup.ts` is pure, taking `now` as an argument: same predicate in every zone, pinned in a test with no clock to stub.

- **Four decisions about that clock, each a way of not lying to the user.** Only the **`.json`** export advances it, and only when a file landed — `download` reports that, the macOS save panel being dismissable and a cancel that quieted the nudge a warning switched off by a gesture that saved nothing. An `.ics` never advances it: events handed to another app, not a restore path. A **live copy of either kind suppresses the line entirely** (`App.showNudge` reads `mirrorStatus.state !== "live"` **and** `cloudStatus.state !== "live"`): nagging somebody to export a backup they take continuously is the app not knowing what it does, and the cloud copy is the same document one transport over — the argument can't apply to one only. The Nudge caption in the settings panel says both: a switch whose behaviour depends on another panel two sections down looks broken. **Dismiss restarts the interval and does not switch the feature off** — "not now" is not "never", and `settings` is where never lives. A never-backed-up browser anchors at **first run**, not the epoch: from zero the app is overdue the instant it opens, a chore handed to somebody with no events, and no honest earlier anchor exists — an event's `start` is when it happens, not when it was written, and seed events aren't the user's work. `backupSnapshot()` stamps that anchor inside the getter `useSyncExternalStore` calls during render, so **without `emit()`**: notifying there would loop.

- **A line over the stage, on every view — the feature's whole risk.** Nothing in circal ever interrupted the user, so the change of character had to be as small as possible while still being seen: `BackupNudge` is one `.caption`, an export pill and a dismiss pill at the top edge, clear of the readout, reserving no layout when away, `pointer-events-none` except on the pills so it can't eat a click meant for an arc under it. A modal was the obvious build, refused for the same reason a `Suspense` spinner is. Off while `shaded` or in ambient (a notice over something that owns the screen is the interruption this design avoids), and above every view, not the dial alone: a warning met in one of four views can be missed indefinitely.

- **A VEVENT with no UID gets a _derived_ one, never a generated one.** `derivedUid()` in `ics.ts` = FNV-1a over DTSTART/DTEND/SUMMARY/LOCATION/RECURRENCE-ID as `<base36>@circal.local`. `crypto.randomUUID()` meant a new id per parse; `feeds.ts` keys events off the uid, so every pull remounted every arc — hover, selection, the arc under the pointer dropped. RFC 5545 requires UID: this fires only on a feed nobody can fix.

- **`zonedToUtc` brackets the wall time with two candidate offsets** — one a day before, one a day after — taking the pre-transition one when neither or both read back. Spring-forward gaps resolve to the instant _after_, fall-back ambiguity to the _first_ of the two, every zone. The earlier two-pass version converged from the naive UTC reading, so which side of a gap it landed on followed the offset's sign: Berlin right, Los Angeles an hour early.

## Recurrence

- **`src/lib/recur.ts` = somebody else's spec, not this app's idea.** RFC 5545 §3.3.10 expand/limit table: BY\* parts expand period into candidate days, given clock, BYSETPOS narrows, then bound. Verified against every worked example in §3.8.5.3. Never "simplify" a branch without re-running that suite — most exist for one example.
- **Seed = instance only when rule generates it.** RFC calls DTSTART first instance yet demands sync with rule; readings differ only for rule contradicting own seed. Editor can _write_ that (deselect weekday event sits on); event stuck on that day = bug user cannot fix. Synchronised rule generates its seed anyway.
- **Rule naming date some months lack simply does not fire there** — 31st, 29 February, fifth Friday (§3.3.10 invalid-instance rule). Only answer inventing no date sender never wrote.
- **COUNT walked into `until` on way in; model stores one bound.** `countedUntil` in `recur.ts`, called from `ics.ts`. Counting by _rule_, before EXDATE — RFC subtracts exceptions from generated set, so excluded day still spends one count. Count past `WALK_CAP` = unbounded, deliberately: over-running shows occurrences that should have stopped, guessing early deletes them; only second loses data.
- **`exdates`/`rdates` = local keys, two forms** — `YYYY-MM-DD` whole day, `YYYY-MM-DDTHH:mm:ss` one instant — exactly EXDATE's two RFC value types. Local: every other day-identity here is (see `dayKey`).
- **Every entry point capped.** `MAX_INSTANTS` (512) per call, `WALK_CAP` (2000) periods per COUNT walk. `SECONDLY` rule names 86,400 instants a day; feed not obliged to be reasonable. Truncation is visible, frozen tab is not.
- **EXDATE and RDATE = properties collected as lists.** Both legitimately appear on several lines of one VEVENT; flat prop map keeps only last — series regains every occurrence it was told to skip. Hence `Block { props, exdates, rdates }` in `ics.ts`.
- **RECURRENCE-ID = override _event_, not patch on series.** `seriesId` + `seriesKey` on `CalEvent`; `occurrencesOn` builds index once per query, skips generated occurrences an override claims. Separate event because that is what it is — own time, title, place, colour, maybe another day than one it replaces. `feeds.ts` MUST give it id including recurrence-id: it shares parent's UID.
- **`RANGE=THISANDFUTURE` resolved in `fromIcs`, not in a consumer.** `linkThisAndFuture` runs once every VEVENT is read, turning flagged override into tail of split series — shape `splitRule` and `store.splitSeries` already model, since that is what range means. There because `feeds.ts` and `backup.ts` each link overrides themselves; one wrong = series drawing twice. Five things to get right, three non-obvious: chained splits **fold left** (second cut measured against first cut's tail, which by then generates the instant); promoted tail takes `uid#recurrence-id`, drops `recurrenceId`, else collides with parent in both key maps; lacking own RRULE it inherits parent's rule with `splitRule`'s **partitioned** lists (merged with its own), else skipped days return; **ordinary** override past cut re-pointed at tail, as `store.splitSeries` does (on head it suppresses nothing, day draws both); cut at or before series' first instant makes tail **absorb** head, keeping its uid — `effectiveScope`'s "folds `future` into `all`" one layer down.
- **`EditScope` asked at press, never standing controls.** Three answers, `"one" | "future" | "all"`; scope belongs to the commit, not the event; one-off has one meaning, never asked. `EventEditor` holds `pending: "save" | "delete"`, swaps footer for question — replacing verbs, not stacking above them: two rows with one inert = footer that lies. Escape backs out, second press closes.
- **"This and all future" = two series; `splitRule` (`recur.ts`) is the whole decision.** Head takes `until = at - 1` (inclusive, bounds a _start_), or existing bound when earlier — split cannot extend series. **The exdate/rdate lists MUST be partitioned, not copied**: `until` bounds generated set only, so RDATE past it still fires, one left on head fires from both halves, future EXDATE not carried over resurrects a skipped day. `store.splitSeries` = one commit — two = two ⌘Z presses per edit, with a futureless series between them — and it **re-points overrides past the cut at the new series**: `seriesKey` still names the instant, so an override left on head suppresses nothing and day draws both it and tail's arc.
- **Splitting at series' first occurrence = "the whole series".** Head would generate nothing, so `effectiveScope` in `App.tsx` folds `future` into `all` — one live event, not two with one dead.
- **`store.remove` takes overrides with it** (`e.id !== id && e.seriesId !== id`). Orphaned override = ordinary event on the day it replaced, nothing explaining it, no surface finding it.
- **`Occurrence.key` = `${event.id}@${instantKey(start)}`.** Event can appear twice on a day now (hourly rule, BYHOUR list); day alone no longer identifies one.
- **Full recurrence shape filled at `store.parse`, not guarded at every read.** Older blob has no `interval`; `undefined` hits maths as `NaN` — series firing on no day. `hydrateEvents` covers `events` _and_ every `feeds` array, returns same object when nothing missing, since `parse` reruns on every cross-tab write. No `SCHEMA` bump: nothing stored changed meaning.
- **Day's query looks back exactly event's duration — whole multi-day fix.** `occurrencesOn` scanned one flat day back, so anything over ~48h existed two days then vanished (every feed holiday is that shape; `lifeDensity` already coloured days dial denied). Overlap test = `start + duration > dayStart`: exact in _milliseconds_, no DST reasoning (old `addDays(dayStart, -1)` guessed by day arithmetic). `lookbackCap` bounds it because lookback _is_ the recurrence window: `Infinity` for `never` (one-off costs one instant however wide), a year for ordinary frequencies, a **day** for `secondly`/`minutely`/`hourly` — `startsBetween` keeps _earliest_ instants, so a wider minutely window answers with last week's and the day vanishes instead of gaining copies.
- **`dayIndex`/`dayCount` on `Occurrence`; `spanLabel` = one voice.** `continuesBefore`/`continuesAfter` say only _that_ a span runs past the day, so a five-day holiday printed one row five times. `Day 3/5` replaces the time column in `CenterPanel` — on the third morning neither a clock time from three days ago nor "Now" answers. `dayCount` measured from `end - 1`: `end` is exclusive, one-day event must read `1 of 1`.
- **Headline row does _not_ get span column, measured.** `DAY 2/4` costs `Sleeper train` most of its letters at interior width; its wait already reads `ends in 45h 34m`, the multi-day fact, and the non-lead row prints position. Keep `!lead`.
- **`startsBetweenIn` = `startsBetween` walked over another zone's wall clock; that is all of zone support.** Feed's `TZID` says the rule was written against _that_ clock's transitions, not the reader's, so seed, window and `until` move into wall time via `wallClockIn`, the walk runs unchanged, results return through `instantOfWall`. `zone === ""` — every event user wrote — delegates through, so floating path costs one string check. Three consequences: `exdates`/`rdates` resolve _inside_ the delegated call, so read as that zone's wall keys, which `EXDATE;TZID=…` means; wall window widened by `ZONE_SLACK` (3h, DST's hour and double summer time's two) with real `[from, to)` re-applied, else an instant a transition moved across the bound is lost; wall time in the _viewer's_ own DST gap shifts an hour, since `wallClockIn` goes through the local `Date` constructor, normalising a nonexistent local time forward. That last is the file's floor — a local event at 02:30 that morning does the same — and closing it means walking the rule in UTC fields, i.e. every getter in `recur.ts`.
