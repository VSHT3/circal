## The mirror file, and the thing that reads it

- **The mirror file _is_ a `.json` backup, plus a `zone` and a `rev`.** Deliberately not a new format: same shape, same validators, so a mirror can go to Import and an export from before any of this to the mirror. `readMirrorFile` goes through `backup.readBackup`, boundary already assuming hostile input — something outside browser writing your calendar is exactly that, however well meant. An absent `zone` or malformed `rev` reads as "did not say" rather than failing file: losing a calendar over bookkeeping is the wrong trade.
- **A file, not a localhost bridge, and the reason is the tab.** A background daemon the page connects to only works while circal is open, making an assistant blind at unpredictable moments — worse than one never there. A file sits on disk whether tab exists or not. It also settles the other half of `AUDIT.md`'s oldest complaint for free: `localStorage` was the only copy, and "Clear site data" is one menu away.
- **`mirrorDigest` is what stops the file churning.** Mirror writes on every store change and a feed pull stamps `fetchedAt` on its calendar — so `serialiseMirror` zeroes a subscription's pull state (`exportBackup`'s own normalisation) and digest compares the three fields actually about the calendar. Without it every subscription refresh rewrites file and looks to a watcher like a changed calendar. Same trick as `baseSignature`, one layer out. An adopt records digest of what store **made** of contents, never contents' own — `adopt` normalises on the way in (`sane` clamps, feeds are swept), so file's digest can differ from store's, and recording file's answered every adopt with one extra write saying nothing.
- **A file ahead of us is merged where both documents are stamped, and adopted where either is not.** `mirrorVerdict`'s `adopt` used to mean "take their document whole", which across two machines discards a day: laptop edits Tuesday, PC Wednesday, and the undo step lands on the machine nobody sits at. `merge.ts` is the missing diff — `Grave` plus `CalEvent.updatedAt`, since a filtered array cannot tell _deleted here_ from _not seen here_. `mirrorMerges` is the gate, `MIRROR_VERSION` 2 what it reads: a v1 file, or `settingsAt` of `0` either side, gets today's adopt/stale behaviour exactly. `connect()` still adopts rather than merges, deliberately — the gesture is a person naming their calendar's file, and on a first run the local document is eight seed events that must not propagate. **`mirrorDigest` is canonical (`canonicalJson`) and cannot go back to `JSON.stringify`:** a merged document holds records from both sides, and an event stored here enumerates its keys differently from the same event rebuilt by `readEvent` out of the file, so an insertion-order digest reads a no-op merge as a change — both machines write, each reads the other's write as news, one write every poll for ever.
- **An undo restamps and buries; `adopt` never restamps and `restore` always does.** A step holds events as they were, _with the stamps they had_, so an undo put back a record the other machine's copy outranks and next merge silently reverted it. `merge.restamped` is the one answer: what a step changes is stamped now, what it removes is graved. `adopt` is exempt because what arrives is a merge or another writer's document, and re-dating it makes adopting machine win every subsequent merge wholesale — the bug this work exists to fix in a different hat. `restore` is not exempt: a user importing a backup asked for that file to win. Tidying that asymmetry into consistency reintroduces one of the two.
- **`rev` is the whole concurrency story, and `stale` does not adopt.** A writer reads, checks rev is still what it read, writes `rev + 1`. `mirrorVerdict` answers `ours` (we wrote it — adopting would loop), `adopt` (somebody moved it on) or `stale` (file is _behind_ us: an older copy restored underneath tab). Stale makes browser re-assert rather than adopt: winding a calendar backwards is the one outcome nothing undoes, and `localStorage` still holds newer truth.
- **Both halves keep that contract now; the browser did not, and it cost events.** `casWrite` in `mcp/file.ts` always read-checked-wrote. `mirrorLink.write()` went straight to `handle.createWritable()` — a blind truncate — so two events written through an agent vanished mid-session, no error either side: `onStoreChange` debounces `SETTLE_MS` (400ms) at `localRev + 1`, an agent writing inside that window does not move `localRev`, and the tab then wrote **its own `rev N+1` from memory**, so both writes carried the same number and nothing downstream could notice. `claim()` is the fix: re-read immediately before replacing, answer with the revision to write or `null` for no write. It reuses `mirrorVerdict` rather than forming a second opinion — the three answers are the same three — and only `adopt` changes anything, since `stale` re-asserting over an older copy is the anti-rollback already wanted. It **abandons rather than merges**: no diff here, only two whole documents, and merging by id resurrects anything deleted locally (`duplicateOf`'s resurrection rule from the other side). Adopting makes the casualty the _local_ edit instead of the agent's, and that one is recoverable — `store.adopt` records an undo step and toasts. The revision comes from disk (`max(found, local) + 1`), not a caller's arithmetic: two writes can queue behind `writing` and the second's number was worked out before the first ran. `absorb` is the adopt path `poll` and the guard share. Verified by driving the race through the shell bridge, not by reading it: pre-fix the agent's event is gone 600ms later, fixed it survives.
- **The window inside `casWriteOnce` is closed by an advisory lock, and the halves are deliberately asymmetric.** Between confirm-read and `atomicWrite` was a milliseconds-wide gap no re-read could close — the confirm-read _is_ the re-read. `acquireLock` takes a sibling `.lock` (exclusive create is the atom; mtime past `LOCK_STALE_MS` reads as a crashed writer and is broken; a live one is waited out to `LOCK_WAIT_MS`, then refused naming the file). Staleness judged by mtime, never pid: a pid cannot tell a dead writer from one on another machine, and a synced folder is exactly where a second writer lives. The browser cannot take that lock — a `FileSystemFileHandle` reaches one file, never its siblings — so on its side `withFileLock` (Web Locks, origin-scoped, exactly the writers sharing the IndexedDB handle) closes tab-vs-tab; browser-vs-server stays what it was, honest by `claim`'s re-read and the server's confirm-read, not excluded. Do not "simplify" either half onto the other's mechanism; neither can see the other's.
- **`atomicWrite` fsyncs, because temp-file-plus-rename alone was two thirds of what its comment claimed.** A rename survives a process crash, not a power loss, where `writeFile` returns with bytes in page cache and rename's metadata can reach disk first, leaving new name pointing at a short file where a complete one was. Temp file synced before rename, directory after — directory **best-effort**, since not every platform will open one and failing a write whose bytes are already durable over a durability nicety is the wrong way round, `remember()`'s trade one layer out. Temp file removed if anything after its creation throws.
- **A write is never a patch, so the reader refuses a file it does not fully understand.** Every mutation round-trips whole document through `readEvent`, which keeps fields it has names for and drops the rest — so an older reader writing a newer file silently loses exactly the fields it was too old to know about. Measured, not feared: published `circal-mcp@0.1.0` bundle drops ten keys per document (`free`, `travel`, `remindLead`, `organizer`, `attendees`, `attendeeCount`; `backupNudge`, `backupInterval`, `deviceZone`, `stampedZones`). `MirrorContents.version` carries envelope version — absent reads as this build's own, for the reason `zone` does — and `assertVersionAllowsMutation` refuses beside zone guard it mirrors. **No override env var**: an operator can reason about a zone mismatch and be right; "my reader is too old for this file" is not that. Reads still go through: reading cannot damage the file.
- **Remembering the handle must never fail a sync.** IndexedDB put persisting handle and rev is bookkeeping; write it follows already put calendar on disk. Reporting that write as failed because note did not stick is the wrong way round — and it is exactly what a browser with storage refused looks like, where file itself is written perfectly well. Found by driving it in a browser, not by reading it.
- **`store.adopt` says nothing itself.** `restore` without the toast: only caller knows which file moved and whether this was a sync or a reconnect. Undoable and owns its settings, so a wrong answer from an assistant is one ⌘Z away — also why `connect()` **adopts** a file already holding a calendar rather than overwriting it. Destructive direction is the one that cannot be undone.
- **`src/lib/mutate.ts` exists so the scope question has one answer.** `EditScope` — one / future / all — is asked at press in app and demanded as a parameter by server, both through same five reducers. Two copies of a three-way question drift into two vocabularies the moment either side changes. Server **refuses** a mutation on a repeating event naming no scope rather than picking one: guessing `all` deletes a year of standups.
- **The zone is in the file because every day boundary here is local.** `dayKey`, `startOfDay`, the whole of `tests/west/`. A reader in another zone would put events on wrong day and be confident about it, so server warns on a read and refuses a write unless `CIRCAL_ALLOW_ZONE_MISMATCH=1`.
- **The MCP server imports the app's own domain layer, and that is the point.** `parseQuickAdd`, `dayAgenda`, `freeGaps`, `scoreEvent`, `describeRule`, `readEvent`, `mutate.ts` — a second implementation of any is a defect, not a shortcut: it is how assistant and dial come to disagree about what Tuesday contains. `store.ts`, `backup.ts` and `notify.ts` import React but touch no DOM at module scope and guard their `localStorage`, so importing them in Node is safe. **Nothing in `src/` may import from `mcp/`** — browser bundle must not gain a byte from it.
- **Built on `@modelcontextprotocol/server` v2 (spec revision 2026-07-28), not the v1 `@modelcontextprotocol/sdk`.** v2 is `McpServer` + `registerTool` with Zod v4: one schema per tool, from which SDK derives the JSON Schema the model sees, validates arguments before handler runs, and infers handler's types. It also carries per-tool annotations that matter for a surface like this — `readOnlyHint` on the read tools (`sync_status` included), `destructiveHint` on `update_event`, `delete_event`, `update_task` and `delete_task` — which is what a client uses to decide what to confirm. **The task tools are their own five** (`list_tasks`, `create_task`, `update_task`, `delete_task`, `plan_task`, plus `toggle_done` as the completing verb — no separate `complete_task`, one verb per meaning; `delete_task` shares `performDeleteTask` with `delete_event`'s task branch, so the alias and the original cannot drift), through the same store shapes the app writes, so the assistant and the dial cannot disagree about what is planned; `create_event` has no task spelling left. **Write summaries name their hazards**: a create whose calendar was neither named nor pinned (`--calendar` / `CIRCAL_CALENDAR`) says `calendar defaulted, not named`, and a not-found reads the `graves` before answering, so a deleted id refuses differently from a typo. **`create_events` is one CAS cycle**, all-or-nothing, and a `key` mints the id (`x-<key>`) so re-running a mirror converges instead of duplicating — identity, not a new stored field, so merge semantics are untouched. Identity cuts both ways: a keyed create outranks a prior deletion’s grave (fresh stamp wins), so the app’s delete loses to the next mirror run — deliberate ("the source re-asserts"), said in the key schema’s own description, and a record is dropped for good at the source. Keys are bounded (`UPSERT_KEY_RE`, 64 chars, no control characters), re-checked in the domain layer per `assertDateKey`’s bargain. **A `zone` argument reads the times as that zone's wall clock** (`instantOfWall`, the travel pivot) and lands in `tzid`, the field the travel "keep" path already writes; every MCP surface then prints both clocks. **stdout is the protocol channel**: log with `console.error`, one `console.log` corrupts the stream.
- **`MirrorFile.remembered()` mints and adopts the default path when nothing is remembered and nobody has said no.** `~/Library/Application Support/circal/calendar.json`, created empty — the safe seed `poll()` reads as "nothing to adopt, the next write fills it" — so an assistant connects on first launch with no gesture at all, not merely no second one. `mirror.declined` in `UserDefaults`, set by `forget()` and cleared only by `pick()`, makes disconnecting stick: without it the next launch mints the default back and silently undoes what the user did. The save panel stays, for a file wanted in iCloud Drive or a repo. Destructive direction unchanged either way: adopting never writes content to a file it did not just create, so a picked or default path already holding a calendar is adopted, never overwritten — the one outcome nothing undoes, the argument `mirrorVerdict`'s `stale` case stands on. `circal-mcp --find` checks this exact path first, named outright rather than discovered, because it sits inside `Library`, which its walk otherwise skips on purpose.
- **A `FileSystemFileHandle` exposes only `.name`, never a path — true of the browser, and now only of the browser.** Deliberate privacy design, no way around it from inside a page, so on web circal cannot tell a user where their own mirror file lives on disk and cannot pre-fill it into a command; `circal-mcp --find` exists for that gap, searching instead of being told, and `/assistant/` explains the absence rather than papering over it. `AUDIT.md` Tier 6.2 named the exception before it existed: shell's own picker returns a security-scoped bookmark, which does resolve to a path, so `MirrorFile` in `mac/main.swift` reads it straight off to mint and adopt default location with no gesture at all — the standing complaint "stops being true the moment the shell owns it," and now does. Copy written for web build still may not claim to know a path it cannot resolve; `circal-mcp --find` still matters there, unchanged.
- **A `.ics` the Dock hands over is text, and the page owns the one import path.** `application(_:open:)` in `mac/main.swift` never parses a calendar — `src/lib/ics.ts`'s `fromIcs` stays the only parser — it reads the file as UTF-8 and calls `window.__circalImportIcs`, the exact function the settings panel's Import button calls, so a drop and a menu import cannot mean two different things: same new calendar, same toast, same undo step. The first draft flushed a cold-launch drop on `didFinish`, reasoning a finished navigation meant the page had registered the global — true before the lazy split, false the moment `Settings` and `EventEditor` moved into their own chunks and pushed the registering effect later still. `window.__circalReady`, posted from that effect the instant it runs, is what the shell now waits for before flushing anything queued; a reload clears the flag until the page posts again, so a drop from before cannot reach a page that has not re-registered.
- **`window.__circalSave` exists because `<a download>` does nothing in a `WKWebView`.** Measured: click resolved to nothing, so both `.json` backup and `.ics` export silently wrote no file at all in app build, while identical code downloaded correctly on web. `backup.ts`'s one `download()` helper is now async and checks shell's bridge first, falling back to anchor, so no call site learns there are two ways to save — the bargain `mirrorLink.ts` already strikes for its own picker beside `showSaveFilePicker`. It returns whether a file was actually written: shell's `NSSavePanel` can be dismissed, and `exportIcs`/`exportBackup` skip their toast on that `false` rather than announcing an export user just cancelled — browser anchor has no cancel to observe, so it always reports `true`.
- **The status menu's login-item and Dock checks read live, in `menuNeedsUpdate`, never a cached boolean.** A login item can be removed from System Settings → General → Login Items without circal knowing, and a cached check would have menu asserting something no longer true; same argument for Dock check, since `NSApp.activationPolicy()` is running app's own answer and nothing else can go stale either. `SMAppService.mainApp.register()` is off until asked, deliberately: a calendar that adds itself to login items unbidden makes people distrust software, and `register()` throwing surfaces through `bridge.note` rather than leaving a check that no longer means what it says.
- **Menu-bar-only mode costs the `.ics` Dock drop, and that is the honest trade, not a bug.** `NSApp.setActivationPolicy(.accessory)` removes Dock tile, and without a tile `applicationShouldHandleReopen` never fires — the drop two bullets up cannot land, leaving ⌥⌘C and status item as only ways back in. Applied at launch, before window exists: switching once window is up needs a re-activate and re-key to avoid leaving app behind others, and toggle does both. Default `.regular`: a mode somebody chooses after finding status item, never one they wake up in.

## The cloud row

- **Email OTP needs _two_ dashboard templates switched to `{{ .Token }}`, not one, and no code in this repo can assert either.** `cloud.requestCode` calls `signInWithOtp`, UI asks for code — but that endpoint mails whichever template Supabase picks by whether address signed in before: **Confirm signup** first time, **Magic Link** after. Switching only Magic Link is trap: _looks_ finished — setter-upper was already returning user when testing, so their sign-in works while every new address gets link in front of form demanding code. Every user once. Found hard way: first sign-in mailed `https://<project>.supabase.co/auth/v1/verify?token=…&type=signup&redirect_to=…`, and `type=signup` is tell, never touched Magic Link template. Fails silently: six empty boxes for code never sent. Neither migration nor client can check it — why it's here. Not first move: neither template _reachable_ until custom SMTP configured (next bullet). Set **Site URL** to `https://circal.day` same sitting — it left `redirect_to=http://localhost:3000` there; inert for code flow, but wrong, bites first time anything generates link. Code not link is deliberate: link needs registered redirect URLs, and inside `mac/`'s `WKWebView` no URL for mail client to hand back — secret travels through person, not platform.
- **Both templates are files in this repo — `supabase/templates/` — dashboard still only thing that sends them.** `confirm-signup.html`, `magic-link.html`, plus `README.md` naming slot and exact subject each (`Your circal sign-in code`, same string twice: subject saying "link" over mail carrying code reads broken before opening). Twins on purpose: one endpoint, two templates, one reader who can't tell which arrived. Pasting manual, one-way — nothing reads dashboard back, so template edited in web form but not repo = change nobody can diff, rebuild silently loses. Edit file, verify, commit, paste. Light mail, not circal's black; reasoning in README: several clients force-invert dark mail, Gmail mobile re-colours on own terms, so black mail arrives as somebody else's guess at black, reads as fault. **Mails count no digits, state exactly one duration** — "fifteen minutes", this project's **Email OTP Expiration** of 900s, named in README beside dashboard field so both move together. Those two facts belong to somebody else's config; first drafts got both wrong in one line ("Six digits, good for one hour") — how reliably shape returns: length is `maxLength={6}` bullet below in different clothes; expiry stated long sends somebody back to code that died while mail said it hadn't.
- **Custom SMTP not a nicety beside those templates — it makes them exist.** Supabase gates auth template editing behind configured SMTP: on built-in sender, nothing to edit, no `{{ .Token }}`. Provider first, templates second; built backwards, you hunt a field that isn't there. Built-in sender agrees: couple messages an hour, on current projects only to project's own team — no custom SMTP = single-user however templates written, not why anybody switched sync on. Two dashboard settings same sitting, neither moves when provider does: auth email rate limit stays where built-in sender left it, raise by hand or new headroom invisible; OTP expiry defaults to an hour — long for a code arriving inside a minute. This project's **900s**, by hand, templates say "fifteen minutes": move one, move other same sitting or mail promises time the code lacks.
- **Client key is `PUBLIC_SUPABASE_PUBLISHABLE_KEY`; rename is the point, not tidying.** Supabase issues `sb_publishable_…` browser, `sb_secret_…` server, demoting `anon` / `service_role` JWTs to Legacy tab — publishable key **is not a JWT**, so `ANON_KEY` told next reader to decode payload-less thing. `cloudLink.ts` names one variable, deliberately no fallback: config taking either name makes deployment still on `PUBLIC_SUPABASE_ANON_KEY` look fine, and failure mode is _absence_ — `config()` returns `null`, no panel, nothing reports it. Verified against `@supabase/supabase-js` 2.112.3 before rename: library is where non-JWT key would break. `checkApiKeyFormat` recognises `sb_publishable_` prefix, never throws; `signInWithOtp` / `verifyOtp` send it as `apikey` plus Bearer; `decodeJWT` only on `session.access_token`; Realtime carries it as connect param, stores whatever `setAuth` gets verbatim — decodes nothing. Re-check Realtime on upgrades: `_getAccessToken` falls back to api key with no session, so key reaches socket as token — harmless only while nothing there parses it. `sb_secret_…` bypasses row level security, never a `PUBLIC_*` variable.
- **One live copy at time, panel = only enforcer.** `SYNC.md` leaves it to UI — two writers each debouncing 400ms into doc other merges = deliberate state — so `Settings.tsx` computes `mirrorEngaged` / `cloudEngaged` as `state !== "off"`; nothing lower knows. `off` = only empty state: `prompt` = remembered handle or signed-in session, `error` = one gesture from writing, both engaged. **Advancing** verbs (Connect, Resume, Send code, Sign in, Unlock) dead while other engaged; **retreating** (Disconnect, Sign out) never — browser can arrive holding both, session predating file pick, must drop one. Change one side, change other, or panel = room with one door.
- **Cloud panel prints transport's sentences, reads exactly one.** `cloudLink.ts` writes both failure sentences, so panel prints `status.message` verbatim — no second vocabulary to disagree. One comparison: exported `LOCKED`, picks **remedy** not words — locked box wants passphrase; no completed pass (`at === 0`) wants its step; else key in memory, unreachable row, Try again = fix. Panel deciding itself = one failure, two descriptions.
- **Sign-in flow records what it did, never what worked.** `Stage` = user gesture — `email` / `sent` / `answered` / `opened`; `Asking` = row display, stage vs transport verdict. Empty `status.name`: code never sent, re-ask address; `answered` plus `error` = refused code, not session. Optimistic advance = how refused code asked passphrase — unlock form, nobody signed in.
- **"Nothing leaves this browser" is now a claim about a _configuration_, and every sentence shaped like it is a standing hazard.** Four captions + one manifesto line argued from it, false day row shipped — Reminders caption, life span row's birth date, Backup row's "only copy", `/manifesto/`; now argue from what stays true: circal _runs_ nowhere but this browser, synced copy leaves sealed. `/assistant/` sharpest, check first: readers likeliest signed in. Argues about mirror _file_; honest claim = file half sends nothing anywhere — blanket "nothing goes to the internet"/"there is no account" = whole-app claim, one gesture from false. Two clauses survived only on "sees"; sentence resting on careful parsing doesn't hold. Such claim means owning its audit: `grep -riE "leaves this browser|no account|nothing.*internet" src/` first.
- **`stamped` asks whether doc carries stamps _at all_; tightening back to `settingsAt > 0` reintroduces worst bug this feature has had.** One comparison, read correctly: `freshInstall()` withholds `settingsAt` so demo day cannot win merge. Missed: two fresh installs, one account, **both** unstamped, neither merges, each adopts other's doc whole — adopting unstamped doc leaves you unstamped, never grow out. Measured, two browsers one row: first event on new laptop adopted away by whichever machine synced next, silently, only undo step on machine nobody watched. "Set up my second machine" = whole reason to switch this on — not edge case, the case. Predicate now `settingsAt > 0` **or** any event, calendar or grave with real instant — what name always claimed. Protection is about **demo data, not settings** — `seed()`, `DEFAULT_CALENDARS`, `duplicateOf` carry `updatedAt: 0`, comment saying why, so browser holding only first run answers `false`, cannot merge, cannot publish eight events nobody wrote (verified: after fix two machines converge on ten events, not eighteen). Merging begins at first real edit — first instant anything needs defending. **A grave counts as a stamp**, subtle half: machine whose only news is a deletion carries no other instant, so records-only reading blocks merge, and that deletion is what gets adopted away — tombstone losing to the absence it exists to be distinguished from. Pre-Phase-0 blob untouched: every stamp reads `0` via `hydrateEvents`' fill-in, still adopt-or-refuse.
- **Client hard-coded length identity provider owns; field truncated silently.** `Settings.tsx` rendered code input `maxLength={6}` — "Six-digit code", placeholder `000000`, `w-[8ch]` — but project's Supabase setting mails **eight**, so eight-digit code kept first six, `verifyOtp` got prefix of real code. Back: 403, `otp_expired`, _token has expired or is invalid_ — same answer superseded/stale code gets — so two days of auth logs read as inbox problem, not input. Every clue corroborated wrong story: token in `auth.one_time_tokens` unconsumed, `last_sign_in_at` still at first attempt's confirmation link, fifteen seconds send-to-submit, too fast to read fresh mail. All fitted "they typed an old code"; none was bug. Shape beats number: **silent cap on value that must match authority elsewhere turns careful user into wrong answer**, error about _validity_, never length — evidence points at far end of wire, one place fault is not. Hence `CODE_MAX` (32) in `cloudLink.ts`: guard against pasting essay into code field, deliberately not description of code. Copy says "code" where it counted digits — field label, placeholder, `requestCode`'s status sentence, panel caption, `README.md` — digit count in UI = claim about somebody else's dashboard, same hazard as two templates above. Nothing to test: defect was JSX attribute, fix is its absence; asserting `CODE_MAX === 32` would restate constant.
- **Write-back not optional, so every sync has second pass, and silence must come from comparing documents, not suppressing notice.** Both machines converge on row, so first writer sees own edit return as other's `rev + 1`: A writes, B merges, adopts, toasts — correctly, B learned something — B writes merged doc back, A finds row ahead of _its_ revision, merges doc byte-for-byte what it had. A told own event was news, undo behind it undid nothing: `store.adopt` records commit whether or not commit changes anything. Rule: **an absorb which does not change the local document must be silent** — no toast, no `store.adopt`, only bookkeeping — so `cloudTake` answers `learned` beside `changed`, `poll` calls `settle` not `absorb` when false. Separate questions, neither implies other: `changed` = row needs our bytes, `learned` = store needs theirs; row merely behind wants write with nothing to announce. Answer _not_ which tab focused, or which device originated write. Genuinely remote change in focused tab should still say so; only honest question is whether document moved. `settle` keeps all `absorb` bookkeeping, `localRev` and `lastDigest` both: dropping either trades one spurious toast for spurious write every `POLL_MS`.
- **`mirrorDigest` had to stop reading record _order_ as a change before any of that could work, and this is the second time this digest has been the whole bug.** Key order first (see comment in `mirror.ts`); array order = same mistake one level out. `store.create` **appends** → creation order; `unite` in `mergeDocuments` sorts by **id** on purpose: makes `merge(a, b)` = `merge(b, a)`. Orders coincide only where events made alphabetically → `learned` true every return trip, fix above did nothing until digest sorted too. Array order no more part of document than key order: nothing renders from it, views sort by time. Cuts writes: order-only diff earns no write-back. File half gets this free, needed it — `mirrorLink.absorb` had identical defect, guarded there not in a decision function: both callers funnel through it.
- **Grave list = one entry per id, later instant wins; `store.write` must enforce — every reader assumed it, no writer did.** `readGraves` collapses on read, `pruneGraves` in every merge, but `remove`, `truncateSeries`, `removeCalendar` _appended_ and `restamped` concatenates both sides: delete undone then redone left two graves for one id, row held one. Same document by every reading rule, two arrays to `mirrorDigest`: deleting machine told its own deletion was news — forever, every pass, nothing settles it. Collapse in **`write`**, not `commit`: undo/redo call `write` directly. Calls `pruneGraves` not restating rule, same reason as hydrate — merge's and store's grave list must not diverge — skips below two entries, can't duplicate: runs every commit, common snapshot has no graves. Fix at write, not teach readers tolerance: readers were already right.
- **"Stay unlocked" keeps derived key, never passphrase, and IndexedDB record _is_ the switch.** `vault.ts` splits into `derive` (passphrase + salt → `{ key, salt }`) and `vaultOf` (that pair → today's `seal`/`open`), `unlock` = composition, no caller moved. Key already `extractable: false` — unlike writing secret down: `structuredClone` and so IndexedDB take `CryptoKey` as opaque handle, so **kept** and **used** while `exportKey` refuses. Salt travels with it, can't be derived from it — `seal` stamps salt into every box's header, so key without one opens what it's handed, produces nothing; `saltOf` can't supply it before first row. **Storage:** own database, not `Settings` field, not fifth `localStorage` key. `Settings` is synced, so "remember on _this_ device" there would arm every other device the moment switched on here — setting contradicting its own name; `localStorage` holds strings, `CryptoKey` isn't. No separate flag: remembered key and intention to remember are one fact, two = two things to keep in step. Record carries `user` so signing in as somebody else discards, not resumes. Off deletes now, not next launch — withdrawing authority is what gesture means — and `disconnect` forgets it before clearing `userId`, for `mirror.declined`'s reason one transport over.
- **Stale-salt path = whole risk in remembering key, third time feature could blame person for own bookkeeping.** Row re-sealed under another salt — another device enrolling against empty row, passphrase changed elsewhere — leaves key opening nothing; ordinary path reaches `open`, throws `WrongPassphrase`, arrives `LOCKED`: _that passphrase does not open the cloud copy_, to somebody who typed none. So `cloudResume` compares stored salt to `saltOf(row.payload)` **before** trusting key; mismatch discards record, prompts `RESEALED`, naming cause. Two readings deliberately _not_ stale: empty row = nothing to compare; unreadable payload = damaged box, not stale key — either sends user to useless prompt. Sentence must outlive pass earning it: `startCloud` runs from `useEffect`, StrictMode mounts twice, first version set `prompt` inside `resume` — second pass found record gone, took ordinary refusal, overwrote explanation with generic sentence. Any remount does that. Hence `resealed` = module state, one place sets `prompt`. Found by driving, not reading.
- **Deleting cloud copy deletes a _row_; panel says so in clause, not implying account erasure.** Removing auth user needs service key — can't be in browser, wants server component `SYNC.md` refuses — so delete leaves email in auth table, nothing attached. `DELETE` scoped by `user_id`; `own_document` policy `for all` over `user_id = auth.uid()`, checked against live project, not assumed — row is all request reaches. Separate press from Sign out, neither does other's job: "not on this device" vs "not at all".
- **Order is feature: `cloudPlan` answers missing row with `write`.** Right — empty slot is what first link sees; one row can't tell "deleted" from "not yet written" without tombstone in table whose whole content is that row — but any pass after delete restores calendar. So `quiesce` first, `vault = null` is the disarm: `write`, `poll`, `onStoreChange` each refuse on null vault, so one assignment disarms settle timer, fallback poll, socket callback, visibility tick; `hush` closes socket so delete isn't returned as change; `await writing` lands in-flight request _before_ row goes. Then delete, then `release` — clears `REV_KEY`, else later session starts at remembered revision, reads empty slot, refills. Second signed-in device still re-publishes: inherent, not overlooked — holds calendar and live link, row is where live link puts it.
- **Failed delete stands link down too; driving it settled that.** V1 restored vault, re-listened: nothing deleted, nothing changes. Measured: `DELETE` then `GET GET POST` — calendar back at fresh revision seconds after someone asked it gone: `DELETE` can commit yet fail returning, restored link refills slot next pass. Ambiguous case = only divergence, and one that matters. Rule: **never put back what a person asked to remove**. `release` runs either way; `UNSURE` says copy may persist, no guess. Clear failure costs needless sign-in; other way costs what button was for.
- **`cloudPlan` holds an unstamped document back from an empty slot — the two-fresh-installs bug's publish half.** Nothing gated the write path: a fresh browser signing into an empty account published its demo day, and the user's real machine first-links with `merging: false`, adopting it whole — undo session-scoped, so a reload made it permanent. `hold` writes nothing until `stamped(store.snapshot())`; first real edit stamps, next pass publishes. Only the empty slot is gated: an existing unstamped row still adopts (a pre-Phase-0 calendar is also all-zero stamps — real events, not demo; asserting over it loses a legacy user's data, which is why the reviewer's "local wins over unstamped" fix is wrong and was not taken). Pre-Phase-0 publish is delayed to first edit, never dropped.
- **A row sealed under another salt stands the link down (`standDownResealed`), never re-asserts.** `stale` + foreign salt = a recreated box (delete + fresh enrolment elsewhere, passphrase changed) this key cannot even open; re-asserting overwrites it blind. Both `poll` and `claim` check `cloudResume(keyed.salt, found.payload)` right after the fetch; mismatch drops vault/key/rev bookkeeping and prompts `RESEALED` — which also fixes the read side, where a re-sealed row used to surface as `LOCKED` to somebody who typed no passphrase. Next unlock derives from the new box's own salt and adopts, undoable.
- **`unlock` re-keeps the remembered key only after the first pass succeeded.** Before: `keep(keyed)` ran pre-validation, so a mistyped passphrase (reachable when `resume` failed on a network error, which returns `false` without `forget`) overwrote a good remembered key with one that opens nothing.
- **Settle timer's callback re-checks the digest; `absorb` clears the timer.** `store.adopt` emits synchronously, so `onStoreChange` ran against the digest the adopt was replacing and armed a write that echoed the adopted document back at rev + 1 — every absorb cost one spurious write waking every device. Same re-check in `mirrorLink.onStoreChange`. And `poll`'s `keep` branch seeds `lastDigest` off the row when a session starts (one decrypt), so the first no-op emit of a session no longer writes an identical document — while offline edits are delivered on that same pass rather than riding the next unrelated emit.
- **An error must not strand outbound sync.** `onStoreChange`'s `error` gate is gone (a failing pass must not swallow edits) and `fail()` arms the fallback poll while a vault stands — one transient 503 with a healthy socket used to stop sync in a visible tab until a remote write arrived. The interval stands itself down once `subscribed && live`, or when the vault is gone.
- **Panel verbs are `try`/`finally`, and `connected()` catches its own chunk fetch.** A supabase-js import that failed (offline first sign-in) threw past `setSigningIn(false)` and wedged every cloud button until reload — the panel stays mounted across open/close, so nothing else reset it.
- **The locked branch carries the delete strip — the way out of a lost passphrase.** Delete lived only on the `live` branch, so the one person who most needs to start over (forgot the passphrase; `LOCKED` for ever) could never reach it. `deleteCopy` needs the session, never the key; `deleteStrip` is one shared two-press strip whose caption names which of the two things it is doing, and the render-phase confirm reset allows `cloudLocked` alongside `live`. The code step gained "Send a new code" for the same shape of dead end: an expired code used to cost the round trip through Change address, which signs out.
- **`startCloud` watches `SIGNED_OUT` and stands down with a toast.** A session that expires under a live link answered every pass with an auth error whose "Try again" could not succeed. Idempotent against our own `release` (it clears `userId` before signing out). The remembered key survives — passphrase authority, not session authority. Cleanup also removes the Realtime channel, and `listen` removes any channel already up, so a remount cannot double every delivery.
