# Repository Guidelines

## Project Overview

**circal** = calendar whose day view is a single dial — web recreation of Raycast macOS app _Radical_. One revolution = one day, clockwise 0.25°/minute. Events = arcs; elapsed day = ramp of light round rim; hand = current minute.

Four views, one idea at four scales: **dial** (`⌘D`) = one day · **week strip** (`⌘E`) = seven of the same face at one rotation · **year ring** (`⌘Y`) = one revolution per year, one mark per day · **life grid** (`⌘L`) = every day you get, one dot each, birth date to expectancy, one viewport. All four draw days in day order ⇒ the moves between them are geometry, not decoration. Day ⇄ life = _zoom_: dial collapses onto the dot of the day it shows; grid wave radiates from it. Day ⇄ week = _zoom_, one step less far: the strip's face for that day **is** the dial ~4× smaller, so the dial scales and translates onto it. Year ⇄ life = _unroll_: a year in day order round a circle **is** a life-grid row rolled up, so the ring straightens onto that row and back. Every other pair crossfades (a day is neither a magnified nor a rolled-up year; a week is neither).

`Clock` picks only what the face is _called_, never geometry. `12h`: noon top, labels `12 · 1…11` twice with AM/PM captions. `24h`: midnight top, labels `00 · 1…23`. Switch = 180° rotation + relabel ⇒ an event arc has the same length and sweep on either face. Also governs **every printed time** (readout, agenda, sidebar, palette, editor) ⇒ `splitTime` / `formatTime` / `formatTimeShort` all take `Clock`; any surface printing one MUST thread it.

No account and no sync **unless a user asks for one**, and no server-side state that is readable: user events live in `localStorage` under `circal.v1`, and the optional cloud copy is one Postgres row per user holding AES-GCM ciphertext `vault.ts` sealed in the browser (`cloudLink.ts`, `SYNC.md` Phase 2). Somebody who never signs in runs the app the sentence used to describe, byte for byte — `supabase-js` is fetched only when sync is switched on. Ships as a Cloudflare Worker serving static assets plus **exactly one route** — `/api/feed`, CORS proxy for ICS subscriptions, because no calendar host sends CORS headers. `supabase-js` talks straight to `*.supabase.co`, so that route is still the only thing the Worker serves and the rule it defends is intact: a second route = a different product; stop.

`README.md` = user keyboard table + feature tour. This file = what you need to _edit_ code safely.

## Architecture & Data Flow

```
src/pages/index.astro   static HTML shell  (src/pages/manifesto.astro = prose, no island)
  └─ <App client:only="react" />        ← the ONLY island in the project
       ├─ useStore()   → { events, calendars, feeds, settings }   (persisted)
       ├─ useState ×5  → location{day,view}, sidebar, editor, palette, settings
       ├─ useNow()     → ticking Date, minute-aligned
       ├─ useReminders() → the minute tick → `Notification`, when switched on
       ├─ useTitleCountdown() → the same tick → `document.title`, only while hidden
       └─ actions: ShellActions (one useMemo object)
            ├─ TopBar / Sidebar / CommandPalette / Settings  receive `actions` whole
            └─ Dial / EventEditor / YearView / LifeView      receive narrow callbacks

  Settings travel as one `settings: Settings` prop, never field by field.
```

- **`src/lib/` = domain layer**, mostly pure. One-way deps: `time.ts`, `fuzzy.ts`, `base64.ts` (base, import nothing) ← `vault.ts` ← `recur.ts` ← `dial.ts`, `events.ts`, `sun.ts`, `moon.ts`, `ics.ts`, `quickadd.ts` ← `describe.ts`, `life.ts`, `remind.ts`, `travel.ts`, `merge.ts`, `store.ts` ← `feeds.ts`, `backup.ts` ← `share.ts`, and `mirrorLink.ts` / `cloudLink.ts` last of all, one per transport. `merge.ts` sits beside `mutate.ts` for `mutate.ts`'s own reason: it is pure over lists, imports `./events` and nothing else, and takes `Settings` as a _type parameter_ rather than importing it, because `store.ts` is above it and a merge needs no field of it. `base64.ts` was carved out of `share.ts` rather than spelled a second time in `vault.ts`: an alphabet swap written twice is two chances for one end of a payload to disagree with the other, and a box nobody can open has no undo step. `vault.ts` sits one step above it and imports nothing else — a passphrase and WebCrypto, no event, no day, no zone. `cloudLink.ts` sits at `mirrorLink.ts`'s tier, composing `store.ts`, `merge.ts`, `mirror.ts`, `vault.ts` and `notify.ts`, and **the two links do not depend on each other at all**: its one reference to `mirrorLink.ts` is `import type { MirrorStatus }`, erased at compile time, so what they share is a status vocabulary rather than a runtime edge or a copy of it that drifts. Components import via `@/lib/*`; never reimplement geometry or date maths locally. `share.ts` sits last on purpose rather than beside `travel.ts` where its subject would put it: it reads a stranger's payload through `backup.readEvent` instead of deciding for itself what a legal event is, and taking a validator from a tier means sitting below that tier. **Every module here has a test file** `tests/<module>.test.ts`; change one, add the case there.
- **That dependency order is a _constraint_, not a description — and the difference is load-bearing.** It has been violated exactly once, and the way it went wrong is the instructive part: per-event reminder leads shipped with `ics.ts` importing `remind.ts` for the three lead states. Acyclic, so nothing failed, no lint fired and no test could have — a tier is not a type. A reader who notices the imports and the sentence disagreeing has two honest options, **move the code or change the constraint**, and noting the discrepancy is neither: the ordering is what makes the graph legible, and a graph nobody can predict is one where the next import is chosen by what compiles. This one was resolved by moving, along the split marks already use — see the lead vocabulary under "Reminders".
- **Store = only source of truth for persisted data.** `App.tsx` holds _view_ state only. Mutations go through `store.*`, never a `setState` copy of an event. Settings-only mutations (`setSecondZone`, `setPlace`, `addFeed`) called straight from `Settings.tsx`, not via `ShellActions` — the shell has nothing to update for them. `removeCalendar` = exception also called from there: it is a calendar action, and removing a subscription is the one way a calendar leaves from the settings panel.
- **Two event lists, two _keys_.** `snapshot.events` = what the user wrote; `snapshot.feeds[calendarId]` = what a subscription mirrored. `App.tsx` concatenates them into `visible` for rendering and _only_ that. Nothing writes `feeds` except `lib/feeds.ts`; nothing exports it; an event whose calendar has `feed` opens read-only. `feeds` = **read model**: assembled from one `circal.feed.<id>` key per subscription, the one `Snapshot` field `write()` never serialises.
- **`dayAgenda(events, calendars, day)`** = single read path onto a day: expands recurrence, clips to day, packs overlaps onto concentric lanes. `Dial` and `CenterPanel` render from its output; the sidebar reads `occurrencesOn` directly, for the mini-month dots only.
- **Units.** Inside the dial everything = _minutes since local midnight_ (`0…1440`). `CalEvent.start`/`end` = **epoch ms**, `end` **exclusive**. Nothing downstream of `dayAgenda` reasons about `Date`.
- **Day and view = URL.** `?d=YYYY-MM-DD&v=year|life`, written through `go()` in `App.tsx`: `push` for a deliberate jump, `replace` for arrow stepping. `go` reads current location from a ref, not the render closure — two `go` calls in one tick would clobber each other. `v` omitted for day view, validated against `VIEWS` on the way in.
- **Panels take `settings` whole, not one prop per field.** `Dial` reads twenty-two of them, `Settings` thirty-seven of the interface's thirty-eight (`deviceZone` is the shell's business, not the panel's); threaded individually, one new boolean meant editing six files (`Settings` interface, panel prop interface in `types.ts`, `App.tsx` forwarding, panel destructure, `backup.ts`). Those counts are why the rule is not a preference: at twenty-two the forwarding is the file, and the four settings the backup nudge and the travel notice added between them cost the panel one line each instead of six files each. Same bargain as `actions`: one prop, shell has nothing to forward. Panels destructure on the body's first line, so bodies read exactly as before. `LifeView` was the last holdout at four fields and converted the moment it wanted a sixth. `zonePlace` = the one exception, its own prop: the shell derives it from `settings.secondZone` via `placeForZone`, so it is not a setting.

## Development Commands

```sh
pnpm install
pnpm dev        # astro dev — http://localhost:4321. NO /api/feed here
pnpm dev:worker # astro build && wrangler dev — the only way to exercise /api/feed
pnpm build:mcp  # esbuild → mcp/dist/circal-mcp.mjs, the MCP server's single-file bundle
pnpm build:mac  # astro build && mac/build.sh → mac/build/circal.app (1.3M)
pnpm mac        # the same, then opens it. `bash mac/build.sh --universal` for both arches
pnpm test       # vitest run — two TZ-pinned projects
pnpm test:watch # vitest
pnpm verify     # THE gate: format:check && lint && check && test && build
pnpm format     # prettier --write . (run this, never hand-format)
pnpm deploy     # astro build && wrangler deploy
```

`pnpm verify` = only quality gate; run before declaring work done. Steps: `pnpm format:check`, `pnpm lint` (eslint), `pnpm check` (astro check / tsc), `pnpm test` (vitest), `pnpm build:mcp` (esbuild — so the bundle's `--external` and `--alias` flags are exercised by the gate, which is how a stale published bundle once stayed invisible), `pnpm build`.

Format and lint carry `--cache`, written into `node_modules/.cache/` (already ignored, no new entry): the whole gate is ~25s cold and ~8s on a repeat, which is the difference between running it and not. Both caches key on config **content**, not mtime — an edited rule or a changed `printWidth` re-checks every file, verified by injecting a rule and by moving `printWidth` to 40 and counting the 95 files it flags either way. A fresh checkout and CI have no cache, so they gain nothing and risk nothing.

## Git & Commits

Commit **regularly** — one commit per coherent change, not per session. A commit touching dial geometry, store schema and a doc in one breath cannot be reverted, bisected or reviewed.

- **Conventional Commits**: `<type>(<scope>): <imperative summary>`, scope optional. Types: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`, `build`, `ci`, `style`, `revert`.
- Subject ≤ 50 chars where it fits, hard cap 72. Imperative mood, lowercase after colon, no trailing period.
- Scope = area, not filename: `dial`, `center-panel`, `store`, `events`, `time`, `sidebar`, `palette`, `editor`, `styles`.
- **Body only when _why_ is not obvious** from the diff (rendering artefact worked around, schema bump, reverted decision). Wrap at 72, bullets `-`, issue refs last (`Closes #42`).
- Never: AI attribution trailers, "this commit does X", emoji, restating a filename the scope already names.
- Run `pnpm verify` before committing. Gate is per-commit, not per-branch.

## Code Conventions & Common Patterns

**Imports** — always `@/*` alias (`@/lib/events`, `@/components/react/types`), never deep relative paths out of a directory.

**Formatting** — Prettier, `printWidth: 100`. `prettier-plugin-tailwindcss` sorts Tailwind classes automatically, including inside `cn()` and `cva()`. **Never hand-sort class strings**; run `pnpm format`.

**Styling** — Tailwind v4, config-less; theme in `src/styles/global.css`. Use token utilities, not raw hex:

| Utility                          | Token                             | Use                                     |
| -------------------------------- | --------------------------------- | --------------------------------------- |
| `bg-void`                        | `#000000`                         | canvas, true black                      |
| `bg-surface` / `bg-surface-2`    | `#131315` / `#1d1d20`             | popovers & cards / controls inside them |
| `border-hairline`                | `rgba(255,255,255,.08)`           | every divider                           |
| `text-ink`                       | `#ffffff`                         | only pure white                         |
| `text-ink-2` / `ink-3` / `ink-4` | `#8e8e93` / `#5c5c60` / `#2e2e31` | secondary / numerals / ticks & disabled |
| `text-accent`                    | `#a3d9e4`                         | default calendar colour                 |
| `text-danger`                    | `#ff5a5a`                         | destructive only                        |

`fill-*` / `stroke-*` variants exist too, used in SVG. Component classes: `.label` (uppercase 11px mono, label voice), `.caption` (12px sans at `ink-2`, prose voice — anything reading as a sentence), `.kbd`, `.fade-y` (mask both ends of a scroll area), `.fade-b` (bottom only, proportional — short list whose first row must stay crisp), `.no-scrollbar`. Pair fade with `.no-scrollbar` on every scroll region; apply fade **only when the list actually overflows** — permanent fade on a fitting list reads as a rendering fault. Chrome greyscale by rule: **colour belongs to events.** Never read `calendar.color` or `event.color` directly — call `colorOf(event, calendars)`: event override first, else its calendar. Presets in `PALETTE` (`src/lib/events.ts`): ten digital pastels, high value, moderate saturation so two can share a dial at 14-unit stroke. **`text-danger` is destructive only, and a link being down is not destructive** — neither the mirror's nor the cloud's error sentence is printed in it, because the calendar is whole in `localStorage` either way and red spends the word "emergency" on a socket. `feedMetaClass` remains the documented exception: a subscription that stopped fetching is showing days that are quietly wrong, which is the one failure in this app's chrome that earns the colour.

**New chrome MUST reuse `ui/primitives.tsx`** — `Kbd`, `FieldRow`, `IconButton`, `ActionPill`, `Segmented`, `Switch`, `Toggle`, `Select`, `DateField`, `NumberField`, `TimeField`, `TextField`, `ColorPicker`. Never hand-roll a button. `FieldRow` = modal row grid shared by event editor, calendar card, settings panel; three modals with three row grids is three products. `Toggle` = `Switch` + own text label, for settings sitting two and three to a row. `DateField` = native `input[type=date]` under a face of your choosing; `openDatePicker` lives beside it, because clicking a date input's field opens nothing in Chrome or Safari. `TimeField` = the app's own clock input — `input[type=time]` is banned because it renders in the _browser's_ locale, not this app's — and it moved here the moment the settings panel became its second caller beside the event editor. `TextField` = one line of typed text at the settings row's own shape, and it takes **`onEnter` rather than living in a `<form>`**: these fields sit inside a dialog whose Escape and ⌘-combos are live, and a form's implicit submit is a second Enter handler nothing in that dialog can see. It arrived when the cloud panel wanted three of them (address, code, passphrase) and the feed URL's bare `<input>` became the fourth caller — which is the rule working: a fourth hand-rolled input is where a convention would have formed by accident. Its `type` is a closed set on purpose — `password` is what a passphrase field _is_, `email` and `url` are what put the right keyboard under a thumb, and nothing else is a text field's business. `ColorPicker` takes optional `fallback`: pass it for an _event_, where `""` = "follow the calendar"; omit for a calendar, which has nothing above it to inherit from.

**Touch targets grow, they are not padded.** Every mouse-sized control in `primitives.tsx` carries a `pointer-coarse:` variant making it finger-sized — 40px `IconButton`/`ActionPill`, 36 a `Segmented` item, 34 a position cell, 30 a swatch. Grown rather than given an invisible 44px hit area, because these sit two and three to a group at a 2–3px gap: a box wider than the pitch reaches past its neighbour's centre and DOM order decides the tap, which is worse than a small target that is honest about where it ends. `Switch` = the one exception, does take a 44px `::before` — its knob is at hardcoded offsets, so the track cannot move. Mouse layout MUST come out byte-identical; check a new control at 360, 390, 430 and 768 for overflow.

**`ColorPicker` is a 5 × 2 grid, not a wrap.** `PALETTE` is one walk round the hue wheel (aqua 174° through mint 150°), so ten in two rows of five is that walk read the way text is read, with the wheel closing where row two ends and row one begins. The two swatches that are _not_ a colour — inherit-the-calendar, any-colour — share a column of their own beside it behind one divider, because the column is one or two cells by turns and the block of ten must never change shape. A wrap divided eleven or twelve cells by whatever the column happened to be and landed on six and five. On `pointer-coarse` that column takes `w-full` and drops onto its own line with the divider hidden: 34px cells leave no room beside a five-wide block, and the line break is the separation the divider was drawing.

**State sync — hard convention.** `react-hooks/set-state-in-effect` active: an effect copying props into state is rejected. When new props must reset local state, use the React render-phase adjustment pattern (three existing sites: `Sidebar.tsx`, `EventEditor.tsx`, `CommandPalette.tsx`):

```tsx
const [seeded, setSeeded] = useState(day);
if (seeded !== day) {
  setSeeded(day);
  setDisplayMonth(new Date(day.getFullYear(), day.getMonth(), 1));
}
```

**Effects for external systems only** — `window` listeners, `ResizeObserver`, timers.

**Hotkeys** — `useHotkeys({ "mod+k": fn }, enabled?)`. Combo format: optional `mod+` (⌘ or Ctrl), optional `shift+`, then lowercased `e.key` (`k`, `escape`, `arrowleft`, `t`). `shift+` is part of the combo whenever Shift is held, printable keys included — without it `⇧⌘Z` and `⌘Z` are one string and redo becomes undo. Handlers skipped while typing in an input unless the combo carries `mod` or is `Escape`. `enabled` = how a modal switches the shell off (see gotchas).

**Modals** — `const dialog = useFocusTrap<HTMLDivElement>(open)` on the `role="dialog"` element. Three dialogs, one hook, no `<Modal>` wrapper: palette = combobox, editor = form, settings = sheet; they share this behaviour and nothing else.

**TypeScript** — `strict`, no `any`. Prefix intentionally unused bindings with `_`.

**Comments** explain _why_, never _what_. Most non-obvious decisions here already carry one; read before changing a line.

## Gotchas

### Faces, dial, week strip

- **`dayKey()` deliberately local-time.** `toISOString()` shifts the day west of UTC, exactly where a day-keyed store breaks. Never swap it in.
- **`Face.tsx` draws a day; `Dial.tsx` makes one editable — split by _question_, not size.** "What does this day look like" (geometry, rings, arcs, labels, band-replaces-ramp) → `Face`; "what did that gesture mean" → `Dial`. `Face` takes `svgRef` + pointer handlers rather than owning them: capture belongs to whoever reads coordinates. Every ring outside the arcs is opt-in, **off by default**; a `Face` with no `onGrab`/`onHover` renders no hit strokes at all = a read-only face. A new dial switch goes in `Face`'s props only if it changes what is _drawn_.
- **Every id inside the face comes from `useSvgId`** — `url(#…)` and `<textPath href>` resolve to the _first_ matching id in the document, so a hardcoded gradient id is correct only while one face is on screen and silently wrong with more. Glow, now-hand gradient, both band masks, every arc label mint their own; anything new needing a `#` reference does too.
- **Week strip read-only**, which keeps `<Face>` honest: seven faces of drag targets = seven chances to edit the wrong day, and the dial is one keystroke away. `WeekView` passes no `onGrab` ⇒ no hit strokes ⇒ 7 × 0 pointer paths instead of 7 × 19. `onHover`/`onFocus` only name the day for the shared readout. A face is a real `<button>`: seven tab stops is a usable order ⇒ no `sr-only` listbox (year ring 365 and life grid 30,000 need one; same argument as the life grid's three milestone buttons).
- **Strip's elapsed ramp on today alone; its rim on every face.** A past day's ramp is a complete bright ring answering "all of it" — a question nobody asked — and shouts down neighbouring arcs ⇒ `elapsed` and `hand` are both `d.today`. The other six faces need something to place arcs against, hence `Face`'s `track`: one circle at `DIAL.TRACK`, at the ramp's own floor, so on today the ramp reads as that rim lighting up. It is the one stroke drawn **translucent rather than opaque** — `TRACK_WIDTH` = three units, two fifths of a pixel at strip size, so the rim exists only as the antialiased fraction a browser rounds it into, and an opaque grey has no fraction to give. Nothing overlaps it, so no alpha compounds.
- **Day ⇄ week scales _and translates_; no `transform-origin`.** The panel already carries one (the life dot) and the dial must land on its face whatever that origin is. Under `scale(s)` about origin `o`, point `c` lands at `o + (c - o) * s`, so putting the panel's centre on face centre `f` needs `t = f - o - (c - o) * s`. `App.face` solves it once; `weekZoomScale` supplies `s`, tested against what matters: the dial's drawn diameter equals `layout.size`. One eased tween, not `ZOOM_STEPS`' geometric ladder — a ~4× zoom, not two orders of magnitude; a ladder over that distance reads as a stutter.
- **`flow.current` is reassigned wholesale ⇒ `face` MUST be carried across it.** `go()` and the popstate handler each build a new `ViewFlow`; a field written into the old one by an effect is dropped on the next view change — hence `faceFrame`, its own ref both writers copy forward. Adding a field to `ViewFlow` means adding it in three places: initial `useRef`, `go`, popstate.
- **⌘W is not available to any web page** (Chrome, Safari, Firefox): it closes the tab and the keydown is never delivered, unlike ⌘D / ⌘Y / ⌘L / ⌘P, which are merely menu equivalents this app already overrides. The week is **⌘E**, not a mnemonic and need not be: the `Segmented` control prints the chip, which is how every view key here is actually found.
- **Strip's readout lives outside the scroll container.** Inside one it centres on the content, wider than the window the moment seven faces do not fit, and the sentence walks off the side. Same reason the selected face is `scrollIntoView`d on arrival rather than left wherever Monday put it, and not smoothly.
- **The strip's three parts are one group, centred together.** Seven circles in a row are about a seventh of the width tall, so a landscape window leaves a great deal of black under them, and a readout pinned to the panel's foot is a caption for the window, not the strip's readout. `weekLayout` returns `groupTop`/`groupHeight` covering captions + faces + readout; leftover height stays outside the group.
- **`angleAt` and `minutesAtPoint` are exact inverses** and MUST stay so. Both take `Clock`, differ only by `origin()` — the minute at top (720 for `12h`, 0 for `24h`).
- **`arcPath` draws a full turn as two half-arcs**, because a single elliptical arc whose endpoints coincide renders nothing. Removing the branch makes a whole-day arc vanish.
- **A gradient built from overlapping strokes MUST be opaque.** Elapsed ring = chain of arcs; translucent ones compound alpha at overlaps, every join a bright bead, trail reads as a row of tick marks. On true black, opaque grey = translucent white, so `Face.tsx` ramps _colour_ (`grey(level)`), butt caps between segments, rounds only the two ends of the whole run.
- **Now-hand stops at `DIAL.HAND_INNER` (205).** A hand through centre crosses readout and agenda — ink spent on a time the readout already prints. It is a spoke: pip on the track at the exact minute, fading out along a `userSpaceOnUse` gradient before the centre panel. If the panel grows, `HAND_INNER` MUST clear its furthest corner — with the totals line on, the lowest thing sits ~135 units below centre and 113 out, so corner = 176 and 29 units are in hand.
- **The strip is read-only about events and _writable_ about days — one gesture, and it is the ring's.** Press, drag across faces, release: a press that never left its face is still a click and goes to that day; anything wider is a run of whole days handed to the same `onCreateSpan` the year ring and the life grid hand over, so the editor cannot tell which face drew the draft. It costs no drag targets and no arc grips, which is what keeps "read-only" true in the sense that mattered: seven faces of grips are seven chances to edit the wrong day. While a run is live the per-face hover is suppressed and the shared readout prints `formatDayRange` plus the count — a card naming one end of a run is a second answer to a question that has one. Escape abandons it, from the strip's own registration, exactly as `Dial` does. The face under the pointer is resolved from `weekFaceCentre`, never the DOM: seven comparisons against numbers the view already has, and a hit test cannot disagree with the drawing. The pointer path is `pointerup`, so the faces' `onClick` takes `e.detail !== 0` to keep the keyboard's own activation working.

### Centre panel / readout

- **Centre = one display, four moods, ordered.** `CenterPanel.tsx` resolves `span` first (range being dragged, else arc under pointer), then today's time, then date. Drag and hover print the _same_ thing — same question — so they share a branch rather than each growing one. Size change = CSS `font-size` transition, 140 ms on `var(--ease)`, matched to the arc's stroke-width transition: arc thickening and clock shrinking into its span is one movement; splitting the two curves makes it read as two events.
- **Headline row = first _timed_, non-past occurrence, only on today.** An all-day event is context, never the next thing, never `running` (`Now … ends in 10h 4m` = countdown to midnight dressed as an appointment). Headline drops start time (the ring is where start time lives) and spends width on name and wait; `untilText` rounds _down_, because a countdown overstating time you have is worse than none. Under `IMMINENT_MS` the dot takes a ring, not a pulse — pulse already means "running", one signal cannot mean two things.
- **Hovered occurrence added back to the card even when ended.** Today's card filters `occ.end > now`; without the exception, pointing at a morning arc printed a span with no name. Costs one row of shift while the pointer is on a past arc — the honest position for it.
- **`totals` measured against two different windows on purpose.** Booked = whole revolution (a six o'clock run is time spent); free = only `WAKING`, because "nineteen hours free" is not an offer. They do not sum to anything, nobody adds them. `WAKING` lives in `events.ts` beside `freeGaps`; the palette's slot search and this line MUST mean the same thing by the word.
- **`totalsAt` places the line against the _stage_, not the dial.** `center` = the only one rendered inside the panel's column, under the card; the other eight = `flex` layer at `inset-0` with `p-4`, so the corner is the _window's_ corner — black a circle in a landscape window never reaches. `CORNERS` in `CenterPanel.tsx` maps them and deliberately has no `center` key: that position is not the corner of anything.
- **A task's readout is one instant, not a span.** `peekedTask` splits out of `peeked`, so pointing at one prints `01:15 DUE` rather than `01:15 – 01:15 · 0m`, which is three ways of saying nothing. It still shrinks the clock (`aside`, not `span`): the readout is answering about something other than now, and that is what the size change means.
- **No `backdrop-filter` on an element also carrying `.fade-y`** — Chromium paints blur over a box far larger than the element, appearing as a grey rectangle mid-dial (see comment in `CenterPanel.tsx`).

### Drag gestures

- **Ring drag accumulates sweep; never measures from grab.** `Draw` holds `{ from, at, sweep }`; `onRingMove` sums `wrapDelta` per pointer event, exactly as the arc's drag does. Measuring from grab caps a new event at twelve hours and turns the range inside out past that, because `wrapDelta` takes the short way. Sweep clamped to `[-from, 1440 - from]` — clamping _sweep_, not the resulting instant, makes the range stop dead at midnight and follow the pointer back the moment it turns, instead of unwinding overshoot first (same reason as `clampDelta`).
- **Arc drag accumulates `wrapDelta` per pointer event; never measures from grab.** Two ring positions do not say which way round the circle the pointer went, so a delta measured from grab flips sign the moment the drag passes twelve hours. Summing short hops lets a drag cross midnight as many times as it likes.
- **Minimum duration clamped on `delta`, not on the resulting instant** (`clampDelta` in `Dial.tsx`). Clamping the end banks overshoot: the arc then lags by however far the pointer ran past the limit before it starts following back. Clamping delta stops dead and releases instantly — and since sound fires only when delta changes, a clamped arc goes quiet, which is feedback saying "this is as short as it gets".
- **A press on an arc that never changed delta is a click.** `onArcUp` opens the editor when `delta === 0` — also the whole implementation of read-only arcs: a subscription's occurrence gets `grip: "none"`, `clampDelta` pins it to zero, the press falls through to opening. No separate `onClick`.
- **`Escape` abandons a gesture in flight**, from `useHotkeys` inside `Dial`, not the shell's: `setDraw(null)`, `setAdjust(null)`. A drag is the one thing here you can start by accident, and before this the only way out was to let go, which committed it. Pointer stays captured on purpose — both move and up handlers bail on a missing gesture, so the release that follows does nothing, no cue because nothing happened.
- **Full revolution = all-day event; `draftEvent` decides.** Any span of `MINUTES_PER_DAY` or more becomes `allDay` with instants snapped to the day's two midnights, so ⌘N, palette and ring gesture all agree. `CenterPanel` prints `All day` in the readout while such a drag is live, because the gesture should say what it is about to make; the arc vanishes on release, since `EventArc` draws nothing for an all-day event.
- **More than one revolution = that many all-day days, same function.** `Math.round(span / MINUTES_PER_DAY)`, so the dial's exactly-1440 sweep (its own clamp) stays one day and the year ring's `n × 1440` becomes `n`. All-day `end` = `addDays(startOfDay(day), days)`, **not** `base + n × 1440 minutes`: a day is not always 1440 minutes long, so a span across a spring-forward landed `end` at 23:00 on the last evening instead of the midnight after it — and `end` is exclusive, so the last day of a trip fell off the dial. Latent at n=1 before the year ring existed; the fix is the same either way.
- **A whole turn is drawn closed — a second rule from the same fact.** `capInset` shortens an arc by half a stroke at each end so painted length = duration — but once the ends meet the inset is a notch at midnight, and a circle with a notch reads as a rendering fault. `GhostArc` returns `<circle>` for a full-day range; `EventArc` drops the inset at `to - from >= 360` (a timed event running through the whole day = any multi-day event's middle).
- **⌘⌫ deletes the arc under the pointer; the key lives in `Dial.tsx`** — the dial owns the hover, so it owns the press (same argument as Escape's gesture-abandon). What a delete _means_ stays the shell's: `onDelete(occ)` goes up, a one-off goes straight through `store.remove`, a repeating one gets the same `ScopeDialog` a drag gets, in danger colour. Off while `covered` (the shell's `busy`), because the editor has its own ⌘⌫ and two handlers on one press delete two different events; off mid-gesture, because the drag in flight is about to write to that same arc; and it never fires on a subscription's occurrence. It **always toasts** — the editor's Delete is two deliberate presses inside a modal, this one is a single keystroke, and a destructive key with no receipt is a key nobody presses twice.
- **⌘ held at the grab duplicates instead of moving; the modifier is read once.** `Adjust.copy` is fixed at `onArcDown`: a ⌘ let go halfway through would turn a duplicate into a move of the thing being copied, the one outcome nothing undoes in a single step. Only for `grip === "whole"` — a duplicate is a move of a copy, so an end grip is a resize whatever is held down, and `grip: "none"` means a subscription's arc is never copied either. While copying, `onArcMove` **withholds `onPreview`**: the original has to stay exactly where it is, and the thing following the pointer is `copying`, the draft's own `FaceGhost` channel in the event's own colour. Nothing is written until the release, and the release asks **no `EditScope` question** — the three scopes say which occurrences an edit reaches, and a duplicate reaches none of them.
- **A duplicate carries the whole event, rule and all; `duplicateOf` (`store.ts`) is the one place that says what "the whole event" means.** The deltas apply to the event's own instants, the reading a plain drag already has, so ⌘-dragging one occurrence of a weekly standup gives back a weekly standup an hour later. Three fields deliberately do NOT travel: `seriesId`/`seriesKey` name a relationship to another event and two events cannot claim one occurrence, and `doneKeys` are ticks against work done once. Three MUST travel **with the shift** rather than beside it: `until` bounds a start, and `exdates`/`rdates` name instants — a series moved an hour later and handed its old keys fires on every day the original skipped. A day-form key is re-emitted as a day, which carries a whole-day exclusion across a drag that crossed midnight.
- **⌘P duplicates through the editor; the asymmetry is the point.** A gesture named a time, so the drag writes and toasts; the palette named none, so an unmodified copy would land exactly under its original and the toast would be the only evidence of it. `actions.duplicateEvent` seeds `setEditor({ id: null, draft })` and commits nothing until Save, so Escape leaves no orphan. It goes to the original's own day first: an editor over a face that cannot show what is being edited is a form.
- **`onRingMove` and `onArcMove` bail when the snapped minute has not changed.** Makes clicks countable (one per fifteen-minute step, not one per pointer event) and drops the re-render `pointermove` would otherwise cause. `cue()` has its own 22 ms floor for the same reason, since a fast flick crosses steps faster than the ear separates them.
- **Lane packing is face-independent.** `dayAgenda` takes no `Clock`: both faces put one day on one revolution, so two events collide on screen exactly when they collide in time.

### Arc labels

- **Arc labels live _inside_ the stroke — geometry, not taste.** `LANE_STEP - ARC_WIDTH` = 13 units of black between two lanes, and hour numerals come down to 333 just outside the first, so a label _beside_ an arc works on the outermost lane and nowhere else. Inside the 14-unit stroke it is 11px of mono with 3.1 units of arc either side, identically on every lane, and costs no radius — the "do not add a ring" rule again. It is also `inkOn(color)`, black on the event's own pastel at ~10:1, the strongest pairing this face has; grey on black beside the arc would be the weakest. **Except on a free arc, where there is no pastel to be black on** — see "Busy and free".
- **The label's budget is glyphs measured against the _paint_, never minutes and never the centre line.** `arcLabel` takes the arc's painted ends (the span less any seam a neighbour claimed), because the round caps put half a stroke back past `head`/`tail`, and a label handed the `capInset`-shortened span forfeits 14 units on every arc — every half-hour event on the face going anonymous (it did). Mono ⇒ width is arithmetic: no `getComputedTextLength`, so no layout read per arc per frame of a drag. Where the gate lands in minutes is a _consequence_ (a word from about 45 minutes, a stub from about 30 out at the rim, nothing on the inner lanes) ⇒ a duration threshold would label an event at the rim and crop the same event two lanes in.
- **A glyph takes its up-vector from the path's direction, so the bottom half is drawn backwards.** `arcPath` grew a `back` flag: the same arc traced anticlockwise from `to` to `from`, invisible on a stroke and the whole difference between a readable label and an upside-down one. `arcLabel` reverses whenever the arc's midpoint is between 90° and 270°; the flip has to land somewhere and at three and nine o'clock the text is vertical either way. Derived from the _drawn_ angle, so both faces get it for free.
- **The label keeps full alpha on a dimmed arc.** Ink here is the _absence_ of light, so dimming it alongside the body takes both towards the black behind them and the name disappears at ~1.5:1. Left alone it softens from about 10:1 to 4.8:1 as the arc recedes, which is the hierarchy the dimming was asking for. In `hover` mode it is mounted at `opacity: 0` rather than mounted on hover: it arrives in the same beat the stroke grows by 3, and text popping in on a growing arc reads as a wobble.
- **A mark on an arc costs two glyphs of the label's budget, and never the name.** `arcLabel` takes the mark, prices it at `ARC_MARK_GLYPHS`, and rides it along **only** when what is left still clears `ARC_LABEL_MIN` on its own — a tight arc drops the glyph and keeps the word, because a symbol shared with everything on one calendar is worth less than the last two characters of a name. The pair is centred as a unit: `startOffset` pushes the text out by half the mark's slot, the glyph sits at the _start_ of that slot so all the slack lands between it and the first letter, and both flip through the bottom half with the path. `MarkGlyph` is the SVG-native renderer for exactly this; `CalendarMark` answers a `<span>` for an emoji and a dot for nothing, and neither is legal inside an `<svg>` or wanted on an arc that already carries its colour.

### Busy and free

- **An event is busy or free, and `CalEvent.free` says which — explicitly, never inferred.** Same argument as `task`: nothing about a span says how seriously it is meant, so reading it off a title, a calendar or a zero-width end would be typing data by coincidence. Busy is the default _and_ the absent value, which is what keeps a field arriving in an old blob harmless. It is `TRANSP` on the wire (`TRANSPARENT` = free, `OPAQUE` and an absent property = busy) and it is named for the word the editor prints rather than for the property, because the property is a spelling and the idea is what the UI has to say out loud. The field is the same checklist `task` was: `hydrateEvents`' shape fast-path (a field left out of that question is a field a blob never gains), `readEvent`, `duplicateOf`, `importIcs`, `feeds.ts`, and `mcp/domain.ts`'s patch path — the last one the sharpest, since an assistant editing a free event's title would otherwise have handed back a rebooked one.
- **Hollow, because the other two encodings were already taken.** Alpha is spoken for: a past arc is drawn at `0.42`, so "free" meaning "fainter" would make a past meeting and a future placeholder the same picture. A dashed stroke reads as tentative — a third meaning nobody asked for, on a face where a dash would also have to survive being a fifth of its size on the strip. `hollowPath` (`dial.ts`) traces the outline half a hairline **inside** the filled arc's own silhouette, so stroking it at that weight paints exactly the same footprint: same radius, same lane, ends landing where the round caps do, and `capInset`'s promise — painted length is duration — untouched. A caller hands it the same `from`/`to` it hands `arcPath`.
- **`ARC_HAIRLINE` is `ARC_WIDTH / 8`, derived and not chosen.** The same `<Face>` is drawn seven to a row on the week strip at about a fifth of dial scale, so a weight picked against the dial's own pixels means something else there. An eighth leaves ten units of black between the two edges — wider than the `SEAM` two neighbouring arcs keep — so the hollow reads as a hole rather than as a thick line.
- **One construction, three shapes, each for a rule that already existed.** A full turn is two concentric circles, closed and uncapped, because an inset once the ends meet is a notch at midnight (`arcPath`'s own rule). A degenerate sweep is the two caps alone, which is a ring — the hollow of the dot a filled path collapses to. Everything between is the racetrack: out along the far edge, round the cap, back along the near one.
- **Hover changes weight, not width.** A filled arc grows three units on a CSS transition; an outline's width lives in the path data and a path swap cannot tween, so a hovered free arc doubles the hairline instead. The footprint never moves, and the feedback still lands in the same beat as the label's fade.
- **The label had to change ink, and this is the part that would otherwise have shipped broken.** `arcLabel` draws the name inside the stroke in `inkOn(color)` — black on the pastel, the strongest pairing the face has — but inside an outline the arc is mostly the black behind it, so that black is not dim, it is _absent_. A free arc's label and its mark glyph take the event's **own colour** (`labelInk` in `Face.tsx`): every `PALETTE` entry is a high-value pastel reading on true black at the same order of contrast the black-on-pastel had, it is the colour of the line it sits in so the pair reads as one object, and a colour dark enough to fail here fails the outline in the same breath — label and arc cannot disagree about whether the event is legible. The full-alpha rule on a dimmed past arc is unchanged.
- **A task is never hollow, and that is a decision.** It books nothing already, so there is nothing for "free" to withhold — and its pip's filled/hollow pair is spoken for: filled is open, hollow is done. One shape cannot carry two meanings on one face, which is the same rule that keeps a pulse from meaning both "running" and "imminent". The editor does not offer the switch on a task at all. An **all-day event still draws no arc**, free or busy, exactly as before.
- **The point of the feature is the arithmetic, not the picture.** `freeGaps` books no block for a free occurrence, so `dayLoad`'s booked total stops counting a birthday as an hour spent and the palette's slot search follows for nothing, because it already reads `freeGaps`. What counts as booked changed; the window it is counted over did not — booked against the whole revolution, free against the waking window, still not summing to anything.
- **Measured on the strip, and the answer is why there is only one encoding.** The two edges do not merge at any size the strip actually draws: at a typical desktop strip the hairline is 0.625 css px with 3.75 css px of black between the edges, and at `WEEK_MIN_FACE` — the smallest face `weekLayout` will draw — it is 0.252 css px with 1.515 between them, a faint hoop beside a solid lozenge, confirmed in a 1:1 screenshot rather than argued. Merging would need the gap under about one device pixel, which needs a face roughly a third of the strip's own floor. So no second encoding was added for small faces: one that degrades gracefully beats two that can disagree about what the same event is.

### Tasks

- **A task is an explicit `CalEvent.task`, never "`end === start`, therefore a task".** A degenerate span is an arithmetic coincidence, and typing data by one is how a five-minute event dragged to nothing silently becomes a to-do. The flag comes _with_ `end === start`, which makes the rest free: the dial's existing sub-cap dot-collapse already draws a pip at the right minute, `freeGaps` drops a zero-width block on its own, `dayLoad` sums nothing. Two things needed a line each — `occurrencesOn` measures day-overlap against `Math.max(duration, 1)`, or a task at exactly midnight is thrown away by an exclusive `end`; and `packLanes` returns a task untouched, so a pip neither buries nor is buried by the meeting it happens during. **Undated tasks are deliberately not modelled**: a list with no day on it is a different product wearing this one as a skin.
- **`doneKeys` = list of `instantKey`s, for the reason `exdates` is one.** A repeating task is ticked one occurrence at a time, and a boolean on the series would tick every Monday at once. Always the datetime form — the day-only form `exdates` also carries exists because EXDATE has two RFC value types, and nothing outside this app writes these. `Occurrence.done` resolved once in `occurrencesOn`, because `dayAgenda` is the one read path onto a day and a list lookup is not a renderer's job. **A tick asks no `EditScope` question**: per-occurrence is the only thing it could mean.
- **Filled while it stands, hollow once done — on every surface.** The pip on the rim and the tick target in the interior are the same two shapes, so the mark you press and the mark you see on the face are one mark. Opposite of the checkbox convention, deliberately: on this face ink is _light_, so an emptied pip reads as spent. In the list the strike through the name is the primary signal and the pip is only the control. **`CenterPanel`'s row is therefore a `div` with two buttons**, not one button — a control inside a control is not a thing HTML has.
- **A task's ICS = VEVENT with no DTEND, plus `X-CIRCAL-TASK`.** §3.6.1 requires DTEND strictly later than DTSTART, and the same section says a DATE-TIME DTSTART on its own ends when it starts ⇒ the spec-legal spelling of a zero-length event is to omit the property. `buildEvent` reads the flag _before_ computing `end`, because the hour-long fallback for a missing DTEND MUST stay for everybody else's VEVENTs (reading those as zero-length would collapse every unterminated meeting onto the rim). A VTODO was the other option and is worse: circal models the half of VTODO that has a day and a minute, and a consumer ignoring the `X-` lines still shows a task at the right time on the right day.
- **`readEvent` lets `end === start` through only for a task**: guard is `task ? end < start : end <= start`, not a blanket loosening. Everything else with no width is a corrupt record — it draws as an arc of the whole day or as nothing.

### Invitations: read, never answered

- **Reading an invitation and answering one are separate features, and only the first exists.** An emailed `.ics` carries who is asking and who is coming, and the import used to throw both away — so `ORGANIZER` and `ATTENDEE` are now read, stored, shown and written back out. Accepting or declining is a **message**, and this app has no account, no server and no outbound channel to send one with; it is not growing one for this, so the surface has no verb, no button, no control to add a guest, and nothing anywhere that looks like a reply. `AUDIT.md` drew that line before the feature existed (the reply half "needs a channel this product has refused; **reading** an invite and showing who is coming does not") and the code is that sentence.
- **Three fields, and the third is the one that keeps the other two honest.** `organizer`, `attendees` and `attendeeCount`: the count is separate because it is the one fact truncation destroys. The editor prints "and 40 others" from the number that _arrived_, never from the length of the list that fitted, so a cap can never quietly turn a thousand-person announcement into a list of thirty-two colleagues.
- **`PARTSTAT` collapses to four states, and everything unmodelled reads as "invited".** `PARTSTATS` is `needs-action` / `accepted` / `declined` / `tentative`; `DELEGATED`, an unknown value and an absent property all read as `needs-action` — the RFC's own default and the only one of the four that claims nothing about intent. Reading a delegation as `Declined` asserts a refusal nobody made and as `Accepted` asserts attendance; and the delegate arrives as its own `ATTENDEE` line with its own status, so that somebody _is_ coming is already on the list and only the relationship between the two is unsayable here. The label is **"Invited"** rather than "No reply" for the same reason: "invited" is true of a delegation and of a silent guest alike, where "has not replied" is a claim about the person and false for the first. `PARTSTAT_LABELS` lives beside the vocabulary, not in the editor — `REPEAT_LABELS`' rule, since the word and the value are one decision.
- **`ROLE` and `RSVP` are read by nothing, deliberately.** Required-versus-optional changes nothing this surface says and nothing the arithmetic does; the organiser is the only person here with a different job and it has its own field. `RSVP=TRUE` is the sender asking for an answer, and printing that request would put a demand on screen beside no way to meet it — precisely the actionable look the whole feature refuses.
- **`METHOD` is neither read nor written, and that is the sharpest decision in the feature.** It separates `REQUEST` from `PUBLISH`, `REPLY` and `CANCEL`, and every one of those readings only pays off in the half that was refused: `REQUEST` wants an Accept button, `REPLY` would patch a status onto an event already on the dial from a file that arrived by mail, `CANCEL` would delete somebody else's event on their say-so. On the way out it is worse — `METHOD:REQUEST` is this app claiming to _organise_ a meeting it only read, which is how a consumer is told to start posting replies to the real organiser. Pinned by a test: `REQUEST`, `REPLY` and `CANCEL` all read as one kept event with its people on it, and `toIcs` never emits the property.
- **Every cap names what it defends against, and one of them is derived.** `readGuests` in `events.ts` owns all of them for its three readers (`ics.ts`, `backup.readEvent`, `store.hydrateEvents`) — the `readRecurrence` shape again, because three copies of these numbers would be three opinions about when a calendar is too big to keep. `ATTENDEE_MAX` = **32**, above every guest list somebody actually reads down and below where a list stops being names and starts being a distribution list; the threat is real and specific, a mailing-list invitation of thousands of lines inside the one ~5MB origin quota that `FEED_BUDGET` already carves 2M characters out of — and `trimFeed` cannot help, because it bounds a subscription in total by dropping whole events and cannot see **one** event that is itself megabytes of addresses. `GUEST_NAME_MAX` = 64, against a pasted paragraph in a `CN`. `GUEST_ADDRESS_MAX` = **254**, which is RFC 5321 §4.5.3.1.3's own forward-path ceiling and therefore derived rather than picked: nothing longer can be a mailbox, so nothing longer is an address being truncated. Duplicates collapse on the lowercased address (a merged reply legitimately restates a line, and one person twice is a list lying about its size), and `attendeeCount` is clamped to never understate the list it labels — the count exists to say what the cap dropped, so it must not be able to print "and −3 others".
- **`duplicateOf` drops the guests.** A duplicate is your own event, not the invitation somebody sent you — the same argument that already keeps `seriesId`/`seriesKey` and `doneKeys` from travelling. Nothing in this app mints a guest list, which is why the row is absent entirely from everything the user wrote.
- **The surface is display only, and every choice in it is about not looking actionable.** The `Guests` row renders `null` unless there is something to show, so it never appears as an empty field inviting input. The organiser sits _outside_ the scrolling list because it is the one name answering "who is asking" and must not be the row that scrolls away; it keeps full `ink` where guests are `ink-2`, greyscale both, since colour on this face belongs to events. A name or the address, never both — 320px has room for one and the name is the answer to "who" — with the address on the row's `title`, since it is the only copy of it on screen. Statuses are `.label` tags, three words of vocabulary at a label's weight rather than a sentence. And the list takes `.fade-y` only past `GUEST_ROWS`, per the standing rule that a permanent fade on a list that fits reads as a rendering fault.

### One event in a link

- **The payload rides in the URL _fragment_, and that is this project's own constraint rather than a preference.** A fragment is never sent to a server; a query string is sent on every click and lands in a log. circal has exactly one route and no server-side state, so an event in a query string would quietly break that promise on behalf of whoever pasted the link — the sender would be the one leaking, and they would never know. `shareFragment` and `shareToken` are the only two places the fragment's spelling lives, so nothing downstream can decide to put it elsewhere. There is nothing stored, nothing to expire and nothing to take down, which is the whole reason this exists as a link rather than as a service.
- **`.ics` is still the answer for every other calendar; this is the circal-to-circal path.** A rule, a mark and a colour survive it, which they cannot survive an export to a product that has no vocabulary for the last two. A link that another app cannot read is not a defect here — it is the reason the format is allowed to be this small.
- **The link is not private, and the app says so at the moment it is minted.** This is an encoding, not encryption: anyone holding the link holds the event. That is exactly what makes the feature work and fatal if a user assumes otherwise, so the copy notice is the confirmation and the disclosure in one line rather than a caveat in a comment nobody reading a chat message will see.
- **The record is positional, and what compactness cost is stated because somebody will want to "clean it up".** Field names are longer than most of the values they would label, so: positional fields, base36 numbers, epoch **seconds** (nothing here writes a sub-minute instant — the dial snaps to fifteen, `parseClock` to one), a duration as a delta off the start rather than a second absolute instant, trailing empties dropped ⇒ an ordinary timed event is four fields and **34 characters against 512** for JSON-plus-base64, a ratio pinned by a test so a "tidier" format has to beat a number. The price: the record is unreadable by eye, and a field may only ever be **appended, never reordered** — which is what `SHARE_VERSION` leading the token is for.
- **base64url's +33% buys a guarantee instead of a guess.** The output alphabet is `A-Za-z0-9-_`, so no character in a title can need percent-encoding, break out of the payload, or be eaten by whatever linkifies the message it is pasted into. Hand-escaping Unicode into a URL-safe subset was the alternative and is a percent-encoder with a different sigil — three bytes per accented character and a table to get wrong. `CompressionStream` was the other and is asynchronous, which a synchronous format called from a click handler cannot use.
- **The four check digits exist because driving the thing found the bug, not because a spec asked for them.** A link cut short on a base64 boundary — a chat client breaking a line, half a link pasted — otherwise decodes into a _plausible_ event with its last field silently altered: the one hostile case shape cannot catch, since the bytes are legal and the instants are fine. `shareCheck` is four base36 digits of the repo's existing `fnv1a`, 1.7 million values for five characters of link, and `fnv1a` is already this codebase's answer to "is this the same content". A refusal is the correct outcome; a wrong event that looks right is not.
- **What travels is decided field by field, and every absence has its own reason.** Guests do not: a link goes into group chats, circal cannot send an invitation, so a guest list here could only be a record of somebody else's. The **id** does not, because one id naming two events in two calendars is exactly what a later import would merge. `seriesId`/`seriesKey` name a relationship to an event that is not in the link. `doneKeys` are ticks against work the sender did, and a shared task arriving pre-ticked is a to-do list that lies. `remindLead` does not, because absent it arrives as `REMIND_INHERIT`, which says precisely "follow this reader's own setting". And the calendar is the receiver's to choose. This is `duplicateOf`'s rule arriving a third time, and it has earned a general form: **a copy carries what the thing is, never what its relationships or somebody else's answers were.**
- **An all-day event travels as a day key and a count, never as instants.** An epoch second minted in Berlin is mid-afternoon of the previous day in Los Angeles, so a birthday would arrive on the 7th; `allDayInstants` rebuilds this reader's own two midnights from `20260308` plus a number of days, `addDays` rather than `n × 1440` minutes for the reason every other multi-day span here uses it.
- **Receiving opens the editor rather than writing anything.** A link that silently added an event to your calendar would be the one thing in this app that changes your data because somebody else sent you a message. It is ⌘P-duplicate's own path — `setEditor({ id: null, draft })` — seeded **during the first render** rather than from an effect, so the right day is never rendered wrong and then corrected, and because an effect copying into state is the convention this repo rejects outright. It reads `store.snapshot()` rather than props for the default calendar, since the store hydrates at its first subscribe one commit later — the travel notice's own lesson, repeating. The consumed fragment is cleared by `writeLocation`'s construction, so a reload re-offers nothing.
- **Share sits in the editor's footer, and deliberately nowhere else.** Not the palette, whose per-event second verb is already Duplicate — one modifier meaning two things on different rows is the bug `Row.alt` exists to avoid. Not a dial keystroke: a key that silently copies your calendar to the clipboard is not a key this app should have. It **is** present on a subscription's event, outside the disabled fieldset, because sharing is copying rather than editing.

### Reminders

- **Reminders never catch up; the window is one minute wide because of it.** `dueReminders` fires only what comes due in `[target, target + 60_000)` — a notification for a meeting that started an hour ago (tab asleep, lid shut) is worse than none, so the test is "due this minute", not "not yet fired". It also **floors `now` to its minute**: `useNow` fires a few ms _after_ `:00`, and an unfloored window starting at `10:17:00.09` misses every event sitting exactly on `10:17:00.000`, which is all of them. All-day occurrences never fire (no minute to count down to), tasks do (a to-do with a time is the thing most worth a nudge), a ticked one does not. Per-event leads changed none of that — only _which_ lead each occurrence is measured against.
- **`Notification.requestPermission()` called from the settings switch and nowhere else.** Chrome and Safari honour it only inside a user gesture, and `useReminders` runs off a timer ⇒ the hook checks `permission === "granted"` and otherwise does nothing at all. The switch goes _on_ only if the answer came back granted, or the panel would be showing a promise the browser will not keep. The reminder's `tag` is the occurrence key so the platform collapses a duplicate; `fired` is the in-memory belt for the same reason, since React invokes an effect twice in development.
- **`CalEvent.remindLead` overrides `settings.remindLead` in exactly the sense `CalEvent.color` overrides its calendar's.** The default names nothing and follows the setting, so moving the setting still moves every event that never asked for its own — which is what makes a global preference worth having beside a per-event field. `leadOf(event, fallback)` is the only reader of that precedence, the way `colorOf` is the only reader of colour's, and it returns `null` for "nothing fires", so a caller cannot accidentally treat silence as zero.
- **Three states in one number, and the encoding is the argument.** A lead is minutes _before_ a start and can only be counted one way, which leaves the entire negative half-line free to mean something other than a number of minutes: `REMIND_INHERIT` is `-1`, `REMIND_SILENT` is `-2`. That is what keeps `0` meaning what it has always meant here — "tell me as it starts" — and a scheme where `0` doubled as off or as absent would make the one lead time this app was built around unsayable. `REMIND_LEAD_MAX` (four weeks) bounds nothing the editor can write and everything an imported `VALARM` or a hand-edited backup can, so a `TRIGGER` of `-P400D` cannot put `dueReminders` on a day four hundred days out every minute.
- **Silence is a state, not a convenience.** Per-event control exists so a recurring thing you already know about can be told to stop nudging you; without a third state the only way to silence one event is to switch reminders off for every event, which is the trade the whole field exists to avoid. Silent is skipped whatever the setting says.
- **One day per _distinct lead_, not one per event.** A lead is now a property of the event, so a 60-minute lead legitimately looks into tomorrow while a 0-minute one looks at today; an occurrence can only come due `lead` minutes before it starts, so the day it starts on is the only day worth asking about. Collecting the distinct leads keeps a calendar of two hundred meetings on the setting's own lead at one `occurrencesOn` query, which is what it cost before the field existed.
- **The Remind row stays visible when reminders are switched off, and the row itself says so.** The inherited option reads `Follow settings · off` rather than a duration, because printing "10 minutes" under a preference that fires nothing is the panel promising something the app will not do. That is where the fact belongs: a `.caption` paragraph used to repeat it under the control, which said what one option already said and made three lines of prose the loudest thing in a 335px column. Hiding the row instead would make an imported event's own alarm invisible — this row is the only view of that data anywhere — and a field that disappears with a preference is a field a user cannot discover they have.
- **The row _is_ hidden on an all-day event, and the value is left alone.** `dueReminders` never fires one, so a lead there is a control with no effect, and a control with no effect is worse than an absence. Whatever an import put on the draft stays on it rather than being reset: it is the sender's statement and it travels back out on the next export.
- **A silent event exports no `VALARM`, and neither does an inheriting one.** The absence of an alarm is the only thing iCalendar can say, and this app reads that absence back as inherit — so materialising the current setting into the file would turn a preference into data, returning as an override nobody set. `ownLead` is the exporter's question (the lead an event names _for itself_, else `null`) and it is deliberately not `leadOf`: one asks what the event says, the other what the app will do about it.
- **The lead vocabulary lives in `events.ts`, the firing in `remind.ts` — the split marks already use.** `events.ts` owns what a `CalEvent` field legally is (`REMIND_INHERIT`, `REMIND_SILENT`, `REMIND_LEAD_MAX`, `ownLead`, `readRemindLead`, beside `ICON_MAX` and `isIconName`); `remind.ts` owns what a lead does (`REMIND_LEADS`, `remindLabel`, `leadOf`, `dueReminders`). `leadOf` stays up there for a reason worth keeping: its fallback is a **setting**, and what a field legally is must be answerable without one. `readRemindLead` is the one validator with four readers — `backup.readEvent`, `store.hydrateEvents`, `ics.ts`'s `VALARM` reader and the editor's own `Select` — the same one-validator-many-readers shape `readRecurrence` has, and the `.ics` reader passing its minutes through it rather than re-spelling the whole-minutes and cap checks is what makes it a fourth reader instead of a second opinion.
- **Snooze stays entirely in the shell; the page is never told.** `Bridge.snooze` (`mac/main.swift`) re-posts the identical `UNMutableNotificationContent` under the same identifier with a ten-minute `UNTimeIntervalNotificationTrigger` — the same banner, shown again, nothing more. The rule two lines up is exactly what routing this through the page would break: a snooze is the user asking for the banner back, not the app deciding a meeting is newly due, and the moment it goes through `remind.ts` the two become indistinguishable. A future reader "fixing" this by involving the page has misread it. The `osascript` fallback gets neither the action nor a tag to snooze with, and correctly does not try.

### Store, feeds, backup

- **`Settings` schema-versioned.** `SCHEMA` in `src/lib/store.ts` bumped when a stored value changes _meaning_ rather than shape (went to `2` when `clock: "24h"` stopped meaning noon-at-top face). Stale schema resets settings to defaults, keeps events.
- **One validator, three readers.** `recur.ts` owns what a legal rule is — the RFC range tables and `readRecurrence`, unknown → `Recurrence`. `backup.readRecurrence` (untrusted JSON), `store.hydrateEvents` (fields a blob predates) and `ics.readRecurrence` (RRULE strings) have three different _jobs_ and share those rules; deciding for themselves they disagreed — backup clamped `interval` at 999 where ics had no ceiling and the store range-checked nothing. Two consequences worth keeping: **the exdate/rdate lists are read before the frequency**, because an RDATE-only series is real (`repeats()` says so) and a bare `NEVER` for `repeat: "never"` is how a `.json` round trip used to lose every date a producer named; and `hydrateEvents` keeps its identity fast path, so it asks about _shape_ and only hands the rule over when the shape is wrong.
- **Store hydration lazy, at first `subscribe`**, not module scope. `load()` and `write()` swallow `localStorage` errors on purpose (private mode / quota must not brick the app) — but both then call `notify(…, "error")`, because a silent failure is indistinguishable from success and that is how a day's events disappear. `load()`'s case is the sharper one: it starts the app **empty**, exactly what a first run looks like, so the notice is the only thing telling the two apart. `readFeeds` is the one catch that stays silent, and says why: a corrupt payload is a cache miss the next pull replaces.
- **Every action derives from `fresh()`, never from the module's `snapshot`.** `fresh()` re-reads the blob when another tab wrote since we last looked; deriving from the in-memory snapshot loses the other tab's events wholesale in the window before its `storage` event arrives.
- **Undo in-memory and session-scoped**, cleared on an inbound `storage` event _only when the base actually moved_: undoing onto a base another tab moved past would resurrect what it just deleted, but a background tab's **feed pull** writes the same key and used to cost the foreground tab all sixty steps — a loss the user cannot attribute to anything they did. `baseSignature()` is the comparison (events + calendars minus their `feed` + settings). `undo`/`redo` also carry today's `feeds` across rather than restoring the recorded ones, because a feed is a live mirror and never part of an undo step. `commit(next, false)` opts a change out of history — settings and feed pulls do.
- **A feed payload never shares the blob.** One `circal.feed.<id>` key each, budgeted: `FEED_BUDGET` (2M stored characters) split equally between the subscriptions, re-divided on every pull. Inside `circal.v1` a mirrored calendar is unbounded and competes with your own events for one ~5MB origin quota, so one fat subscription made every later save fail — quota is per origin, which is also why the cap is a shared total and not "1MB each" five times over. Over budget, `trimFeed` keeps recurring events first (a rule is bytes that describe years) then nearest today, and the calendar's meta line says `1,228/4,000 cached`; a refused `setItem` drops the key and says `Not cached — no room`. Both messages are under twenty characters, because that line is one `.label` wide and truncates. Migration out of a legacy inline `feeds` field runs in `hydrate()` — shared by `load()` and `fresh()`, because either can be first to see a blob — and rewrites the blob immediately, so it happens once. Deliberately **not** a `SCHEMA` bump: a bump resets settings, and where a payload is stored is not something a setting means.
- **`feedCache` is not an optimisation you can drop.** `fresh()` runs on every action and re-reads every feed key; without the id → `{ raw, events }` map, a single 300-event subscription re-parses on every nudge of an arc. It is also what makes `sameFeeds` able to tell a real change from a re-read, which stops `fresh()` handing React a new snapshot for nothing.
- **`seed()` only runs when no stored blob exists**, anchors on today's local midnight.
- **The backup nudge, and why a data-safety setting is the one that defaults on.** `localStorage` is the only copy, "Clear site data" erases it without asking, and the macOS app and every Chromium browser answer that with a live mirror — Safari and Firefox have no File System Access API and no way to hold a file handle at all, so noticing that no backup has been saved in a long time is the only answer those two can be given. Hence `settings.backupNudge` **on** where `remind` is off: a reminder is a convenience somebody opts into, a warning about losing everything is not, and a prompt defaulting to off is a prompt nobody ever meets. The interval comes from `BACKUP_INTERVALS` (7/14/30/60/90 days, **30** by default, a stray stored value pinned by `sane()` like every other enumerated setting), and `backupDue(lastBackup, intervalDays, now)` in `backup.ts` is pure and takes `now` as an argument, so the predicate says the same thing in every zone and pins in a test with no clock to stub.
- **Four decisions about that clock, each of them a way of not lying to the user.** Only the **`.json`** export advances it, and only when a file actually landed — `download` already reports that because the macOS save panel can be dismissed, and a cancel that quieted the nudge would be a warning switched off by a gesture that saved nothing; an `.ics` never advances it at all, because an `.ics` is events handed to another app and not a restore path. A **live copy of either kind suppresses the line entirely** (`App.showNudge` reads `mirrorStatus.state !== "live"` **and** `cloudStatus.state !== "live"`), since nagging somebody to export a backup they are continuously taking is the app not knowing what it does — and the cloud copy is the same document one transport over, so the argument does not get to apply to only one of them. The Nudge caption in the settings panel says both, because a switch whose behaviour depends on another panel two sections down is a switch that looks broken. **Dismiss restarts the interval and does not switch the feature off** — "not now" is not "never", and `settings` is where never lives. And a never-backed-up browser is anchored at **first run**, not the epoch: measured from zero the app is overdue the instant it opens, which hands a chore to somebody who has not made a single event, and there is no honest earlier anchor — an event's `start` is when it happens rather than when it was written, and the seed events are not the user's work. `backupSnapshot()` stamps that anchor from inside the getter `useSyncExternalStore` calls during render, so it stamps **without `emit()`**; notifying from there would loop.
- **It is a line over the stage, on every view, and that is the whole risk of the feature.** Nothing in circal has ever interrupted the user, so the change of character had to be as small as it could be while still being seen: `BackupNudge` is one `.caption`, an export pill and a dismiss pill at the top edge, clear of the readout, reserving no layout when it is away, `pointer-events-none` except on the pills so it cannot eat a click meant for an arc under it. A modal was the obvious build and was refused for the same reason a `Suspense` spinner is. It is off while `shaded` or in ambient — a notice arriving over something that owns the screen is the interruption this design is avoiding — and it sits above every view rather than the dial alone, because a warning you meet only in one of four views is a warning that can be missed indefinitely.
- **A VEVENT with no UID gets a _derived_ one, never a generated one.** `derivedUid()` in `ics.ts` = FNV-1a over DTSTART/DTEND/SUMMARY/LOCATION/RECURRENCE-ID, formatted `<base36>@circal.local`. It was `crypto.randomUUID()`, which meant a new id on every parse: `feeds.ts` builds each event's key from the uid, so every pull remounted every arc and hover, selection and the arc under the pointer all dropped. UID is required by RFC 5545, so this only fires on a feed nobody can fix.
- **`zonedToUtc` brackets the wall time with two candidate offsets** — the one in force a day before and a day after — taking the pre-transition one when neither or both read back. That resolves a spring-forward gap to the instant _after_ it and a fall-back ambiguity to the _first_ of the two, in every zone. The earlier two-pass version converged from the naive UTC reading, so which side of a gap it landed on depended on the sign of the offset: Berlin was right and Los Angeles an hour early.

### Recurrence

- **`src/lib/recur.ts` is somebody else's specification, not this app's idea.** RFC 5545 §3.3.10 read down the expand/limit table: a period is expanded into candidate days by the BY\* parts, given a clock, narrowed by BYSETPOS, then bounded. Verified against every worked example in §3.8.5.3. Do not "simplify" a branch without checking that suite again — most of them exist for exactly one example.
- **The seed is an instance only when the rule generates it.** RFC calls DTSTART the first instance but also requires it to be synchronised with the rule; the two readings differ only for a rule that contradicts its own seed. This editor can _write_ that contradiction (deselect the weekday the event is on), and an event that then refuses to leave that day is a bug the user cannot fix. A synchronised rule generates its seed anyway.
- **A rule naming a date some months lack simply does not fire there** — the 31st, 29 February, a fifth Friday (§3.3.10's invalid-instance rule). The only answer that does not invent a date the sender never wrote.
- **COUNT is walked into `until` on the way in; the model stores one bound.** `countedUntil` in `recur.ts`, called from `ics.ts`. Counting is by the _rule_, before EXDATE — RFC subtracts exceptions from the generated set, so an excluded day still spends one of the count. A count past `WALK_CAP` is read as unbounded on purpose: over-running a bound shows occurrences that should have stopped, guessing one too early deletes them, and only the second loses data.
- **`exdates` and `rdates` are local keys in two forms** — `YYYY-MM-DD` for a whole day, `YYYY-MM-DDTHH:mm:ss` for one instant — exactly EXDATE's own two RFC value types. Local, because every other day-identity here is (see `dayKey`).
- **Every entry point is capped.** `MAX_INSTANTS` (512) per call, `WALK_CAP` (2000) periods per COUNT walk. A `SECONDLY` rule names 86,400 instants a day and a feed is not obliged to be reasonable; truncating is visible in a way a frozen tab is not.
- **EXDATE and RDATE are the properties collected as lists.** Both legitimately appear on several lines of one VEVENT, and a flat prop map keeps only the last — a series quietly gaining back every occurrence it was told to skip. Hence `Block { props, exdates, rdates }` in `ics.ts`.
- **RECURRENCE-ID is an override _event_, not a patch on the series.** `seriesId` + `seriesKey` on `CalEvent`; `occurrencesOn` builds the index once per query and skips any generated occurrence an override claims. A separate event because that is what it is — its own time, title, place and colour, possibly on a different day from the one it replaces. `feeds.ts` MUST give it an id including the recurrence-id, since it shares its parent's UID.
- **`RANGE=THISANDFUTURE` is resolved in `fromIcs`, not in a consumer.** `linkThisAndFuture` runs once every VEVENT has been read and turns the flagged override into the tail of a split series — the same shape `splitRule` and `store.splitSeries` already model, because that is what the range means. It lives there because `feeds.ts` and `backup.ts` each link overrides themselves, and one of them getting it wrong is a series that draws twice. Five things it has to get right, and only three were obvious: chained splits **fold left** (the second cut is measured against the first cut's tail, since by then that is the series generating the instant); the promoted tail takes `uid#recurrence-id` and drops its `recurrenceId`, or it collides with its parent in both consumers' key maps; without an RRULE of its own it inherits the parent's rule with `splitRule`'s **partitioned** lists (merged with any of its own), or the days the sender skipped come back; an **ordinary** override past a cut is re-pointed at the tail, exactly as `store.splitSeries` does it (left on the head it suppresses nothing and the day draws both); and a cut landing at or before the series' first instant makes the tail **absorb** the head and keep its uid, which is `effectiveScope`'s "folds `future` into `all`" one layer down.
- **`EditScope` is asked at the press, never offered as standing controls.** Three answers, `"one" | "future" | "all"`; the scope belongs to the moment of committing rather than to the event, and a one-off has one possible meaning and is never asked. `EventEditor` holds a `pending: "save" | "delete"` and swaps its footer for the question — replacing the row of verbs, not stacking above it, because two rows of verbs with one of them inert is a footer that lies. Escape backs out of the question, a second press closes.
- **"This and all future" is two series; `splitRule` (`recur.ts`) is the whole decision.** Head takes `until = at - 1` (inclusive, bounds a _start_), or its existing bound when that is earlier — a split cannot extend a series. **The exdate/rdate lists MUST be partitioned, not copied**: `until` bounds the generated set only, so an RDATE past it still fires and one left on the head fires from both halves, and a future EXDATE not carried over resurrects a day the user had already skipped. `store.splitSeries` is one commit — two would be two ⌘Z presses for one edit, and the state between them is a series that has lost its future — and it **re-points overrides past the cut at the new series**: `seriesKey` still names the instant, so an override left on the head suppresses nothing and the day draws both it and the tail's own arc.
- **Splitting at the series' own first occurrence is "the whole series".** The head would generate nothing, so `effectiveScope` in `App.tsx` folds `future` into `all` there — one live event rather than two, one of them dead.
- **`store.remove` takes the overrides with it** (`e.id !== id && e.seriesId !== id`). An orphaned override is an ordinary event sitting on the day it used to replace, with nothing left to explain it and no surface that can find it.
- **`Occurrence.key` = `${event.id}@${instantKey(start)}`.** An event can appear more than once on a day now (an hourly rule, a BYHOUR list), so the day alone no longer identifies one.
- **The full recurrence shape is filled in at `store.parse`, not guarded for at every read.** A blob written before it has no `interval`, and `undefined` reaches the maths as `NaN` — a series that fires on no day at all. `hydrateEvents` covers `events` _and_ every `feeds` array, and returns the same object when nothing is missing, because `parse` runs again on every cross-tab write. No `SCHEMA` bump: nothing stored changed meaning.
- **A day's query looks back exactly the event's own duration — the whole multi-day fix.** `occurrencesOn` scanned a flat day back, so anything longer than ~48h existed on its first two days and then vanished (every holiday a feed delivers is that shape, and `lifeDensity` was already colouring days the dial denied). Overlap test = `start + duration > dayStart`, so the window is exact in _milliseconds_ (no DST reasoning; the old `addDays(dayStart, -1)` was a day-arithmetic guess at it). `lookbackCap` bounds it because the lookback _is_ the recurrence window: `Infinity` for `never` (a one-off costs one instant however wide the window), a year for ordinary frequencies, a **day** for `secondly`/`minutely`/`hourly` — `startsBetween` keeps the _earliest_ instants it finds, so widening a minutely rule's window answers with last week's and the day vanishes instead of gaining copies.
- **`dayIndex`/`dayCount` live on `Occurrence`; `spanLabel` is the one voice for them.** `continuesBefore`/`continuesAfter` say only _that_ a span runs past the day, so a five-day holiday printed an identical row on all five. `Day 3/5` replaces the time column in `CenterPanel` — on the third morning neither a clock time from three days ago nor "Now" is the answer. `dayCount` is measured from `end - 1`, because `end` is exclusive and a one-day event must read `1 of 1`.
- **The headline row does _not_ get the span column, and that was measured.** `DAY 2/4` costs `Sleeper train` most of its letters in the interior's width; its wait already reads `ends in 45h 34m`, which is the multi-day fact, and the non-lead row below prints the position. Keep `!lead`.
- **`startsBetweenIn` is `startsBetween` walked over another zone's wall clock, and that is the whole of zone support.** A feed's `TZID` says the rule was written against _that_ clock's transitions, not the reader's, so the seed, the window and `until` all move into wall time with `wallClockIn`, the existing walk runs unchanged, and every result comes back through `instantOfWall`. `zone === ""` — every event the user wrote — delegates straight through, so the floating path costs one string check. Three consequences: `exdates`/`rdates` are resolved _inside_ the delegated call and are therefore read as that zone's wall keys, which is what `EXDATE;TZID=…` means; the wall window is widened by `ZONE_SLACK` (3h, DST's one hour and double summer time's two) and the real `[from, to)` re-applied, or an instant a transition moved across the bound is lost; and a wall time inside the _viewer's_ own DST gap shifts an hour, because `wallClockIn` goes through the local `Date` constructor, which normalises a nonexistent local time forward. That last one is the floor the whole file stands on — a local event at 02:30 on the same morning does the same thing — and closing it means walking the rule in UTC fields, which is every getter in `recur.ts`.

### Event editor

- **The card is two columns above `md`, one below, and 672px wide rather than 330.** The seam is one the file already had: the left column is the event — Date, Time, the zone caption, Where, URL, Guests, Type, Shows as, Remind, Repeat — and the right is how it is filed and looks on the face — Calendar, Color, Mark. `URL` sits under `Where` because the two are one question, a room or a link. Notes span both, being the one field read rather than scanned, and are also what balances the two halves. Width is what earned it and it paid twice: thirteen rows in one 330px column scroll on every laptop, so the fields sat behind a fold on the surface whose whole point is seeing the draft while you edit it — and the footer's four verbs measured ~397px against the 306px a 330px card leaves, which is why "Share link" wrapped onto two lines with Save's chips clipped off the right edge. Each column is 335, still above the 320px floor every inline row in a `FieldRow` is written to wrap at.
- **The footer's `Kbd` chips are `hidden md:flex` (`Chord`), and Share link is icon-only, below that width.** Something had to go at 306px and the chips are the honest choice: ⌘↵ and ⌘⌫ still work, all four verbs keep their words, and a card that narrow is most often a phone, where a chip advertises a key the reader does not have. Hidden rather than dropped, so this stays one footer that is wider on a desktop instead of two footers. `ScopeChoices` caps its three answers at `max-w-[300px]` for the same arrival: unstretched they were 645px wide and read as a settings page rather than a question — a no-op in `ScopeDialog`, whose card is 300px anyway.
- **A `<fieldset>` cannot be the scroll parent, and the scroll container is a plain `div` _around_ it.** A fieldset lays its children out in an anonymous box that sizes to content and ignores the height flexbox gave the fieldset, so `flex-1 overflow-y-auto` on it silently scrolls nothing. Measured at 390×844: the grid took its full 592px, the notes band ran a hundred pixels past the card and the footer painted over it. Height is constrained on a real box now; the fieldset sits inside as a block, only ever as tall as what it holds, and keeps the `disabled` cascade that is its whole reason for existing.
- **The editor's Date row is two dates; the second names the _last day covered_, inclusive.** `lastDay = startOfDay(new Date(draft.end - 1))`. Every edit touching the far end is then a day-shift of `end` (`daysBetween(lastDay, picked)`), which needs no all-day branch: a timed span keeps its clock time, an all-day one keeps its exclusive midnight. `handleEndTime` anchors on `lastDay` too — anchoring on the start's day collapsed a multi-day span the moment one of its times was retyped. Both fields always show; hiding the only control that reaches a state is worse than printing the same day twice.
- **The editor's Date row MUST call `showPicker()` itself.** The row is a transparent `input[type=date]` stretched over a label, and Chrome and Safari open the calendar only from the indicator the input is hiding — clicking the field opens nothing. `openDatePicker()` in `EventEditor.tsx` wraps the call, because it throws outside a user gesture and does not exist in every browser rendering the field.
- **The all-day toggle remembers the times it had, never the span.** `timedSpan` in `EventEditor.tsx` = ref holding `{ startMin, endMin }`, captured on the way into all-day and reapplied to the current first and last day on the way out; without it, off → on → off reset every event to 9–10am and silently discarded times the user had set. Two clock times rather than a duration, because the span in _days_ belongs to the Date row now and a stored duration would overrule it — and the toggle itself carries the span across (`end: addDays(lastDay, 1)`), since flipping a switch must not delete four days of a five-day trip.
- **`<input type="time">` banned here** — renders in the _browser's_ UI locale, not the app's. Use `TimeField` in `EventEditor.tsx`, backed by `parseClock` (accepts `10:45 AM`, `10:45am`, `1045`, `9p`, `13:00`).
- **The editor refuses to flatten a rule it cannot spell.** `isExpressible` in `EventEditor.tsx` gates the controls; `describeRule` prints a sentence instead. Snapping BYSETPOS or BYWEEKNO onto the nearest checkbox is how an import quietly becomes a different meeting.
- **Read-only events = `disabled` fieldset**, not a prop threaded through every control — it cascades to swatch buttons and `Select`s nested two components deep, which nothing else would reach. The title input sits outside it and carries its own `disabled`. It is a block **inside** the scroll container, never the scroll container itself — see the fieldset bullet above.
- **The editor's live draft rides on `EditorTarget.live`, not on state of its own.** Five fields (`DraftMark`), reported from the one `patch` in `EventEditor`, folded in by `App.trackDraft`, which **returns the same target when none of them moved** — React bails out of an identical state value, so typing a title costs no render, no canvas repaint, no SVG diff. On the target rather than beside it because that is the only lifetime that could be right: a preview outliving its modal is a mark nothing can clear, and six `setEditor(null)` sites would each have had to remember. Readers fall back to `target.draft`, the seed, correct until the first change.
- **`patch` in `EventEditor` merges off the render's own `draft`, not through the updater form** — the shell has to be told the same value the field is about to show, and a prop cannot be called from inside an updater (those must stay pure). Safe because no handler there patches twice in one event; a handler that ever needs to MUST merge both partials into a single call.
- **`colorOf` takes `Pick<CalEvent, "color" | "calendarId">`.** A draft is not an event yet and has no id; widening the parameter to what the function actually reads is cheaper than minting a fake one, and it keeps colour precedence in exactly one place.
- **A drag on a repeating arc asks the same `EditScope` question the editor does; nothing is written until it is answered.** `App.adjustOccurrence` holds a `PendingAdjust` (the occurrence + the dial's two minute deltas) and **re-arms `preview`**, because the dial drops its own on pointer-up: without that the arc springs back to where it started and jumps again on the answer, which reads as the gesture having failed. Cancel is then just dropping the preview — there is nothing to undo. `"all"` puts the deltas on the event's own instants (the seed moves, every occurrence follows); `"one"`/`"future"` measure from `occ.start`/`occ.end`, the occurrence's real instants and not the clipped ones. A one-off is written on release with no question.
- **The notice after a drag is measured against what was actually written** — the series' own new seed for `"all"`, the occurrence's for the other two. A multi-day event's clipped occurrence notifies either way, deliberately: its visible ends are not the event's instants, so the dial could not step the day itself and an arc leaving the face without a word reads as a deletion.
- **`ScopePrompt.tsx` owns the question; `ScopeChoices` is the shared body.** The editor renders it in its own footer (the edit is already on screen and a modal over a modal is a stack nobody can read); the dial gets `ScopeDialog`, a card that has to print the event and its new span, because the gesture is over and the card covers the readout. Two copies of a three-way question drift into two vocabularies. `ScopePrompt.tsx` is in `eslint.config.js`'s `no-autofocus` exemption for the same WAI-ARIA reason the palette and editor are.
- **`CalEvent.color` = override, not the colour.** Empty string = "follow the calendar", the default every event should stay on, so recolouring a calendar still moves them. Only `colorOf` knows precedence.

### Previews and drafts

- **One notion of "the event about to exist", on both faces: the range under the pointer, else the draft in the open editor.** White and translucent while it is being drawn (there is no colour to show yet), its own colour once the editor has one. The shape is identical across the release _and_ the save — the dial's ghost path is byte-identical to the arc that replaces it — which is what stops either handover looking like the drawing having been thrown away.
- **Each face draws it in its own units; clipping is the face's own question.** `YearView` takes `{ from, to, color }` in dates and lights those days as days that _carry_ it — `markRadius(count + 1)` in its ink, no white overlay. `Dial` takes instants, because a draft can sit on another day entirely once its date row has been edited: `drafted` clips to the day with `minutesOfDay` at each end rather than elapsed milliseconds (a day is not always 1440 minutes long), returns `null` for a draft that does not reach the day, and 0…1440 for one whose middle covers it. An **all-day draft gets no arc at all**, for the same reason a saved all-day event gets none.
- **No preview for an event that already exists.** `App.pending` is `null` unless `editor.id === null`. An existing event already has its arc and its marks; a second set drawn over them is the same event twice, and once the editor's time rows move it the two disagree on screen. Previewing an _edit_ would mean replacing the arc rather than adding one, which is what `onPreview`/`DragPreview` already does for drags.

### Calendars and marks

- **A calendar may be made, renamed, recoloured and deleted, and deleting one keeps its events.** `store.removeCalendar` _moves_ the user's own events to the first calendar still standing and returns `{ into, moved }` so the toast can say where they went — a calendar is a label, and deleting a label is not a way to ask for a year of appointments. Two invariants make that always possible: the last calendar that is _not_ a feed cannot go (return `null`; the card disables its verb and says why), and a feed's payload lives in `feeds`, so removing a subscription is still a wholesale drop. `App.calendarRemoval` mirrors the same rule so the verb is disabled rather than failing — change one, change both.
- **A mark is one field in two vocabularies, told apart by alphabet — and only one of them can still be typed.** `Calendar.icon` and `CalEvent.icon` are each a Phosphor name (`[a-z0-9-]+`) or a literal emoji; `isIconName` is the whole discriminator — no prefix, so the stored value reads as itself in a backup and in devtools. `""` = the plain colour dot on a calendar and "no mark" on an event, **and so is a name this build does not carry**: `CalendarMark` falls through rather than rendering nothing, and neither `readCalendar`/`readEvent` nor the hydrators drop an unknown name, because a backup that has been through an older build MUST NOT come back with the mark missing. `firstGrapheme` keeps a flag, a skin tone or a ZWJ family one character — `[...s][0]` gets all three wrong. **The emoji input is gone from the picker, the format is not.** An emoji belongs in the title, where it is searchable and travels through `.ics`; a 72px box offering a second way to say the same thing was not worth a third of the row. Everything that _renders_ one stays, so a value from a backup or an older build keeps drawing — which is precisely why `isIconName` and `firstGrapheme` are still exported and still tested.
- **A cap per vocabulary, and a name is never sliced — `readMark` is the one validator.** `ICON_MAX` (16) guarded both alphabets with one number and that was silent data loss: one grapheme against a word list whose longest entry is `currency-circle-dollar` at 22, so ten of the 247 names in `marks.ts` were over it, and the cap ran in `readEvent`/`readCalendar` **after** `isIconName` had approved the value. A name that validated was stored as sixteen characters matching no path and drawing as the plain colour dot, with nothing raised anywhere. `person-simple-run` is one of the five `SEED_MARKS`, so this was not confined to marks somebody chose by hand: every new install corrupted its own seed data the first time a backup round-tripped it, and `suitcase-rolling` survived only by being exactly 16. So `ICON_NAME_MAX` (48) is its own number, deliberately roomy rather than fitted — a cap set to 22 has to move whenever an icon is added, which is exactly the maintenance nobody did to the old one. And the two vocabularies fail differently: a **name** is kept whole or dropped, because slicing manufactures an invalid value out of a valid one where dropping lands on the same dot honestly (`""` is already what an unknown name renders as); an **emoji** is still truncated, because there one grapheme is exactly what the field holds and `firstGrapheme` is what keeps a flag or a ZWJ family intact doing it. `readMark` is `readRecurrence`'s shape — one place deciding what the field legally is, with `backup.readEvent` and `backup.readCalendar` as its readers. A name shorter than the cap is returned untouched even with no path for it: a set that shrinks must not blank a mark.
- **`markOf` is deliberately not `colorOf`, and its third argument is why.** Colour _must_ inherit: every event needs one, so `CalEvent.color` is an override on a required field. A mark is optional at both levels, and a face where forty arcs have all picked up the same three glyphs says nothing the colour was not already saying — so `markOf(event, calendars, inherit = false)` returns the event's own and stops there unless asked. The argument is `settings.inheritMarks`, which is **off**; on, a calendar's mark becomes a default its events take, which is the useful reading for one-calendar-per-kind-of-thing. The parameter default matches the setting default, so a caller that forgets gets the conservative answer.
- **Shape and colour are read apart.** `CalendarMark` takes whatever colour the caller resolved — `calendar.color` where a calendar is named, `colorOf(event, calendars)` where an event is — so an event can borrow its calendar's glyph and still wear its own colour, and neither answer implies the other. Two deliberate abstentions: the event editor's _header_ dot is the event's colour swatch and gets no mark, and **`CenterPanel` has none at all** — its dot is `4.5–5.5 × u`, about five pixels, so a glyph there is a smudge while a legible one would widen every row's leading slot inside a panel whose corner has 29 units of clearance to `HAND_INNER`.
- **247 icons, and the number is measured.** All 1,512 Phosphor bold paths = 621 KB raw / **206 KB gzipped**, more than the entire rest of the app ⇒ "just ship them all" is a picker costing more than the product. These 247 = 120,676 raw / **44,496 gzipped**, the fifth of the library a calendar ever wants. The long tail used to be answered by the emoji field beside the grid and is now answered by the title, which is free and in colour either way. That still makes it the single heaviest module in the build — about a fifth of everything a cold load used to fetch — and it is **no longer a byte of the critical path**: `ui/marks.ts` has no static importer anywhere and is fetched on demand, which took the three chunks `client:only` blocks first paint on from 236,732 to 193,796 gzipped — **−42,936, −18.1%**, against −1.7% for lifting both modals off the same path. The old "a quarter of the bundle" line went with the mis-attribution that produced it (see the `icons.*` chunk below). The set may grow by an icon at that price per icon; it may not grow back onto the first frame.
- **A mark still draws on the first painted frame, and a dot popping into an icon is still the failure being avoided** — that argument is now the reason the eager core exists rather than the reason not to split. Two mechanisms, both in `ui/icons.tsx`. A **path cache in `localStorage` under `circal.marks`**, read _synchronously at module load_, so a mark the user has already chosen draws immediately with no chunk fetched: a handful of path strings is a kilobyte or two against the table's 44,496. A cache miss on a real name kicks the lazy import off and repaints through a `useSyncExternalStore` signal; `""` and an emoji need no path and so never fetch anything. And **`SEED_MARKS`, five paths inlined eagerly** — `house`, `briefcase`, `users` from `DEFAULT_CALENDARS`, `person-simple-run` and `suitcase-rolling` from the sample events — loaded into the cache _before_ the `localStorage` layer, because a brand-new visitor's cache is empty and the app's first impression on every new visitor was those five dots turning into glyphs. It costs **1,072 gzipped bytes** (74,376 → 75,448 on the shared chunk) and it is deliberately the seed's own five: it mirrors `seed()` in `store.ts`, and a creeping "popular icons" set is how 44 KB gets back onto the first frame one defensible addition at a time.
- **One case is left late on purpose: a backup restored into a browser with no cache.** The names are real and nothing has drawn them here before, so the plain coloured dot draws — already exactly what an unknown mark name draws — and fills in when the table lands. Once per browser per restore, stated in the module's own comment rather than hidden, and the alternative was to keep 44 KB on every cold start of every user to spare that one frame. The flicker it replaced was found by clearing storage and throttling the chunk to three seconds, which is the only way any of this is visible: at full speed the fault and the fix look identical.
- **The chunk the build calls `icons.*` is not the mark renderer, and the name is wrong on purpose.** It measures 75,448 gzipped, which invites the reading that the split did nothing; what is actually in it is the `motion` library plus shared UI, and Rollup named a shared vendor chunk after `icons.tsx` because that module sits in its import graph. The renderer itself is a few hundred bytes. That name has already cost this project two rounds: `AUDIT.md` quoted the chunk's **whole** 118,143 gzipped bytes as the weight of `marks.ts` + `icons.tsx`, so the table looked like a prize three times its real size, and the same chunk still measures 75,448 with every path gone from it — 118,143 − 74,376 ≈ 43,767, which is the table's actual share and agrees with the 44,496 chunk it became. Fixing the name means pinning `manualChunks` in the Astro config — fighting the bundler for a cosmetic gain, with real chunking to re-argue afterwards — so it was not done, and the rule is the mitigation: read a bundle report by what a chunk contains, never by what it is called.
- **The paths are vendored, and that is not an optimisation.** `@phosphor-icons/react` ships every icon as a component carrying all six weights inline — four times the weight of the one this app draws. Bold only, as data, is the whole library's worth of choice at none of the price. Measure before adding an icon library here; the number is the argument, not the taste. To add a mark, copy the `bold` entry out of `@phosphor-icons/react/dist/defs/<Name>.es.js`; the viewBox is 256 units and the paths are unmodified MIT.
- **One `MarkPicker`, in its own file, at two sizes; `noneLabel` is the only thing the two callers differ on.** The calendar card and the event editor ask the same question and `""` is the same empty string in both — it just stands for "a plain colour dot" on one and "follow the calendar" on the other. It is `src/components/react/MarkPicker.tsx` rather than `ui/icons.tsx` because a picker is chrome: it speaks lucide, reaches for `primitives.tsx` and `useFocusTrap`, and that file may use none of the three. Search matches on bare letters (hyphens and spaces stripped from both sides), so `first aid`, `firstaid` and `aid` all find `first-aid`; `fuzzyScore` is deliberately not used, because its subsequence match is tuned for command titles and ranks `bird` over `barbell` for `b`.
- **The picker asks for the whole table the moment it opens, and renders empty rather than "no match" while it arrives.** `useAllMarks` is the one caller that wants all 247, so the lazy import is a natural consequence of opening it rather than something the grid has to arrange; a search hitting an unloaded table would otherwise print "no match" for a mark that exists, which is a lie the user cannot tell from a missing icon. Empty is silent and lasts one round trip. The count in the controls comes from the same hook, so it says 0 and then 247 rather than claiming a number the grid is not showing.
- **The compact grid is a porthole, so the expand button is not a luxury.** Four rows of eight inside a 330px card is thirty-one rows' worth of set seen 24px at a time: enough to take a shape you already have in mind, useless for _choosing_ one. `MarkBrowser` is the same controls — none, search, count — over a grid of `auto-fill minmax(46px, 1fr)` cells, which puts all 247 on one screen at 1.8× the size inside a 900px window, measured. Its height is **fixed** (`min(88vh, 640px)`): a card that hugged its rows would jump a foot up the screen on the first keystroke of a search. One query serves both grids, so narrowing large and closing leaves the row narrowed the same way, and picking closes — the grid covers the card whose field you were filling in.
- **`Color` and `Mark` share one 26px rhythm, and it is arithmetic rather than taste.** The two rows sit directly above each other in the card's right-hand column, so anything they disagree about reads as a ragged column. `Swatch` is a 26px cell with the ring on the **dot** at a 2px offset — `18 + 2 × (2 + 2)` is exactly 26, where the ring on the _wrapper_ drew 4px outside the cell and put a selected swatch's left edge clear of every other row's content. That 26 is also `MarkFields`' none-button and its `h-[26px]` fields, so both dividers land on the same x. And both blocks end on the column's right edge: the mark grid's cells are `aspect-square w-full` (eight fixed 26s plus seven gaps is 236 against 220, so every cell used to spill 2px out of its 24px track and the last column past the card), and the swatch grid is `flex-1` with centred cells (left tight it stopped 39px short of the grid under it). The colour tracks then carry ~1.5px more air than the 8px row gap — invisible, where a 39px step is not.
- **`FieldRow`'s 38px is a _step_, not a minimum, and `ColorPicker` is sized against it.** Two columns holding different rows only line up where a tall row is a whole multiple of the short one, and a rule one pixel out reads as a rendering fault where an obviously different height reads as a different row — `Color` came out 77 against the left column's 76, and that single pixel is what you see. `min-h-[38px]` is border-box with the `border-b` inside it, so two steps is **75px of content**: the swatch block is 60, hence `py-[7.5px]`, which is `(2 × 38 − 1 − block) / 2` and moves if the cell or the gap does. A half-pixel padding is a whole device pixel at DPR 2 and the honest way to hit an odd content height.
- **`FieldRow fill` is how a column stops ending in a hole.** The editor's two columns are stretched to the taller one, so the shorter one's leftover sat under its last row and read as that row's own empty space — 116.5px under `Mark`, measured. The mark grid is the one thing in that column with a use for the room, so it takes it: `shrink grow basis-[108px]`, which is four rows wherever nothing imposes a height (one column, the calendar card, the fullscreen browser) and eight in a stretched column. `fill` makes the row a `flex-1` item and stretches its value cell; the parent column carries `md:flex md:flex-col`, so on one column the row is `auto` again and no `md:` prefix has to leak into `primitives.tsx`. Settings never uses it.
- **The browser is a portal to `document.body`, and Escape is the _caller's_ prop.** A portal because the card it is opened from is `overflow-hidden` and animates a transform, either of which clips a `fixed` descendant, and because it has to sit above that card (`z-[65]`) rather than inside it. `browsing`/`onBrowse` live in `EventEditor` and `CalendarEditor` because every modal here claims Escape on a `window` **capture** listener and capture listeners on one target fire in the order they were added — the editor's is always first, so a listener inside the picker could only ever close the card as well. Same argument as the shell holding the life grid's drawn run. While the grid is up the card's own ⌘↵ and ⌘⌫ are off, which is `busy` one layer in. Focus goes back to the expand button from an effect declared **above** `useFocusTrap`, so its cleanup lands first: the trap remembers the last focus outside any `[role=dialog]`, and this dialog was opened from inside one, so its answer is a control on the page behind.
- **`MarkTip` names the mark under the pointer, at the mark, in both grids.** A grid of glyphs is read with the pointer, so a name printed in a strip somewhere is a saccade away from the thing it is about — the footer version was built first and lost to that. It costs the neighbours it covers, which is the trade every tooltip makes and why this one is 26px, `pointer-events-none` (a click still lands on the cell under it) and gone with the pointer. The `title` attribute went with it: the platform's own tooltip answered the same question a second time, later, in another voice. Three things are load-bearing. It is **portalled and `fixed`**, because the grid scrolls and the card is `overflow-hidden` for its corners — either would crop a bubble drawn inside them. Its width is **arithmetic**, not measured: `.label` is 11px mono at 0.18em tracking, so ~8.6px a glyph is enough to clamp it against the window's edge with no layout read and no second render (`arcLabel`'s own trade; the estimate came out exact on the longest name in the set). And a **scroll moves it rather than dropping it** — focus landing on a cell above the fold scrolls the grid to show it, so dropping meant the first Tab named a mark and unnamed it in the same beat. `usePeek` is one delegated listener reading `data-mark`, and the 4px between two cells is deliberately not an answer, the loupe's rule about the blanks between its years.
- **The mark grid has no fade — a rule about what a fade is for.** A fade says "the list continues" and pays for that hint by dimming its own last row: a good trade over prose or an agenda, where a half-legible row is still placed by the ones above it; a bad trade over a grid of glyphs, where the dimmed row is precisely what you are trying to compare. Search is the real answer to a list of 247. `.fade-b` survives on `CenterPanel`, gated on row count, where it sits over text.
- **The calendar card is a `CalendarEditor`, opened from two places and owned by neither.** The sidebar's pencil and ⌘P's `New calendar…` / `Edit …` rows both go through `actions.newCalendar` / `actions.editCalendar`; the shell holds `{ id }` and resolves the `Calendar` from the store every render, so a rename from another tab updates the card and a deletion closes it. The palette rows are not decoration: the pencil is a pointer affordance and the sidebar is not on screen at all on a phone.
- **A palette row's second verb is `Row.alt`, on ⌘↵ and on the foot of the panel.** A row can only name one target, so a per-event action has to hang off the event's own row — a `Duplicate …` row of its own would either double the result list or guess which match it meant. ⌘↵ falls through to _nothing_ when the highlighted row has no `alt`, because running the primary instead would make one modifier mean "duplicate" on one row and "open" on the next. The foot is fixed height and always present, for the same reason the mini-month's dot row is: a strip that appears would move the list under the pointer.

### Sun, moon, zones

- **Your lightcycle band replaces the elapsed ring; it does not join it.** Both live on `DIAL.TRACK` at `DIAL.TRACK_WIDTH`, and `elapsedSegments` returns `[]` whenever the band has half left to draw (`place && (daylight || moonlight)`, computed once as `band`). A second band on its own radius _next to_ the track was the first attempt and read as one line accidentally doubled. Deliberately no `DIAL.SUN`.
- **Second zone's band = a different place, so it does get its own rim.** `DIAL.ZONE_BAND` (424) sits 21 units outside the track, 13 inside the zone numerals it belongs to; `SunBand` takes `radius` for exactly this. Halves = `zoneDaylight` / `zoneMoonlight`, independent of yours, because the point of the ring is comparing two places and comparing them half-drawn is not a comparison. Coordinates come from `placeForZone(secondZone)`, resolved in `App.tsx`; `null` (`UTC`, aliases like `Asia/Calcutta`) = no band, no switches offered.
- **Lightcycle bands = the one sanctioned break in "chrome is greyscale".** They are data about the day, not chrome: warm-but-desaturated for day, dim violet for night, neither may compete with an event arc. Same opaque-segment technique as the ring they replace, same alpha-compounding reason.
- **`light(m)` in `SunBand` MUST stay continuous through zero.** Returns signed light (positive sun, negative night) and civil-twilight shoulders reach exactly `0` at the horizon, so the warm band and the violet band meet without either starting on a step. Every discontinuity in that function is a visible edge on the rim — shoulders used to begin at `0.04` and the band began with a hard line. 288 segments (five minutes each, eight-unit chord) stops the ramp looking stepped.
- **Two halves = draw-time filter, not an argument to `light`.** The curve is computed for the whole day either way and the segment loop drops the half switched off, so the half that stays keeps the exact shape it had beside the other. Yours defaults on, because the band _is_ the track; with both off the elapsed ring comes back rather than leaving the rim empty. Second zone's defaults off — its caption annotates a ring already there, and the band is another ring. `night` = old name for `moonlight`: `migrateSettings()` in `store.ts` carries the stored one across, `readSettings()` in `backup.ts` does the same for a backup.
- **`DIAL.ZONE` (446) fixes `PAD` (30).** The crop leaves 470 units of radius; a 15-unit numeral centred on `ZONE` reaches 453, and the caption beside the topmost one runs up to 131 units further right — eight units short of the crop at the worst anchor angle. Anything further out gets cropped: move `PAD` before you move `ZONE`, and keep `ZONE_BAND` _inside_ `ZONE`, because the caption runs horizontally outwards from the numeral and would otherwise cross the band.
- **Zone caption hangs off the topmost of four marks**, to its right, never beneath — beneath it collided with the hour numeral below it and ran off the viewBox at three o'clock. Four marks 90° apart ⇒ one is always within 45° of top, where the horizontal room is.
- **Zone ring measured against the viewer, never against UTC.** `delta = zoneOffset(now, zone) + now.getTimezoneOffset()` — the caption reads `Tokyo +7`, because you are the origin of this dial and "GMT+9" makes the reader do subtraction. Also the only form staying right in the weeks when one of two zones has changed for DST and the other has not.
- **`sun.ts` returns minutes since local midnight and does not clip.** A place far from the viewer legitimately produces a negative sunrise or a sunset past 1440; `Face.tsx` samples inside `[0, 1440]` and lets the rest fall off the face.
- **Place chosen by city, never typed.** `settings.place` carries the IANA zone it was picked by, and `placeForZone` is the only thing turning a zone into coordinates, so the picker can always show what the band is drawing. `store.parse()` drops a stored place with no `zone`: a band the settings panel says is off is worse than no band. Coordinates come from `zone.tab`, so they name the zone's principal city — a couple of minutes of sunrise error at worst, finer than the band draws.
- **The moon lives in the sidebar, the one thing here that draws something the calendar does not contain.** Not on the face: every radius the dial gains costs `PAD` and legibility, and unlike the lightcycle band the moon is not a fact about the _day_. It reads the _selected_ day, which is what earns it — arrowing through a week walks the moon through its week. `moon: false` by default, because chrome does not appear unasked.
- **One drawing, in this app's own voice.** There was a second register — `Aperture`, the disc occulted behind a watchmaker's window by bites of exactly its own radius, in night blue with stars — and it went: the mechanism was the more interesting picture and it was the only chrome in circal that was neither greyscale nor flat, which is a fight eyecandy does not get to win. `MOON_STYLES` / `MoonStyle` went with it; a stored `moonPhase` string becomes `moon` in `migrateSettings`, and a backup's in `readSettings`, since either register was a moon somebody asked for.
- **`light(m)`'s rule again, for the moon: the terminator is an ellipse of `rx = r|1 − 2k|` over the lit half**, filled with black below half and with the moon above it. `k = 0.5` collapses it to nothing, exactly the straight edge a quarter moon has — one function covers all eight phases with no branch per phase. Only the **lit** part is drawn: no circumference and no dark limb, so a crescent is a crescent rather than a disc with a crescent on it, and a new moon is nothing at all. The shadow is still a painted `#000000` fill rather than a hole, because it occludes the lit half by covering it.
- **`CalEvent.tzid` is the zone a _rule_ is read against, never where an instant is.** Instants stay epoch ms and `end - start` stays elapsed ms; the zone only ever decides which wall clock the recurrence walk sees (`startsBetweenIn`). `""` = floating, which is every event the user writes — an event dragged onto this dial means the hours it was dragged onto. A non-empty IANA name now arrives from **two** writers, and knowing which one put it there is load-bearing: `ics.ts`'s DTSTART reader, where the zone came out of a file, and `travel.keptEvents`, where the user answered "keep them as they are" and the app stamped the zone they were written in. `isZone` in `time.ts` is the one validity probe (`Intl` throwing is the only signal the platform gives), shared by both writers and by `backup.readEvent`, which drops anything it refuses back to floating rather than storing a zone nothing can resolve.
- **The `.ics` export carries the zone and deliberately carries no `VTIMEZONE`.** DTSTART/DTEND/RECURRENCE-ID go out as `;TZID=<zone>:<wall stamp>`, EXDATE/RDATE reuse the key's own digits (the key already _is_ that wall clock, so nothing is converted), and UNTIL stays a UTC stamp — §3.3.10 requires exactly that once DTSTART carries a zone, which makes that stamp load-bearing rather than incidental. No `VTIMEZONE` because every mainstream consumer resolves an IANA name against its own tz database, and a synthesised component would either duplicate that database or lie about the DST rules. The user-facing half is one `.caption` in the editor — `Times in <city>` — and it now fires for **every** zoned event rather than only a subscription's: a stamped event is one the user deliberately left on the clock it was written on, and this row is where that answer stays legible afterwards. Still print-only, and there is still no picker: a zone reaches an event from a feed's TZID or from that one answer, never from a field.

### Travel: the device that moved

- **Nothing here is a corruption, and the prose must not pretend otherwise.** A user's own event is floating, so its instant is absolute and what the dial draws is that instant on whatever clock the browser now has: fly Berlin → New York and 09:00 is drawn at 03:00, the same moment it always was, which is precisely _why_ it moved. The defect was never the arithmetic — it was that the app said nothing. So `travelNotice(stored, current, hasEvents)` compares `settings.deviceZone` against the zone read **once** on load and asks, once, and the question is the whole screen (`TravelPrompt`, shaped like `BirthPrompt`) rather than a modal over a working dial. It names **cities, never IANA identifiers** — `Europe/Berlin` is a database key and somebody who has just landed is owed the name of the place they left — and it proves what happened with a resolved illustration rather than a description: what a 09:00 event written back there reads as on this reader's own face. Two answers, both legitimate, neither styled as the safe one, and **no dismiss**: "keep them as they are" _is_ the do-nothing answer, and a dismiss would leave the app knowing the device had moved and drawing the day as though it had not.
- **The shift is derived through the wall clock and is a function of each instant, never a subtraction.** `movedInstant` is `instantOfWall(wallClockIn(at, from), to)` — the pivot the recurrence walk already turns on, which also settles a wall time landing in a DST gap or a repeated hour the way every other reader here settles it. Two zones are not the same distance apart all year (Berlin and New York are six hours apart in July and five in the fortnight their transition dates disagree), so an event in March and one in July do not move alike, and one shift computed for "now" and applied to a list would be wrong for most of it. `until` moves at **its own** instant for the same reason: it bounds a start, and a series handed its old bound stops on the wrong day. `exdates`/`rdates`/`doneKeys` deliberately do not move at all — they are local wall-clock keys, and both answers keep the wall clock intact, one by preserving it and one by naming the zone it was kept against. Rewriting them is the resurrection bug `duplicateOf` documents, arrived at from the other side.
- **An all-day event is re-anchored under both answers and stamped under neither.** A date has no clock to keep, so "keep the old times" is meaningless for it, and an offset applied to a day boundary puts the 5th on the 4th — five hours off midnight is the previous evening. `reanchored` puts it back on local midnight of its own calendar date in the new zone, `addDays` rather than `n × 1440` minutes, the same argument the dial's multi-day span already makes.
- **Each answer is one recorded commit carrying both the events and the new `deviceZone`, and deliberately does _not_ own its settings.** `commit(next, true)` puts the whole answer in one undo step, so ⌘Z gives the calendar back — but the device zone rides along inside that step precisely so an undo does **not** restore it: an undo that "fully" undid the answer would put the prompt straight back in front of somebody who has already answered it. That asymmetry is the kind of thing a later reader tidies into consistency; it is deliberate, and it is why `setDeviceZone` (the silent path for a first run, an unmoved device, or a browser with no events of its own) passes `false` and writes no history at all. The silent path reads the stored zone from the store rather than from props, because hydration is lazy and the first commit's snapshot is still empty.
- **Keeping stamps the events, and the stamp has to stay legible afterwards or the answer was a trick.** `keptEvents` writes the old zone into `tzid`, which is what lets three surfaces go on naming the clock those hours belong to: the readout prints the city beside a span (never during a drag — a range being drawn has no event yet), the agenda row prints it in the trailing slot, and the editor's `Times in <city>` caption fires for every zoned event. The agenda slot is the cheap one on purpose: on a row that is neither the headline nor running it was **always empty**, so nothing gives up a column and the measurement that took `DAY 2/4` off the headline row still holds. Precedence inside that slot is urgency first — `ends in 12m` outranks where the thing was written — and a place is set `uppercase` because the slot's other two readings are prose and this one is a tag.
- **The clear knows which zones _this app_ stamped, and that list exists because `tzid` has a second writer.** The first version walked every event carrying a zone; an imported `.ics` lands in the same `snapshot.events` with real zones out of the file, so the settings row overcounted and its verb flattened a colleague's weekly 09:00 New York standup to floating — which then walks its rule against the reader's own wall clock, the exact defect `startsBetweenIn` exists to prevent, reintroduced by a settings row rather than by the domain layer. `keepEventsInZone` now records what it stamped with in `settings.stampedZones` in the same commit, and the count, the places and the clear are all scoped to it; a **list** because two journeys kept in a row stamp two zones and one field would strand the first journey's stamps, and `sane()` refuses an entry `Intl` cannot resolve and deduplicates, since a garbage entry would scope the clear to nothing while the row still counted against it. The residue is named in the caption rather than papered over: an imported event genuinely naming the same city is indistinguishable from a stamped one and goes with them. Telling them apart needs a provenance field on every event — a permanent addition to the model to serve one settings row, against a residue that is narrow and one undo step wide.
- **Clear is the one travel action that _does_ own its settings.** It empties `stampedZones` as it clears, so an undo that restored the stamps without the list naming them would leave them unclearable. Both derivations — the count and the places — read what the events actually carry rather than the setting alone, so a remembered zone that has outlived its events counts nothing and shows no row.

### Shell, sidebar, top bar, focus

- **The shell's hotkeys are two registrations, split on `busy`.** Escape is always live — it belongs to whatever is on top — and everything else is off while a panel is up: ← stepping the day under an open editor is the same bug as ⌘Z undoing behind one, and "is the user typing" does not catch it, because focus on a button inside a dialog is not typing. A panel that wants one of those keys keeps it for itself: the palette closes on its own ⌘P, since the shell's copy is off while it is open.
- **Escape's order is panel → life run → drawer → lit grid → ambient, and the life run is in the shell for exactly that reason.** `useHotkeys` fires every registration; there is no precedence between them. So the year ring can keep its own `setSpan(null)` — nothing else on the shell's list is live in that view — but a run drawn across a **lit** life grid is the natural way to use the field, and a local handler there would abandon the drag and clear the thread in one press, the two-things-per-key bug this list argues against. Hence `LifeViewProps.draw`/`onDraw`: `App` holds the run so it can put it at the front of the queue. The field's own handlers then bail on `!draw` (the dial's "both handlers bail on missing gesture" rule) so a pointer still down and still moving cannot re-arm what Escape just dropped, and `Field` clears the run on unmount for the reason `Dial` clears its preview.
- **`useFocusTrap` finds the opener by `[role=dialog]`, not by its own ref.** React commits a child's `autoFocus` _before_ attaching the parent's ref, so a ref-based "is this focus inside me" test recorded the dialog's own first field as the thing that opened it, and Escape restored focus to a detached node. One document `focusin` listener for every trap, refcounted, for the same ordering reason: a dialog mounted only while open (the editor) does not exist when the button that opens it takes focus.
- **A trap's restore runs from a passive cleanup, by which time the dialog's nodes are gone** and focus has fallen to `body`. So restore fires on `body`-or-still-inside and checks `isConnected` — anything else moved focus deliberately and knows better than the trap does.
- **The sidebar is `inert` when closed, not `aria-hidden`.** It is held mounted for 180 ms while it leaves, and `aria-hidden` over live tab stops is a keyboard user tabbing into controls nobody can see. `inert` takes the focus and the accessibility tree together, which is the one thing "this column is closed" actually means.
- **`push` against `drawer` is measured, not a breakpoint.** The dial is height-bound on any stage wider than it is tall, so taking `SIDEBAR_W` off the width there costs the instrument _nothing_ — the face does not even shrink. The moment the stage would become width-bound, every pixel the column takes comes out of the face: `rowWidth - SIDEBAR_W < rowHeight` is that condition. It is not "is this a phone": an iPad in portrait is 1024 wide and still cannot afford it, and a half-screen desktop window flips over exactly where it starts to hurt. Measured on the **row**, never on `main` — `main` is already the pushed width, so asking it would shrink the stage, flip to drawer, un-shrink, and oscillate. The pre-measurement frame is invisible because the sidebar starts closed.
- **The drawer lives inside the row, under the top bar, and that is why it has no close button** — the button that opened it is still on screen and still reachable, so a header of its own would be a second verb for one action. It is modal in effect (it covers the whole face) ⇒ `role="dialog"`, a focus trap, `tabIndex={-1}` for the trap to land on, and Escape. It is **not** in `busy`: `busy` gates the hotkeys because ← under an open editor steps the day out from under unsaved work, and a drawer has no unsaved work. `shaded` is the other question — "is the instrument reachable" — and that is what the ambient timer and the dial's ⌘⌫ ask.
- **The mini-month's dot row is always mounted, empty or not.** Rendered only when a day carried something, the cell's `flex-col` re-centred and the numeral rose by half a dot on exactly the days that had events — so the month read as a ragged line and the shift, not the dots, was the loudest thing in the grid. `h-[3px]` unconditionally. Any cell whose contents are conditional has this bug waiting in it.
- **The sidebar has no agenda — a decision, not a tidy-up.** The column printed the selected day's occurrences two hundred pixels from the dial's interior printing the same ones, the same fact twice, and it was the fact this 260px column had least room for. What is left is what the interior cannot do: navigate to a day (the mini-month), manage the calendars, and one complication. If an agenda ever comes back it needs an argument the interior does not already answer.
- **Settings is a near-full-screen overlay flowing balanced columns, not a 420px scroll.** `columns-[320px]` on the scroll area, each `Section` a card with `break-inside-avoid`, so a new group spends width before it spends scroll — the panel only ever grows, and a setting below the fold is a setting nobody finds. Consequences: a column is 320px, so every inline row inside a `FieldRow` MUST `flex-wrap` (a two-toggle row overflows a card at phone width otherwise), and the last row of each section takes `last`, because the card's own border is the boundary.
- **`.label` is a label voice; a sentence uses `.caption`. And the two greys it is written in are a hierarchy, not a choice.** 11px mono uppercase at 0.18em tracking is legible as three words and hostile as prose. `ink-2` (~5.4:1 on `surface`) is for anything that _names_ something — a `FieldRow` label, a group heading, an inline word naming the control beside it, a `NumberField` suffix; `ink-3` and `ink-4` are for anything that _annotates_ one — a `PARTSTAT` tag, a count, a time under a title. A name may **not** take `ink-3`, because `ink-3` is also what `input::placeholder` prints in: at the same grey a label and the words standing in for a missing value read as one kind of thing, and a card of unfilled rows was a wall of identical grey with the labels no louder than the absences. `ink-4` (~1.5:1) is decorative only, never text. `.caption` = 12px sans at `ink-2`; add `tabular-nums` where it prints a time or a count. Every inline `.label` naming a control moves with its row label or the row comes apart at the two voices.
- **`MOD`, in `ui/primitives.tsx`, is the only place a modifier is spelled.** `useHotkeys` has always accepted `metaKey || ctrlKey`, so the chips were the one Mac-only part of the app. Read from the platform at module scope — the island is `client:only`, so nothing can disagree — and only ⌘ is translated: ⇧, ↵ and ⌫ are printed on the keys themselves, and `Ctrl Shift N` across four segments costs the top bar something else. It is 40px against ⌘'s 18, making the left group 67px wider, so **`TopBar`'s two measured thresholds are a pair** (readout 1220/1450, wordmark 1430/1660) written as whole class strings — Tailwind reads the file as text, and a class it cannot see is a class it does not emit. Anything joining that group re-measures both, on both spellings.
- **The top bar has three measured breakpoints and a fourth segment moved all of them.** The date readout is absolutely centred on the _bar_, not on the space the two button groups leave, so everything the left group gains comes straight out of the readout's clearance — and the wordmark is what yields, every time, because it is the only thing up there that is identity rather than information. Wordmark gone below **1430px** (1080 at two segments, 1180 at three), readout gone below **1220px** (was 820), and the `‹ Today ›` stepper gone below **480px**, where the three groups stopped fitting a phone at all. The stepper is the right thing to drop because it is the one control with another route to it — the drawer's mini-month, a face in ⌘E, a date typed into ⌘P — where hiding a view or the drawer's own button would cost something with no second way to reach it. All three measured against the longest header `formatDayHeader` produces (`Wednesday · Sep 30`); anything added to that group re-measures all three, and the check is a sweep from 360 to 1600 looking for an overflow or a collision, not a spot check at two widths.
- **`settings.weekStart` is one setting because it is one fact, and it is geometry as well as chrome.** The strip's seven days, the mini-month's grid _and_ its header row, the top bar's week range, the life grid's columns (they are real weeks) and the loupe's transpose (a row is a weekday) all read it, and three settings would let them disagree about where a week starts. `WeekStart` is `0 | 1 | 6` — the three starts anybody picks; the arithmetic in `weekOffset` is general and the picker is not. **No default parameter anywhere in `lib`**: an implicit Monday is exactly the bug, and a required argument is what makes a missed callsite a type error. `LifeLayout` and `LoupeLayout` carry it, so everything already taking a layout reads it there rather than growing a parameter. RFC's own `wkst` is untouched — a rule's meaning is not a display preference. **The one place `weekStart` still gets a default is `freshInstall()` in `store.ts`**, and only there: `weekStartFor(locale)` (`time.ts`) reads `Intl.Locale`'s `getWeekInfo()`, or the older non-standard `weekInfo` property where `getWeekInfo` is absent, maps ISO's `firstDay` — 7 → Sunday, 6 → Saturday, anything else or a throw → Monday — and runs only on the branch a browser with nothing stored takes, so a value already in `localStorage` can never be overwritten by it. No `SCHEMA` bump for it: a bump resets settings to their defaults, and where a default came from is not a change of what it means, the same argument `hydrateEvents`'s missing-field fill-ins already stand on.
- **`settings.wakingFrom`/`wakingTo` is what "free" is counted against; `DEFAULT_WAKING` is now a default rather than the answer.** `dayLoad(occurrences, waking)` takes the window explicitly, because the caller holding `settings` is the one that knows it. Booked is still measured against the whole revolution and free only against this window — they do not sum to anything, and the palette's slot search and the totals line MUST keep meaning the same thing by the word, which is the whole reason it is one pair of numbers and not two settings.
- **The tab title is the reminder that survives a backgrounded tab, and it needs no switch.** Push needs a server; `document.title` does not, and `· 14m · Standup` works whenever the browser is open, which is the honest maximum here. `useTitleCountdown` writes it **only while the tab is hidden** — a visible one already has the answer on screen in the ring and the headline row — restores the title it found on mount on unmount, on nothing being due and on the tab coming back, and carries no `settings` flag because a title is not a notification and asks nobody's permission. It rounds down like `untilText` and prints `now` rather than `0m` for something already running: `0m` is a countdown that has arrived and then stays arrived for the whole meeting.
- **`CommandPalette` takes `settings` whole, at five fields.** It reached the clock, `inheritMarks`, `defaultDuration` and the two waking ends, under a comment claiming the fourth would convert it — the same drift the panel-props rule exists to stop. `TopBar` (one field) and `Sidebar` (two) stay on scalars, which is the other half of the same rule: a panel reading one field should not re-render on a thirty-eighth changing.
- **`Settings` and `EventEditor` are `React.lazy` behind their overlays; `LifeView`, `YearView` and `WeekView` deliberately are not.** The three view panels hold both faces mounted and hand geometry to each other mid-transition — the day ⇄ life zoom, the day ⇄ week zoom, the year ⇄ life unroll — so a chunk arriving a frame late would arrive during a flight already under way. Neither modal hands geometry to anything, which is what made them the cheap half. Each sits in its own `<Suspense fallback={null}>` — no spinner, because a fallback that resolves in tens of milliseconds inside a modal is a flash, and this app refuses that kind of chrome. `Settings` is mounted unconditionally (it gates its own visibility off its `open` prop via `AnimatePresence`, and its exit animation needs it in the tree to run), so `Suspense` fetches its chunk the moment `Shell` first commits — off the critical path but not delayed. `EventEditor` only enters the tree once `editor !== null`, so left alone nothing would fetch its chunk until the first ⌘N or arc press paid a real network round trip for it; an idle-time effect (`requestIdleCallback`, `setTimeout(…, 1)` where Safari has neither) warms it instead, once the shell has nothing more urgent to do. Measured on an isolated worktree at that commit alone, gzipped: critical path 240,807 → 236,621 bytes, **−1.7%** (27,079 raw, −3.7%); `Settings` (6,083) and `EventEditor` (4,794) moved off it entirely. That number is worth keeping beside the marks split's **−18.1%**, because the two together are the only estimate-versus-measurement pair this repo has: the modals were the obvious lever and bought almost nothing, the icon table was the one nobody wanted to touch and was ten times the win. `sun.ts` (14,154) is what is left of any size on that path, and it is a NOAA solar model the first frame's rim genuinely needs.
- **The settings panel's scroll box and its `columns-[320px]` box MUST be two elements, and this shipped broken.** A multi-column container fragments along the **inline** axis: fill one fragmentainer and the next column goes to the _right_, not down. When the multicol is itself the scroll container the fragmentainer is its own height — definite here, the dialog caps at `min(900px,92vh)` — so past three columns' worth of cards the rest lands outside the box. Chromium leaves the column height unconstrained for a scroll container and grows downwards, which is why every check passed there; Firefox honours the definite height, and at 1512×982 put Data and Mirror in column four and Cloud and About in column five (`scrollWidth` 2055 against a 1238 client, `scrollHeight` **equal** to the client, so not even a vertical scrollbar hinted at it) with `.no-scrollbar` hiding the horizontal one. A settings panel silently ending after Feedback, in the browser this app's own backup nudge is written for. The fix is one wrapper: the outer element scrolls, the inner one has auto height and therefore no fragmentainer to overflow. **Any scroll region that grows a `columns-*` MUST keep them on separate elements, and MUST be checked in Firefox** — `pnpm verify` cannot see this and Chromium will not show it.

### The mirror file, and the thing that reads it

- **The mirror file _is_ a `.json` backup, plus a `zone` and a `rev`.** Deliberately not a new format: same shape, same validators, so a mirror can be handed to Import and an export from before any of this can be handed to the mirror. `readMirrorFile` goes through `backup.readBackup`, which is the boundary that already assumes hostile input — and something outside the browser writing your calendar is exactly that, however well meant. An absent `zone` or a malformed `rev` reads as "did not say" rather than failing the file; losing a calendar over bookkeeping would be the wrong trade.
- **A file, not a localhost bridge, and the reason is the tab.** A background daemon the page connects to only works while circal is open, which makes an assistant blind at unpredictable moments — worse than one that is never there. A file sits on disk whether the tab exists or not. It also settles the other half of `AUDIT.md`'s oldest complaint for free: `localStorage` was the only copy, and "Clear site data" is one menu away.
- **`mirrorDigest` is what stops the file churning.** The mirror writes on every store change, and a feed pull stamps `fetchedAt` on its calendar — so `serialiseMirror` zeroes a subscription's pull state (`exportBackup`'s own normalisation) and the digest compares the three fields that are actually about the calendar. Without it every subscription refresh rewrites the file and looks to a watcher like the calendar having changed. Same trick as `baseSignature`, one layer out. An adopt records the digest of what the store **made** of the contents, never the contents' own — `adopt` normalises on the way in (`sane` clamps, feeds are swept), so the file's digest can differ from the store's, and recording the file's answered every adopt with one extra write that said nothing.
- **A file ahead of us is merged where both documents are stamped, and adopted where either is not.** `mirrorVerdict`'s `adopt` used to mean "take their document whole", and across two machines that discards a day: the laptop edits on Tuesday, the PC on Wednesday, and the undo step lands on the machine nobody is sitting at. `merge.ts` is the missing diff — `Grave` plus `CalEvent.updatedAt`, since a filtered array cannot tell _deleted here_ from _not seen here_. `mirrorMerges` is the gate and `MIRROR_VERSION` 2 is what it reads: a v1 file, or a `settingsAt` of `0` on either side, gets today's adopt/stale behaviour exactly. `connect()` still adopts rather than merging, deliberately — the gesture is a person naming their calendar's file, and on a first run the local document is eight seed events that must not propagate. **`mirrorDigest` is canonical (`canonicalJson`) and cannot go back to `JSON.stringify`:** a merged document holds records from both sides, and the same event stored here enumerates its keys differently from the same event rebuilt by `readEvent` out of the file, so an insertion-order digest reads a merge that changed nothing as a change — both machines write, each reads the other's write as news, one write every poll for ever.
- **An undo restamps and buries; `adopt` never restamps and `restore` always does.** A step holds the events as they were, _with the stamps they had_, so an undo put back a record the other machine's copy outranks and the next merge silently reverted it. `merge.restamped` is the one answer: what a step changes is stamped now, what it removes is graved. `adopt` is exempt because what arrives is a merge or another writer's document, and re-dating it makes the adopting machine win every subsequent merge wholesale — the bug this work exists to fix, wearing a different hat. `restore` is not exempt because a user importing a backup has asked for that file to win. A reader tidying that asymmetry into consistency is reintroducing one of the two.
- **`rev` is the whole concurrency story, and `stale` does not adopt.** A writer reads, checks the rev is still what it read, writes `rev + 1`. `mirrorVerdict` answers `ours` (we wrote it — adopting would loop), `adopt` (somebody moved it on) or `stale` (the file is _behind_ us: an older copy restored underneath the tab). Stale makes the browser re-assert rather than adopt, because winding a calendar backwards is the one outcome nothing undoes and `localStorage` still holds the newer truth.
- **Both halves keep that contract now; the browser did not, and it cost events.** `casWrite` in `mcp/file.ts` always read-checked-wrote. `mirrorLink.write()` went straight to `handle.createWritable()` — a blind truncate — so two events written through an agent vanished mid-session with no error on either side: `onStoreChange` debounces `SETTLE_MS` (400ms) at `localRev + 1`, an agent writing inside that window does not move `localRev`, and the tab then wrote **its own `rev N+1` from memory**, so both writes carried the same number and nothing downstream could notice. `claim()` is the fix: re-read immediately before replacing, and answer with the revision to write or `null` to not write at all. It reuses `mirrorVerdict` rather than forming a second opinion, because the three answers are the same three — and only `adopt` changes anything, since `stale` re-asserting over an older copy is the anti-rollback that was already wanted. It **abandons rather than merges**: there is no diff here, only two whole documents, and merging by id resurrects anything deleted locally (`duplicateOf`'s resurrection rule from the other side). Adopting makes the casualty the _local_ edit instead of the agent's, and that one is recoverable — `store.adopt` records an undo step and toasts. The revision comes from disk (`max(found, local) + 1`) rather than from a caller's arithmetic, because two writes can queue behind `writing` and the second's number was worked out before the first ran. `absorb` is the adopt path `poll` and the guard share. Verified by driving the race through the shell bridge, not by reading it: pre-fix the agent's event is gone 600ms later, fixed it survives.
- **The window inside `casWriteOnce` is closed by an advisory lock, and the halves are deliberately asymmetric.** Between the confirm-read and the `atomicWrite` there used to be a milliseconds-wide gap no re-read could close — the confirm-read _is_ the re-read. `acquireLock` now takes a sibling `.lock` (exclusive create is the atom; mtime past `LOCK_STALE_MS` reads as a crashed writer and is broken; a live one is waited out to `LOCK_WAIT_MS`, then refused naming the file). Staleness is judged by mtime and never by pid, because a pid cannot tell a dead writer from one on another machine, and a synced folder is exactly where a second writer lives. The browser cannot take that lock — a `FileSystemFileHandle` reaches one file, never its siblings — so on its side `withFileLock` (Web Locks, origin-scoped, exactly the set of writers sharing the IndexedDB handle) closes tab-vs-tab, and browser-vs-server remains what it was: honest by `claim`'s re-read and the server's confirm-read, not excluded. Do not "simplify" either half onto the other's mechanism; neither can see the other's.
- **`atomicWrite` fsyncs, because temp-file-plus-rename alone was two thirds of what its comment claimed.** A rename survives a crash of the process; it does not survive a power loss, where `writeFile` returns with the bytes in the page cache and the rename's metadata can reach the disk first, leaving the new name pointing at a short file where a complete one was. The temp file is synced before the rename and the directory after — the directory **best-effort**, because not every platform will open one for it and failing a write whose bytes are already durable over a durability nicety is the wrong way round, which is `remember()`'s trade one layer out. The temp file is removed if anything after its creation throws.
- **A write is never a patch, so the reader refuses a file it does not fully understand.** Every mutation round-trips the whole document through `readEvent`, which keeps the fields it has names for and drops the rest — so an older reader writing a newer file is silent loss of exactly the fields it was too old to know about. Measured, not feared: the published `circal-mcp@0.1.0` bundle dropped nine keys per document (`free`, `remindLead`, `organizer`, `attendees`, `attendeeCount`; `backupNudge`, `backupInterval`, `deviceZone`, `stampedZones`). `MirrorContents.version` carries the envelope version — absent reads as this build's own, for the reason `zone` does — and `assertVersionAllowsMutation` refuses beside the zone guard it mirrors. **No override env var**: a zone mismatch is something an operator can reason about and be right, "my reader is too old for this file" is not. Reads still go through, because reading cannot damage the file.
- **Remembering the handle must never fail a sync.** The IndexedDB put that persists the handle and the rev is bookkeeping; the write it follows has already put the calendar on disk. Reporting that write as failed because the note about it did not stick is the wrong way round — and it is precisely what a browser with storage refused looks like, where the file itself is written perfectly well. Found by driving it in a browser, not by reading it.
- **`store.adopt` says nothing itself.** It is `restore` without the toast, because only the caller knows which file moved and whether this was a sync or a reconnect. It is undoable and owns its settings, so a wrong answer from an assistant is one ⌘Z away — which is also why `connect()` **adopts** a file that already holds a calendar rather than overwriting it. The destructive direction is the one that cannot be undone.
- **`src/lib/mutate.ts` exists so the scope question has one answer.** `EditScope` — one / future / all — is asked at the press in the app and demanded as a parameter by the server, and both go through the same five reducers. Two copies of a three-way question drift into two vocabularies the moment either side changes. The server **refuses** a mutation on a repeating event that names no scope rather than picking one; guessing `all` deletes a year of standups.
- **The zone is in the file because every day boundary here is local.** `dayKey`, `startOfDay`, the whole of `tests/west/`. A reader in another zone would put events on the wrong day and be confident about it, so the server warns on a read and refuses a write unless `CIRCAL_ALLOW_ZONE_MISMATCH=1`.
- **The MCP server imports the app's own domain layer, and that is the point.** `parseQuickAdd`, `dayAgenda`, `freeGaps`, `scoreEvent`, `describeRule`, `readEvent`, `mutate.ts` — a second implementation of any of them is a defect, not a shortcut, because it is how the assistant and the dial come to disagree about what Tuesday contains. `store.ts`, `backup.ts` and `notify.ts` import React but touch no DOM at module scope and guard their `localStorage`, so importing them in Node is safe. **Nothing in `src/` may import from `mcp/`** — the browser bundle must not gain a byte from it.
- **Built on `@modelcontextprotocol/server` v2 (spec revision 2026-07-28), not the v1 `@modelcontextprotocol/sdk`.** v2 is `McpServer` + `registerTool` with Zod v4: one schema per tool, from which the SDK derives the JSON Schema the model sees, validates arguments before the handler runs, and infers the handler's types. It also carries the per-tool annotations that matter for a surface like this — `readOnlyHint` on the six read tools, `destructiveHint` on `update_event` and `delete_event`, which is what a client uses to decide what to confirm. **stdout is the protocol channel**: log with `console.error`, one `console.log` corrupts the stream.
- **`MirrorFile.remembered()` mints and adopts the default path when nothing is remembered and nobody has said no.** `~/Library/Application Support/circal/calendar.json`, created empty — the same safe seed `poll()` already reads as "nothing to adopt, the next write fills it" — so an assistant connects on first launch with no gesture at all, not merely no second one. `mirror.declined` in `UserDefaults`, set by `forget()` and cleared only by `pick()`, is what makes disconnecting stick: without it, the next launch would mint the default straight back and silently undo what the user just did. The save panel stays, for a file wanted in iCloud Drive or a repo. The destructive direction is unchanged either way: adopting never writes content to a file it did not just create, so a picked or default path that already holds a calendar is adopted, never overwritten — the one outcome nothing undoes, the same argument `mirrorVerdict`'s `stale` case already stands on. `circal-mcp --find` looks at this exact path first, named outright rather than discovered, because it sits inside `Library`, which the walk it otherwise does skips on purpose.
- **A `FileSystemFileHandle` exposes only `.name`, never a path — true of the browser, and now only of the browser.** Deliberate privacy design, and there is no way around it from inside a page, so on the web circal cannot tell a user where their own mirror file lives on disk and cannot pre-fill it into a command; `circal-mcp --find` exists for exactly that gap, searching instead of being told, and `/assistant/` explains the absence rather than papering over it. `AUDIT.md` Tier 6.2 named the exception before it existed: the shell's own picker returns a security-scoped bookmark, which does resolve to a path, so `MirrorFile` in `mac/main.swift` reads it straight off to mint and adopt the default location with no gesture at all — the standing complaint "stops being true the moment the shell owns it," and now does. Copy written for the web build still may not claim to know a path it cannot resolve; `circal-mcp --find` still matters there, unchanged.
- **A `.ics` the Dock hands over is text, and the page owns the one import path.** `application(_:open:)` in `mac/main.swift` never parses a calendar — `src/lib/ics.ts`'s `fromIcs` stays the only parser — it reads the file as UTF-8 and calls `window.__circalImportIcs`, the exact function the settings panel's own Import button calls, so a drop and a menu import cannot come to mean two different things: same new calendar, same toast, same undo step. The first draft flushed a cold-launch drop on `didFinish`, reasoning that a finished navigation meant the page had registered the global — true before the lazy split, and false the moment `Settings` and `EventEditor` moved into their own chunks and pushed the effect that registers it later still. `window.__circalReady`, posted from that same effect the instant it runs, is what the shell now waits for before flushing anything queued; a reload clears the readiness flag until the page posts again, so a drop from before it cannot be handed to a page that has not yet re-registered.
- **`window.__circalSave` exists because `<a download>` does nothing in a `WKWebView`.** Measured: the click resolved to nothing, so both the `.json` backup and the `.ics` export silently wrote no file at all in the app build, while the identical code correctly downloaded on the web. `backup.ts`'s one `download()` helper is now async and checks for the shell's bridge first, falling back to the anchor otherwise, so no call site learns there are two ways to save — the same bargain `mirrorLink.ts` already strikes for its own picker beside `showSaveFilePicker`. It returns whether a file was actually written: the shell's `NSSavePanel` can be dismissed, and `exportIcs`/`exportBackup` skip their toast on that `false` rather than announcing an export the user just cancelled — the browser anchor has no cancel to observe, so it always reports `true`.
- **The status menu's login-item and Dock checks read live, in `menuNeedsUpdate`, never a cached boolean.** A login item can be removed from System Settings → General → Login Items without circal knowing, and a cached check there would have the menu asserting something no longer true; the same argument covers the Dock check, since `NSApp.activationPolicy()` is the running app's own answer and nothing else can go stale, either. `SMAppService.mainApp.register()` is off until asked, deliberately: a calendar that adds itself to login items unbidden is the kind of thing that makes people distrust software, and `register()` throwing surfaces through `bridge.note` rather than leaving a check that no longer means what it says.
- **Menu-bar-only mode costs the `.ics` Dock drop, and that is the honest trade, not a bug.** `NSApp.setActivationPolicy(.accessory)` removes the Dock tile, and without a tile `applicationShouldHandleReopen` never fires — the drop two bullets up simply cannot land, leaving ⌥⌘C and the status item as the only ways back in. Applied at launch, before the window exists, because switching it once the window is up needs a re-activate and a re-key to avoid leaving the app behind others; the toggle itself does both. Default `.regular`: a mode somebody chooses after finding the status item, never one they wake up in.

### The cloud row

- **Email OTP needs one thing no code in this repo can do: the Supabase dashboard's Magic Link template must be switched to send `{{ .Token }}`.** `cloud.requestCode` calls `signInWithOtp` and the UI then asks for six digits, but that one endpoint mails whichever of the two the template is written for — so on a project left at its default a user gets a link, in front of a form demanding a code that never arrives, and nothing fails anywhere for anyone to notice. Neither the migration nor the client can assert it, which is exactly why it is written down here. It is also not the first move on a new project — the template cannot be reached until custom SMTP is configured, which the next bullet is about. A code rather than a link is deliberate: a link needs registered redirect URLs, and inside `mac/`'s `WKWebView` there is no URL for a mail client to hand back, so the secret travels through the person instead of through the platform.
- **Custom SMTP is not a nicety standing beside that template — it is the thing that makes the template exist.** Supabase gates auth email template editing behind a configured SMTP provider, so on a project still on the built-in sender there is nothing to edit and no `{{ .Token }}` to set: the order is forced, provider first and template second, and a project stood up the other way round leaves whoever is following the bullet above hunting for a field that is not there. The built-in sender argues the same way on its own terms — a couple of messages an hour, and on current projects only to addresses on the project's own team — so a deployment without custom SMTP is single-user however the template is written, which is not a feature anybody switched sync on for. Two dashboard settings belong in the same sitting, because neither moves when the provider does: the auth email rate limit stays exactly where the built-in sender left it and has to be raised by hand, so a new provider's headroom is invisible until someone does, and OTP expiry defaults to an hour — a long life for six digits sitting in an inbox, when the code reaches the person who asked for it inside a minute.
- **The client key is `PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and the rename is the point rather than tidying.** Supabase now issues `sb_publishable_…` for the browser and `sb_secret_…` for a server, demoting the `anon` / `service_role` JWTs to a Legacy tab — and a publishable key **is not a JWT**, so a variable still called `ANON_KEY` was an instruction to the next reader to decode something with no payload to read. `cloudLink.ts` names one variable and there is deliberately no fallback reading the old one: a config that accepts either name makes a deployment still holding `PUBLIC_SUPABASE_ANON_KEY` look like it works, and this feature's failure mode is _absence_ — `config()` returns `null`, the panel does not render, and nothing anywhere reports a problem. Verified against `@supabase/supabase-js` 2.112.3 before the rename, because the library is where a non-JWT key would have broken: `checkApiKeyFormat` recognises the `sb_publishable_` prefix and never throws, `signInWithOtp` / `verifyOtp` send it as `apikey` plus Bearer and `decodeJWT` is only ever applied to `session.access_token`, and Realtime carries it as a connect param and stores whatever `setAuth` is handed verbatim — it decodes nothing. Realtime is the one to re-check on any upgrade: `_getAccessToken` falls back to the api key when there is no session, so the key does reach the socket as a token, which is harmless only for as long as nothing on that path parses it. The `sb_secret_…` key bypasses row level security and must never be a `PUBLIC_*` variable.
- **One live copy at a time, and the panel is the only thing enforcing it.** `SYNC.md` leaves this to the UI — two writers each debouncing 400ms into a document the other is merging is a state to reach deliberately — so `Settings.tsx` computes `mirrorEngaged` / `cloudEngaged` as `state !== "off"` and nothing lower down knows. `off` is the only state in which a link holds nothing: a `prompt` is a remembered handle or a signed-in session, and an `error` is one gesture away from writing, so either counts as engaged. Each side's **advancing** verbs (Connect, Resume, Send code, Sign in, Unlock) go dead while the other is engaged; its **retreating** ones (Disconnect, Sign out) never do — a browser can arrive holding both, a session from before the file was picked, and it has to be able to let one of them go. Change one side and change the other, or the panel becomes a room with one door.
- **The cloud panel prints the transport's sentences and reads exactly one of them.** `cloudLink.ts` writes both failure sentences, so the panel prints `status.message` verbatim rather than translating a code into a second vocabulary that can disagree with the first. The one comparison it makes is against the exported `LOCKED`, and it is to choose the **remedy**, not the words: a locked box wants the passphrase again, a link that never completed a pass (`at === 0`) wants the step it was standing on, and anything else has a key in memory and a row it merely could not reach, where Try again is the whole fix. A panel deciding for itself what went wrong is how two files come to describe one failure differently.
- **The sign-in flow records what it did, never what worked.** `Stage` is the gesture the user made — `email` / `sent` / `answered` / `opened` — and `Asking` is what the row actually shows, derived by reading that stage against the transport's own verdict. An empty `status.name` means the code never went out, so the address is asked for again; `answered` plus `error` is a refused code rather than a session. Optimistically advancing a step and trusting it is precisely how a refused code came to ask for a passphrase, which is a form asking to unlock something nobody is signed in to.
- **"Nothing leaves this browser" is now a claim about a _configuration_, and every sentence shaped like it is a standing hazard.** Four captions and one line of the manifesto argued from it and were false the day the row shipped — the Reminders caption, the life span row's birth date, the Backup row's "only copy", and `/manifesto/`; they now argue from what stays true, that circal _runs_ nowhere but this browser and that a synced copy leaves sealed. `/assistant/` is the sharpest instance and the one to check first, because its readers are the likeliest to have signed in: the page's argument is about the mirror _file_, where the honest claim is that the file half sends nothing anywhere — a blanket "nothing goes to the internet", or "there is no account", is a claim about the whole app and one gesture from being false. Two clauses in it survived only on the word "sees", and a sentence that rests on a reader parsing carefully is not a sentence that holds. Adding a claim of this shape means owning the audit of it: `grep -riE "leaves this browser|no account|nothing.*internet" src/` before writing another one.
- **`stamped` asks whether a document carries stamps _at all_, and tightening it back to `settingsAt > 0` reintroduces the worst bug this feature has had.** It was that one comparison, and it read correctly: `freshInstall()` withholds `settingsAt` on purpose so a demo day cannot win a merge. What it missed is that two fresh installs signed into one account are **both** unstamped, so neither may merge, so each adopts the other's document whole — and adopting an unstamped document leaves you unstamped, so they never grow out of it. Measured on two browsers against one row: a first event created on the new laptop was adopted away by whichever machine synced next, silently, with only an undo step on the machine nobody was looking at. "Set up my second machine" is the whole reason somebody switches this on, so it was not an edge case, it was the case. The predicate now reads `settingsAt > 0` **or** any event, calendar or grave carrying a real instant, which is what its name always claimed. The protection is about **demo data, not settings** — `seed()`, `DEFAULT_CALENDARS` and `duplicateOf` all carry `updatedAt: 0` with a comment saying why, so a browser holding nothing but its first run still answers `false`, still cannot merge and still cannot publish eight events nobody wrote (verified: after the fix two machines converge on ten events, not eighteen). Merging begins at the first real edit, which is the first instant there is anything to defend. **A grave counts as a stamp**, and that is the subtle half: a machine whose only news is a deletion has nothing else carrying an instant, so under a records-only reading it could not merge, and the deletion is precisely what would get adopted away — the tombstone losing to the absence it exists to be distinguished from. A pre-Phase-0 blob is untouched by all of this: every stamp in it reads `0` through `hydrateEvents`' fill-in, so it is still adopt-or-refuse.

### Assets, service worker

- **Icons and `og.png` = the only unhashed assets, so `CACHE` in `sw.js` ships them.** Everything Astro builds is content-hashed; `public/` is not. The Worker serves `public/` stale-while-revalidate, so an installed client gets the _old_ icon one more time after a change unless `CACHE` is bumped. Bump it in the same commit touching an icon.
- **`sw.js` keys a navigation by its own URL — a two-page fix.** It used to `cache.put("/", …)` for _every_ navigation, correct while there was one route and wrong the moment there were two: reading `/manifesto/` once overwrote the cached app shell, so the next cold offline launch booted the manifesto instead of the dial. Offline it now tries the requested page first and falls back to `"/"`, so an uncached path still boots something. Adding a third page needs nothing; changing this back needs a very good reason.
- **`icon-192.png`, `icon-512.png`, `apple-touch-icon.png` rasterised from `icon.svg`** — `rsvg-convert -w N -h N public/icon.svg -o public/icon-N.png` — and `public/og.png` (1200×630) rendered in browser, because it sets type in Geist and Geist Mono and no rasteriser here has them: mark at the icon's own stroke proportion, `circal` at 104px/500 and `-0.035em`, tagline in mono at 22px/500 uppercase and `0.2em` tracking on `--ink-2`. No build step for any of them; edit SVG, re-render, bump `CACHE`.
- **Favicon's `r=11` / `stroke-width=2.4` chosen at 16px, not by ratio.** That radius puts both stroke edges on whole pixels where the circle otherwise smeared across three, and anything thinner antialiases to grey instead of white. Re-render at 16px before changing either.

### Sound and haptics

- **`lib/feedback.ts` builds its `AudioContext` inside `onPointerDown`, never at module load.** A context made outside a user gesture starts `suspended` and stays there, so the first drag of a session would be silent; it also re-`resume()`s on every cue, because a backgrounded tab comes back asleep.
- **Every cue = one mechanism: 3 ms noise impulse struck through bandpass resonators, one impulse per hit time.** `SOUNDS` in `feedback.ts` is the whole instrument — `step`/`slide` = single hits; `opened`/`created`/`deleted` = the same thing hit two or three times 50–100 ms apart, pitch _order_ carrying meaning (up finished, down removed). An earlier draft used oscillators for long cues and they sounded like another app's notification; do not reintroduce tone here. Each hit gets its own contact transient scaled by how hard it lands — without one, later hits read as hiss with resonance on it.
- **`level` = gain _into_ narrow resonance, not peak.** Most of a 3 ms impulse's energy never gets through, which is why multi-hit cues carry levels above 1. Offline peaks at the shipped `LEVEL` of 1.35: `step` 0.43, `slide` 0.20, `created` 0.42, `deleted` 0.42, `opened` 0.28 (its `Synth.peak` directly, since `renderVoice` normalises the sum and `LEVEL` never touches a voice). Retune by rendering into `OfflineAudioContext` and measuring — and measure **in a stream**, sixteen clicks at 45–110 ms, the only condition a drag cue ever occurs in. One click rendered on its own is not that condition, and the difference is not academic: see the hour detent below.
- **The contact is the sound; the resonance table is colour.** A Q=8 bandpass passes about 1% of a 3 ms noise burst while the `contact` highpass passes nearly all of it, so the click leads its own resonators by **13.6 dB** — the frequencies in `SOUNDS` are a tint, not a tune. Measured proof: `step` and `slide` are an octave apart on every partial and come out 6.9 dB apart in level and **3.6%** apart in spectral centroid. This instrument speaks in level: anything that needs to be told apart here has to be told apart by how loud it is, or by _when_ it lands.
- **The exciter is seeded (`BURST_SEED` = 43) — a bug fix, not tidiness.** The burst is ~130 samples and a resonator hears only its own passband: at Q=8 and 1950 Hz, bandwidth × duration ≈ 0.7 ⇒ **one degree of freedom**, each resonance excited by very nearly a single coin toss. `Math.random()` tossed it once per page load (the buffer is cached for the session), putting 4.2 dB of peak and **30 dB** of tonal balance between one reload and the next: `step` was a dull 1950 Hz knock in one session and a bright 4200 Hz tick in the next, switching only on refresh. 43 is measured rather than chosen: of the first 400 seeds it is the one whose band energy at every resonance in `SOUNDS` sits nearest the ensemble mean of a random draw (within 1.8 dB at both 44.1 and 48 kHz, against a median 4.0 and p90 6.1 for a random session), so it is the burst the table was tuned against, every time. Per-click level repeatability (0.1 dB across a drag) is unchanged; that is what caching was ever for.
- **A drag has one click, and the hour is deliberately not accented.** There were two more cues — `stepHour`/`slideHour`, a deeper notch every fourth step, on the theory that a dial should be countable by ear. Two things killed it. It never worked: the first version accented with timbre and ring length and measured **1.3 dB in a stream** against a click-to-click spread of 0.1 dB, a fifth of the way to audible, and it sat there unnoticed for months. And when it was retuned to a genuine 4 dB plus a 14 ms rebound it was still the wrong feature — the centre of the face prints `9:00 – 11:30 · 2h 30m` for the whole gesture, so the accent was a second answer to an answered question, on a channel already firing fifteen times a second. **Do not add it back.** If a drag ever needs a second signal, the readout is the one that already works.
- **Only `gated` cues are rate-limited.** `step`/`slide` can fire dozens of times a second and share one `MIN_GAP_MS`; one-shot cues bypass it deliberately, since `opened` lands within milliseconds of a drag's last click — exactly the gap that limit exists to swallow.
- **Keyboard = second instrument, `lib/keys.ts`, one mechanism all the way down: every key = sum of damped sinusoids, no noise anywhere.** That is the point — a recorded switch is broadband hiss with resonance on it, and a screenful of that is fatigue. Voice = `Synth` (`layers`, `length`, `peak`); `render` sums layers and scales the _sum_ to `peak`, because two partials add to somewhere between 1.0 and 1.5 depending where phases land, and guessing that is how one key ends up twice its neighbours. **No asset, no fetch**: eight buffers rendered on the first keystroke of a session, at the device's own sample rate, in well under a millisecond.
- **Two letter clicks = Radical's, refitted from its bundle** — 2600 → 200 Hz over 8 ms, and steady 2325 Hz, both with 1.4 ms time constant, nothing above 3.5 kHz in either, fitted to spectral correlation 0.96 against the originals. Parameters rather than an asset on purpose: exact at any device sample rate, and free. Do not "improve" one by adding a noise transient — that is precisely the difference between this and a clack.
- **All three big keys were recordings first (Everglide Oreo board) and all three lost.** Space = 1820 → 140 Hz at τ 2.0 ms, the letter click lower and longer; it was click over a 145 Hz partial ringing 14 ms first, on the theory a bar needs a tail to sound like a bar, and the tail read as boom next to clicks this dry. Delete starts at 1500 rather than 2600 and glides less far, so it reads as duller than a letter rather than brighter — taking character away should not sound like typing one; the recorded one's _release_ measured 1.8× its press (0.115 against 0.064), exactly why it sounded like a key that could not make up its mind. Return lands twice, and once a layer could start late that clunk was reachable from parameters, which took the last asset out of the app.
- **A late layer is how a key lands twice, and belongs in the buffer — never in the caller.** `Layer.at` (seconds) offsets a contact inside one voice: `render` measures that layer's glide, decay and 0.2 ms attack from its _own_ start. One buffer per voice keeps a keystroke one `start()`, and is the only way the gap between two contacts scales with `playbackRate` — scheduled separately, jitter would move pitch and leave the gap behind. Return's contacts are 9 ms apart; 14 ms was the first draft and read as two separate keys.
- **`CLICKS` alternates strictly; never picked at random.** A two-item bag chosen randomly repeats about half the time, and a repeated keystroke is the one artefact alternation exists to prevent. Radical itself picks randomly and gets away with it only because ±8% of `playbackRate` hides the repeat; both are kept here, jitter _and_ strict alternation.
- **Levels = one family across both instruments, every key a multiple of `LETTER_PEAK` (0.24)** — just under the dial detent's measured 0.27, because typing happens hundreds of times to a drag's once. Space and Return 1.1×, delete 0.92×; letter release 0.275× its press, space 0.32×, delete 0.30×, Return 0.42× because its let-go is the sound of the thing having happened. Nothing is baked anywhere, so `LETTER_PEAK` moves the whole keyboard and keeps every ratio. The 0.27 it is measured against is `step`'s, now the _quiet_ half of the detent pair — the hour's 0.43 is an accent four times a drag, not a working level, and the keyboard is not compared to it.
- **`useTypingSound` listens on `window`, reads `e.code`, not `e.key`.** "Anything being typed" is a property of the document, not of a component, so one pair of listeners covers palette, editor, settings panel and anything added later — no field knows about sound. The physical key makes the noise, so shifted `2` and `@` are one key. Silent: bare modifiers, `⌘`/`Ctrl`/`Alt` combos, `date`/`range`/`checkbox`/`radio` inputs, `SELECT` — a select is arrowed through rather than typed into, and a combo is a command, which panels announce for themselves. Held-key map cleared on `blur`, because a field losing focus mid-hold never sees its `keyup` and the stale entry would fire on that key's next press.
- **Auto-repeat makes no sound: `if (e.repeat) return`.** One press = one sound however long the finger stays down — both what a keyboard physically does and the only thing that actually fixes a held arrow machine-gunning. Rate-limiting repeats was the first attempt and failed: a 30 ms repeat interval clears any floor short enough to pass a fast typist's digraphs, and `MIN_GAP_MS` (18) exists only for those. Verified with 40 trusted `autoRepeat` events: two sounds, press and release.
- **A panel arriving says `opened`, from an effect keyed on the panel's own flag** (`paletteOpen`, `settingsOpen` in `App.tsx`), not from a cue at each call site — four call sites between ⌘P, the top bar and the palette handing over to settings, and they would drift. Audio is an external system, which is what an effect is for. Channels come from a ref updated in its own effect, so flipping Sound while a panel is open does not re-announce it, and `actions` need not depend on them. Refs are never written during render in this repo.

### Quick-add and palette parsing

- **Quick-add reads the sentence right to left.** `parseQuickAdd` in `lib/quickadd.ts` peels a duration, then a time or dash-range, then a date off the _end_ of the line; whatever is left is the title, because the title is the only free-text field and always the prefix. Order between the parts therefore does not matter: `lunch 1pm tomorrow 45m` = `lunch tomorrow 1pm 45m`. Duration is attempted before time (`1h30` = 90 minutes, `130` = 01:30 — only the unit tells them apart) and date last, so a bare number _in a sentence_ is an hour rather than a day of the month. A range carries a dash and only a dash: `to` appears in titles ("go to gym") far more often than in times, and a parser that ate it would eat the title.
- **`parseQuickAdd` returns `null` unless the line names more than a title, and it invents nothing.** A bare word is a search and a bare date is a jump — the palette already answers both, and that rule is the whole reason a create row does not appear under every query in the app. A day with no time is an **all-day** event, because that is what was said; a duration with no start takes `defaultStart` (next quarter hour on today, 9:00 on any other day), which is ⌘N's own rule, imported rather than copied. It creates and closes with no review step, so the row prints the resolved span before you press Enter.
- **The palette's whole-query parsers live in `lib/quickadd.ts` and split three ways.** `parseDate` (jump), `parseSlot` (the free-time search — the only form in which a bare number means minutes) and `parseDurationToken` (unit required, what the scanner uses). They were private to `CommandPalette.tsx` and untested, which is exactly why composing them into a sentence was not the "wiring" it looked like.
- **A repeat is claimed before the date and always carries a word of its own.** `parseRepeat` reads `daily` / `every 2 weeks` / `every other friday` / `weekdays` / `every mon/wed/fri`, and the scanner tries it _first_ on each pass: `every friday` ends in a weekday, so a date matcher reaching it first would take the weekday, leave `every` in the title and produce an event that happens once. The converse rule is why a bare weekday is never a rule — `party friday` is one party, and reading it as fifty-two is the worst mistake this parser could make.
- **A weekday rule moves the first instance onto a day the rule generates.** `gym every monday` typed on a Wednesday starts on the Monday. Without it the seed is a day the rule skips, so the arc you just made vanishes off the face as it saves — `daysOfPeriod` generates from the rule, not from the seed. Only when no date was named: an explicit `2026-09-14` is an instruction and outranks the tidying.
- **`RepeatSpec` carries only what the editor can spell** — frequency, interval, `byDay`. No `until`: an end date would have to eat a _second_ date out of the same line and nothing in the sentence says which of the two is the last one. A rule typed in the palette is therefore always a rule you can still edit afterwards.
- **`in` is the switch between a length and an offset, so it is deliberately not in `FILLER`.** `dinner 2h` = a two-hour dinner; `dinner in 2h` starts two hours from now. Sweeping `in` up as a connector — the obvious tidy-up, since the word was being stranded in the title — leaves the length reading in place and _removes the evidence_: a two-hour dinner at the default hour, with no `in` left to explain why. `parseOffset` is claimed before the duration matcher for the same reason, or `2h` is taken out from under it.
- **Everything after `in` is the offset, greedily, and a length goes in front of the name.** `in 1h 30m` = ninety minutes from now — reading it as "in an hour, lasting thirty minutes" is the trap, because that spelling of ninety minutes is completely normal. So both together is `45min dinner in 1h`, which is why `parseQuickAdd` also claims a **leading** duration, from the left, after the right-to-left pass (a trailing one still wins, and the title is never left empty). `in` in front of anything that is not a duration stays a word: `dinner in Rome`, `coffee in a bit`.
- **An offset names a clock; a date still names the day.** `dinner tomorrow in 2h` = tomorrow at now-plus-two-hours: `fromNow` sets the day only when nothing else did, and a named day keeps its date while `fromNow % MINUTES_PER_DAY` supplies the minutes. Unnamed, the offset rolls the day itself — 23:20 plus two hours is tomorrow at 01:15 — and an explicit clock time outranks an offset, because a line carrying both was edited half way.
- **An offset lands on the quarter hour** (`snap(minutesOfDay(now) + offset, 15)`), nearest rather than next, which is also what makes `now` mean the quarter you are _in_: at 10:07 the next one is eight minutes away and "in eight minutes" is not now. Every machine-chosen time in this app sits on the dial's own grid — `defaultStart` does, a drag does — and 19:07 on a 15-minute face reads as an accident.
- **The palette ranks with `fuzzyScore`; it does not filter with `includes`.** Letters must appear in order but not adjacently (`dsgn rev` finds "Design review"), and **one** query character is forgiven from four characters up — which covers a wrong letter and a transposition alike, since both leave a clean subsequence once the offender is dropped. Sort is score first, then the old nearness-to-the-day tiebreak; an empty query scores everything `0`, so the list's own order survives. Command rows keep their hand-written order until there is a query, because "New event first, calendars last" _is_ the answer to an empty box.
- **Two things in `fuzzy.ts` are corrections, not decoration.** The run bonus _rises_ through a run (`RUN * n`), because flat it scored three adjacent letters the same as three word-initials and `run` ranked "Roll up now" over "Morning run" — a whole word is not an initialism. And the scan restarts from every word start, because greedy alone lets the first letter take the earliest place it fits: `run` matched the `r` inside "Morning" and then had to reach for the rest. Both are cheaper than a dynamic program over every candidate on every keystroke, which the eight rows on screen do not justify. A hit outside the title is charged a **penalty** (`FIELD_PENALTY` in `CommandPalette.tsx`), never a multiplier — a score can be negative, and halving a negative promotes it.

### Life grid

- **Life grid = canvas, and that is not an optimisation.** Thirty thousand dots = thirty thousand DOM nodes: mount alone costs the best part of a second and nothing can be animated afterwards. `drawField` in `LifeView.tsx` batches the field into one `Path2D` per distinct colour, issues one `fill` each, walks one `Date` per year with `setMonth(0, 1 + doy)` — which rolls over, so day 59 is Feb 29 or Mar 1 as that year decides.
- **Field drawn once into an offscreen canvas; the visible one only blits it.** That makes the reveal affordable: a wave frame = one `drawImage`, one radial gradient in `destination-in`, one arc, about 4 ms, rather than thirty thousand arcs. Both canvases sized by `devicePixelRatio` and drawn in CSS pixels — at half coordinates a two-pixel dot is a grey smear. The offscreen canvas is filled _before_ being handed to its ref, because `react-hooks/immutability` rejects mutating a value already living in one.
- **Nothing following the pointer is drawn on that canvas.** Hover, selection, today's halo = SVG circles in the overlay; a hover repaint of the field would cost every dot. Field rebuilt only for a new box, span, density, search, or _day_ — why `LifeView` derives `todayKey` and memoises `today` from it, rather than passing the ticking `now` into anything but the percentage readout.
- **Today's dot takes its event's colour when it has one.** Drawn outside the colour batch (the only dot with a different radius), and skipping the density lookup there was a real bug: every event on today — including an all-day one, the obvious thing to try — was invisible. What marks the day as today is the accent halo in the overlay, not the fill.
- **`lifeLayout` picks how many lines a year gets, per box.** A year on one line is 372 columns wide, and in a landscape window that makes the cell twice as wide as tall: dots merge sideways into dashes. `SPLITS` in `lib/life.ts` tried in order, the one leaving the biggest dot wins — desktop lands on two lines of 27 weeks, phone on four or six, neither ends up with dots it cannot see. Splits are always whole weeks, so a week group is never cut in half.
- **A year = `linesPerYear` rows; columns = real Monday-to-Sunday weeks.** A row is a year only at the one-line split; at the desktop's 27-week split a row is half a year, on a phone a quarter or a sixth. Column = `jan1Offset(year) + dayOfYear`, so a year starts as many blank slots in as its 1 January is deep into its week ⇒ any seven adjacent columns are a week. Also why months cannot be a gap: a month is not a whole number of weeks, so it is a tonal band drifting along the row instead (`TONE` in `LifeView.tsx`, alternating on `getMonth() % 2`). The band pair is deliberately narrow and was retuned once already: six alternations across fifty-odd columns sits near the dot pitch, so widening the contrast stops reading as months and starts reading as vertical striping down eighty rows. Coarser bands are not the escape either — `SPLITS` cuts a year into one to six lines, so a half-year band _is_ a line at 27 weeks and the striping merely turns horizontal.
- **The grid ends by fading, never by a mark.** Expectancy is a guess and a red ring on the last day is a claim about a date; the last `FADE_DAYS` (7) ramp to black through `smoothstep` instead, event colours included — the sole thing allowed to dim a colour, because it is the grid running out rather than distance. **A count of days, never a share of the span**: a tenth of the life was wrong — any share big enough to see is years of it, the last decade goes grey, and the softness stops reading as an edge condition and starts reading as data about your seventies. Seven dots is the smallest thing unmistakably a fade and not a ragged row. Ramp quantised to `FADE_STEPS` and every colour built once per (base, step): `dim` mints a string per call and this loop runs thirty thousand times. Greys get their own numeric-keyed table, being all but a handful of the dots.
- **`lifeCellAt` = exact inverse of `lifeDotX`/`lifeDotY`** and MUST stay so, including week gaps and line split. Snaps to the nearest dot rather than requiring a hit inside one: at four pixels a dot is smaller than the pointer's own uncertainty.
- **`lifeDensity` counts dated events and yearly repeats, nothing else.** A daily or weekly rule has no end date and fires more often than the grid can distinguish, so it would paint every remaining day of a life one colour and say nothing. The hover tip is the exception and uses `occurrencesOn`, because that is a question about one day.
- **Searching the life grid = the same engine twice, never a second matcher.** `scoreEvent` in `lib/events.ts` (title, then location and notes at a penalty, over `fuzzyScore`) is the whole of "does this event match" for both the palette's ranking and the grid's thread, so a day can never light for a query the list would not have found. `LifeView` hands the events that score non-null to `lifeDensity` — the same call the field itself is built from — so a searched day and a carrying day agree about spans and about which recurrence rules a grid this size honours. The grid shows _every_ match; the palette list caps at eight, so the thread is legitimately wider than the list.
- **A search takes the colour channel whole.** Under an active query a day that did not match loses its event colour: `SEARCH_TONE` (past 0.13, future 0.06) is the only thing left; hits keep their colour at `radius * 1.55`, drawn in a second `Path2D` batch after the field — `Path2D` carries no radius, so two radii = two maps. The horizon survives on purpose: a thread with no lived-against-left is a pattern rather than an answer.
- **The query lives in `App`, not in the palette, and outlives it.** ⌘P closes and the field stays lit, because the answer is drawn at eighty years and wants reading. The palette reports every keystroke through `onSearchLife`, only while `view === "life"`; App clears on palette _open_ via the render-phase adjustment pattern (a child cannot setState a parent during its own render, which is what the reset-on-open would otherwise be). `Escape` peels layers in order: panel, then the lit grid, then ambient.
- **The palette drops its `backdrop-blur` while threading.** 2px is wider than a dot: blurring is sanding off the answer the query just lit, on the surface the query is searching. Scrim thins to `black/35` at the same time.
- **The life grid's keyboard is a listbox of one _year_, rebuilt as the cursor leaves it.** The year ring's shape (one `sr-only` `role="listbox"`, `aria-activedescendant`, the canvas draws the cursor) but 365 options is a list and thirty thousand is a wall, so the options are the days of `cursorDay`'s calendar year, clipped to the span. A row of this grid already is a calendar year, which is why the year is the unit the labels speak in. The canvas is `aria-hidden`: it is the half of the picture that cannot be read out, and two nodes describing one field is a field described twice. ← → step a day, ↑ ↓ a week (the columns are real weeks, so seven days is straight up or down), Page a year, Home/End the two ends of the life; all of them `stopPropagation`, because in this view ← → belong to the shell and step the year. The keyboard's ring and the pointer's are **one** ring and **one** `DayTip` — `active = hover ?? cursor` — since two marks on that field at once is two cursors.
- **Every option's label comes off `density`; only the active one is counted.** `density` is exactly what the field is painted from, so a label that reads it agrees with the picture by construction. `dayTally` runs for the cursor's day alone — expanding recurrence 366 times to fill a list nobody reads straight through is a frame spent on nothing, and the one day somebody is standing on deserves the tip's own answer.
- **A drag on the life grid is the year ring's gesture at the next scale out, through the same `onCreateSpan`.** Press, drag, release: a press that never left its day is a click and names the day, anything wider is a run of days and therefore a multi-day event, and the shell hands both faces' answers to the same `openDraft`. The anchor is a **ref** and only the resolved `LifeRun` is state — a render per pixel of a gesture whose visible output is already `draw` is a render for nothing. `draw` lives up in `LifeView` because the **strip** prints it (`RunChip`), which is where a sentence about the whole grid goes and is the slot the search chip already takes; the hover tip is suppressed while a run is live, because a card naming one of the run's two ends is a second answer to a question that has one.
- **A run is drawn as bands, never as dots, and `CellBand` is why that is affordable.** A run of days is contiguous in reading order ⇒ at most three rectangles (the tail of the first line, every whole line between, the head of the last), so dragging the entire life costs three `<rect>`s instead of thirty thousand arcs on a canvas that would have to be rebuilt per pointer move. One private `cellBands` serves both surfaces, each reading the answer in its own axis: `lifeBands` gets rows of days, `loupeBands` gets weeks of weekdays, clipped to the year on screen. The transpose again.
- **The life grid lights `pending` too, the rule the other two faces already keep.** White and faint while the run is being drawn (there is no colour to show yet), the draft's own colour once the editor has one, so the handover to the modal does not look like the range was thrown away. `run` refuses a `pending` that misses the span outright — `lifeRange` clamps rather than declining, so an event edited onto 1850 would otherwise light the birth dot.
- **Life grid's box measured by the shell, not the view.** `App.tsx` observes `main` and resolves `lifeStage(...)` from it, because the zoom needs the day's dot in screen coordinates _before_ the grid exists — the dial has to know where it is going. Also why `LIFE_META_H` is a constant and the readout strip is given exactly that height in CSS: the shell subtracts it to find the field's origin, and a strip growing by two pixels would land the dial two pixels off every dot.
- **Life span = two settings, both storable wrong rather than merely missing.** `sane()` in `store.ts` = one clamp — `birth` not `YYYY-MM-DD` becomes `""` (shows the prompt again), `lifeExpectancy` pinned inside `LIFE_EXPECTANCY_RANGE` — run on `parse`, on `store.setLife`, and on `restore`, because `readSettings` in `backup.ts` only guarantees types.
- **Milestones are three or four marks, and the count is the whole design.** `lifeMilestones` in `lib/life.ts` returns the round days inside the span (10,000 / 20,000 / 30,000) plus the midpoint — a default eighty-year life gets three. A thousand and five thousand are numbers that sound like milestones and are not: both land before anybody has a memory of the day, and both are already behind every user. Decades are **not** in the list; the rules and their labels already name them, and a dot on top of a rule is the same fact twice.
- **The midpoint is `floor(days / 2) + 1`, not the rounder-looking `ceil(days / 2)`.** The card's second paragraph makes an arithmetic claim — past this dot the half you can still spend is the smaller one — and on an even span `ceil` leaves one more day ahead than behind, which makes the sentence false. `tests/life.test.ts` asserts the claim, not the formula. A midpoint colliding with a round day is dropped rather than drawn twice: two marks on one dot is one mark that cannot be clicked.
- **The milestone ring is drawn in the SVG overlay; the hit area is a real `<button>` in its own layer.** Two layers, one `marks` array, because the ring has to sit under today's halo and the hover ring (a milestone is a property of the grid; those three are about where you are in it right now) while the target has to be above the canvas. The buttons are also **the grid's only focus path** — three tab stops is an order somebody can use, where thirty thousand dots is not. They cost those three days their click on the field, which is exactly what `Go to this day` in the card is for; it is not a courtesy.
- **The milestone prose lives in `lib/life.ts` beside the function, and it has no em dashes.** House rule for this app's long-form user-facing writing, asserted in `tests/life.test.ts` so a future paragraph cannot quietly reintroduce one. Code comments keep the repo's own voice; the ban is on prose the user _reads through_ — the milestones and now the whole of `src/pages/manifesto.astro` (866 words, verified by reading the rendered page; the suite has no DOM and cannot reach it, so it is on you). A one-line caption in a panel is not long-form and is not covered.
- **`lifeMilestones` walks with `addDays`, so it has a `tests/west/` case.** A mark 10,000 days out crosses twenty US DST transitions; a millisecond walk would drift an hour off midnight and put the dot on the wrong day for every user west of UTC. Same rule as `dayKey` and `startOfDay`: touch a day-keyed function, add the western case.
- **The shell's clock ticks once a minute, and that is free rather than a compromise.** Nothing in circal prints a second: `splitTime` is `HH:MM`, `untilText` and `formatDuration` round to the minute, the hand is `minutesOfDay`. `useNow` aligns to its own period boundary, so `useNow(60_000)` in `App.tsx` fires at `:00` — the exact instant every one of those strings changes (verified in the browser: `01:17 → 01:18` landed at `01:18:00.09`). It used to tick at 1 Hz and wake Dial, CenterPanel, YearView and LifeView 3,600 times an hour to redraw pixels that were already right. **A surface that genuinely needs finer than a minute asks for its own clock in the leaf that prints it, never by raising the shell's rate.** There is exactly one: `LifePercent` in `LifeView.tsx`. The same hook also re-aligns rather than only ticking: `visibilitychange`-to-visible and `window`'s own `focus` both re-read the clock and re-arm the timer to the true boundary, because a suspended machine or a throttled background tab leaves the last tick stale — by up to a full period — until the next one fires on its own. The shell's wake observer (`NSWorkspace.didWakeNotification`, dispatching a synthetic `focus` at the page) is what turns a laptop lid into that same correction rather than waiting on whatever else next focuses the window; a reload would fix the same skew and was rejected, since it throws away scroll position, an open editor and an unsaved draft to correct a clock that is wrong by at most sixty seconds.
- **`PERCENT_DECIMALS` is derived, not chosen, and moving it needs the table beside it.** One step of the life percentage's last digit is `span / 10^(decimals + 2)`: at six it is 25s on an eighty-year span and 47s at the 150-year maximum — a figure with six decimals on it that sits still, slower than the shell's own minute. At eight it is 0.25s, so it steps several times per tick of the one-second clock below and three in four values are never drawn; that is only honest on `requestAnimationFrame`, and a digit changing faster than it can be read is noise. **Seven is the only value inside five seconds across the whole of `LIFE_EXPECTANCY_RANGE`** (2.5s at the default, 4.7s at 150 years). `tests/life.test.ts` pins the bound rather than the arithmetic: it asserts the digit moves within five seconds on every span the app draws, within three on the default, and _not_ within one — the last being what keeps it from outrunning its own clock.

### Loupe

- **The loupe is a magnifier, not a zoom, and the difference is the view's whole invariant.** Thirty thousand dots at four pixels is legible as a picture and illegible as a day, but pan-and-zoom turns the life into a map, and a map of your life is a worse idea than a picture of it. So the eighty years never move: the year under the pointer is drawn a second time, large, on a card over the field. The other candidate was a fisheye in place, wrong here for a reason the year ring is not — a ring is one-dimensional and closed, so `spread` conserves its own slack, where a grid pushed aside in two axes either overlaps rows or opens a hole, and its columns stop being real weeks. Distorting the cartogram means the picture you are reading is no longer the picture.
- **The loupe is the grid's own cell arithmetic at `colsPerLine = 7`, transposed — arithmetic, not taste.** At the desktop split a line of the field already spans the whole width, so a year magnified in the field's own orientation gains nothing across and has nowhere to go down. Turned on its side it is `LOUPE_COLS` (54, always the wider of a year's 53 or 54, or the strip wobbles as the pointer crosses a year) rather than 372, and the pitch comes out four or five times the field's. A column _is_ a week, so there is no week gap — the field's gap groups seven columns that are one, and here one column already is. `loupeCell(d).row === mondayOffset(d)` is the claim, and it is the tested one.
- **`LOUPE_GAIN` is a coverage correction, not a preference.** The field's dot covers about `0.36` of its cell (`π·r²` over `pitchX · pitchY` at the desktop split); the loupe's covers `π · 0.4²` = `0.50` of a square one. Same `TONE` = forty per cent more light per unit area, and the plate came out bright enough to compete with the event colours, the one thing this grey channel may not do. Gain = `0.36 / 0.50`. The _ratio_ inside `TONE` is untouched, so past still reads against future and the month band still drifts; only the absolute light moves.
- **The loupe writes the field's own `hover`, which makes it a control rather than a picture.** Pointing at a big dot moves the small one's ring and the tip; pressing opens the day; dragging draws a run of days and hands it to the editor, the one thing a four-pixel field cannot be asked to do at all. So the card is the one surface here that has to _keep_ the hover when the pointer leaves the canvas — hence one `onPointerLeave` on a wrapper around the pair, never on the canvas, and hence a blank cell inside the loupe is ignored rather than clearing (crossing one would drop the card out from under the pointer). `loupeLayout` returns `null` when the cells would not beat the field's own dot by `1.8`, or would be under five pixels: a second picture the size of the first is worth none of the room.
- **The card hangs in the half the pointer is not in, on two thresholds.** `sideFor` flips to the top past `0.62` of the field and back below `0.5`, because a single line across the field would flip 150px of chrome for every pixel of jitter across it — this is `DayTip`'s own flip with hysteresis, since the card is not a tooltip. `DayTip` then takes an `avoid` band and moves to the other side of the pointer when it would land on the loupe, and only when that other side is actually clear. Both the band and the keyboard's `aim` are the reason `locate` returns its point even for a miss: which half the pointer is in is a question the blanks between years can answer as well as a day can.
- **The card waits `LOUPE_DWELL` before it arrives — the difference between a tool and a flicker.** It is the largest thing in this app that appears without being clicked, so a pointer crossing the field on its way to the top bar must not throw a hundred and fifty pixels of chrome up behind it. `asked` is its own flag rather than a reading of the hover, because the hover changes every four pixels and the wait must not restart for that; `wake()` early-returns once asked, so field → card → field never re-dwells. **The keyboard skips it entirely** — `aim` sets `asked` directly, since the dwell exists for a pointer that was going somewhere else and a keypress never is. Arriving is `LOUPE_IN`, leaving is `LOUPE_OUT`, two thirds of it: things go faster than they come, and a card that lingers is in the way of the thing it was magnifying.

### View transitions

- **Day ⇄ life = zoom, year ⇄ life = unroll, day ⇄ year = crossfade.** `PANEL` in `transitions.ts` holds all of it; `AnimatePresence` keys one panel per view. The dial scales down onto the dot of the day it is showing (`transformOrigin` = _style_, so already right on the frozen render of the panel that is leaving) while the grid's wave leaves that same dot; back the other way, the wave collapses onto it and the dial grows out of it. The exiting panel gives up pointer events at once — for the best part of a second it is still on top of the incoming one, and a click landing on the view you just left is a bug you cannot see.
- **`exit` is a variant label, so the panel MUST be handed the whole table.** `initial` and `active` are resolved during render and passed as objects (see the frozen-props rule below), but `exit="exit"` is a _label_, and a label with no `variants` prop resolves to **nothing at all**, silently, with no type error and no lint. That is exactly what happened: `variants` was dropped when the other two came off labels, and for two months every panel exit did nothing — the dial popped out instead of shrinking onto its dot. Objects outrank the table, so `variants={PANEL}` costs nothing and is what keeps `exit` alive. Verified by measuring the leaving panel's `transform` across the flight, which is the only way this is visible.
- **Zoom's scale keyframes are geometric, not linear.** Apparent size is linear in scale, so a plain `1 → 0.008` tween hangs at full size then disappears in three frames. `ZOOM_STEPS` = five keyframes each a third of the last, on `ease: "linear"`, with uneven `times` so the smallest step gets the longest slice — that is the settle. The wave's own curve is near-linear for the same reason in reverse: every ease-out crossed the window in 120 ms then crept.
- **A leaving element cannot read the new view from its props**, because they are frozen at its last render. `ViewFlow` is therefore a _ref_ (`flow` in `App.tsx`, `{ from, to, day }`, written by `go()` and by the popstate handler): motion resolves a dynamic `exit` variant when exit starts, and `usePresence` fires then too, so both read `.current` and get truth. `usePresence` also holds the life view mounted until its wave has collapsed — `safeToRemove()` called by the animation's `onComplete`, and immediately when there is no wave to run.
- **The year ring owns both halves of the unroll; the shell only keeps out of its way.** `YearView` is the one with the ring's geometry and both ends have to agree on it to the pixel, so it draws the ⌘Y → ⌘L and ⌘L → ⌘Y flights itself on a canvas and holds its own unmount open with `usePresence` — the same contract `LifeView` has with the zoom. `PANEL`'s two unroll branches therefore neither fade nor scale: the canvas is already showing you the whole thing and a fade over it only takes contrast off it. `stage` = null (no birth date, box too small) falls the pair back to the crossfade, and the `!canUnroll` arm of the presence effect is what stops that hanging the panel forever.
- **`unroller` is an honest unroll, not a fly-to-target.** At `t` the days sit on a circle of curvature `(1 - t) / radius` while the arc _length_ eases from the ring's circumference to the row's width, so they stay on one curve the whole way; lerping 365 positions straight to their destinations instead scatters particles at a line. `1 / k` is not a number at `t = 1`: the point is written as `sin θ / k` and `(1 - cos θ) / k`, which tend to `s` and `0`, and there is a guard below `1e-9`.
- **The unroll's easing is not `EASE`, and cannot be.** The angle still subtended falls as roughly `(1 - t)²` — curvature merely halved is still a semicircle — so nearly all the _visible_ straightening is in the first half of `t`. On `EASE`, which spends two thirds of its travel in the first quarter of its time, the ring was a line 150 ms in and the move was over before the eye found it. `UNROLL_EASE` leans the other way. For the same reason the life grid arrives on a **0.44 s delay**: the ring is the same greys the grid is, so against thirty thousand dots the whole movement is invisible and it has to happen on black.
- **A year is not always one row, so the unroll settles onto the true dots.** `lifeLayout` splits a year across up to six lines, so the straightened ring is only ever the first of them. From `SETTLE_FROM` the days blend off the flattening curve onto `lifeDot`'s actual answer; both curves are continuous, so it still reads as one movement instead of unroll-then-rearrange. 1 January's dot is the anchor and `length` is measured to 31 December's when the two share a line — the desktop case, where the ring lands on exactly the row it becomes with neither end to reel in.

### Intro animation

- **The intro is not a reveal. Every element of the face animates itself, and `introDelay` is the whole schedule.** One rule — an element is delayed by _where this face puts it_ — asked of a tick, an hour, an event arc and a segment of the elapsed ramp alike, so the day assembles in day order because the day **is** the order. There is no timeline object anywhere and nothing has to be kept in step with anything else; a ring added later gets its place for nothing. A first version masked the whole instrument behind a rotating conic gradient, which is one line of CSS and reads as a wipe: nothing has mass, nothing arrives, and the ordering the geometry already contains is thrown away and re-imposed from outside.
- **The delay is an _angle_, not minutes since midnight, and that is what makes it work on both faces.** The hand starts at the top, which is midnight on the 24-hour face and noon on the twelve-hour one. Keyed to the clock, a twelve-hour face begins assembling at the bottom and spends the first half-turn out of step with its own hand — verified by eye, which is the only way this could have been caught.
- **Three CSS classes and `pathLength="1"` carry all of it** (`global.css`). `.intro-draw` and `.intro-arc` normalise the dash arithmetic to the path's own length, so a half-hour tick and a six-hour arc take the same easing and read as one gesture; `.intro-pop` lands what has no length to draw, about `fill-box` so a numeral grows around itself rather than around the dial. `backwards` fill is load-bearing on all three — without it an element is fully drawn for the whole of its own delay, which is every element visible on the first frame. An arc's **group** carries the fade and its **body** carries the draw, because the body's own opacity is `0.42` on a past arc and a keyframe ending at `1` brightens every morning event on the way in and then drops it.
- **The hand is the one part that is not CSS, and it is a rotation of the same `NowHand`** — so when the shell puts `intro` down there is nothing to hand over. It turns once at a constant rate, in step with the assembly because both are linear in `INTRO_SWEEP_MS`, then springs on to the current minute **carrying the turn's velocity**: no seam between a hand travelling at a rate and a hand running out of momentum, and about four degrees of overshoot, which stops the whole thing reading as a diagram. Written as SVG's own `rotate(deg cx cy)` **attribute**: `motion`'s `style` route resolves `transform-origin` against the element's own bounding box, which for a spoke is out on the rim, and the hand swung about its own middle and left the face. Same trap `NowHand` documents one level down.
- **`INTRO_MS` carries 950 ms of slack past the settle, and it is not padding.** Dropping `intro` is what takes the rotation off, and a spring is still a fraction of a degree from home when its `visualDuration` is up. Measured: 1.6° at 3.0 s, four pixels of snap at the rim.
- **`circal.intro` is its own key, and `App` puts `intro` back down after `INTRO_MS`.** Not a setting: a `SCHEMA` bump resets settings, and replaying the arrival at somebody who has used the app for a year is the opposite of an introduction — and nobody chose it, so it is not a preference either. Marked seen the moment it _starts_, because a reload halfway through an animation is not a request to watch it again. The shell drops the flag on a timer because ⌘Y, ⌘L and ⌘E each unmount the dial, and a boolean left true would replay the whole thing on the way back. Off under `prefers-reduced-motion` and **not** marked seen there, so turning the preference off still gets you one; Settings hides `Play again` in that case rather than offering a button that plays nothing.
- **Three keys now sit outside the `circal.v1` blob, and each has its own reason for being out.** `circal.intro` because what it holds is neither the user's data nor a preference, and a `SCHEMA` bump must not be able to replay the arrival. `circal.marks` because a path cache is render state that is regenerated from a chunk on demand: it is never exported and never restored, and a backup carrying it would be shipping a build's internals as user data (`ui/icons.tsx`). `circal.backup` because a last-backup time _inside_ a backup file would, on restore, tell a fresh browser that a backup it never took had already happened — silencing the one warning Safari and Firefox get. `circal.feed.<id>` is the fourth and the odd one out: real data, kept out of the blob for quota rather than for meaning, and reassembled as `Snapshot.feeds`. A new key needs an argument of this shape, or it belongs in the blob.

### Year ring

- **Year ring commits on _release_, which is what makes a drag possible there.** `onPointerDown` used to call `onSelectDay` and leave for the dial, which left no room for a gesture. Now the press starts a `Span`, and `onUp` reads `sweep === 0` as a click (name the day, go) and anything wider as a range (`onCreateSpan` → an all-day draft) — exactly the dial's arc rule. Also the reason `locate` returns `{ day, onRing }` rather than `null`: a hover needs the radius gate, a captured drag does not, because the angle is the whole question once the ring is in hand.
- **Year sweep clamped to `[-from, days - 1 - from]`, never rolled into the next year.** Rolling would have to commit a day to change the `year` prop, and committing is what leaves this view — the same argument the arrow keys already make. Sweep is accumulated per pointer event with `ringDelta` for the dial's reason: two positions on a ring do not say which way round the pointer went.
- **The year ring's keyboard is a listbox, not 365 tab stops.** The month grid this replaced put every day in the tab order, which is a wall. The marks live on a canvas and cannot carry a name each, so the semantics live in an `sr-only` `<ul role="listbox">` with `aria-activedescendant` — one stop, arrows inside it, and the ring draws the cursor with the same magnifier the pointer gets. Arrows move a **cursor**, Enter chooses: naming a day here `goDay`s to the dial, so a listbox committing on every arrow press would fall out of the view on the first one. The cursor is clamped at both ends of the year, because rolling into the next one would have to commit. ← / → still step the _year_ whenever the ring does not hold focus; inside it they belong to the ring, which is why `onKeyDown` calls `stopPropagation` (`useHotkeys` listens on `window`, and React's root bubbles to it).
- **The year face shares the dial's crop, and `YEAR.MONTH` is `DIAL.ZONE` on purpose.** Same 1000-unit space, same `polar`, same `VIEW_BOX`, so ⌘D ⇄ ⌘Y is one object relabelled rather than two drawings of different sizes. `faceToPanel` reproduces `xMidYMid meet` for anything drawn _beside_ the SVG (the unroll's canvas), because a few pixels off on the first frame of a transition between two exact positions is the one error you cannot hide.
- **`markRadius` has fifty-eight units of travel because the interior is empty.** The ring _is_ the face, and at the twenty units it started with, a year read as a hairline round a hole. An empty day still gets a mark (`DAY_STUB`), which at render size is a square — the dot the same day is in the life grid; a ring with holes in it stops being a year. Today is a pip inside the ring rather than a brighter mark, for the reason the life grid haloes its dot: a day's colour is its events', and being today is not one of them. `DAY_INNER`/`DAY_OUTER` were pulled in from 336/396 to leave the magnifier somewhere to go, and `TICK_INNER` clears `DAY_OUTER + GROW_OUT`.
- **The hover is a magnifier, and it grows _outwards_.** At 0.99° the day you are pointing at is smaller than the pointer, so a highlight that only changed colour left you counting teeth — and a fixed bar drawn over the ring was four times the mark it was pointing at on a one-event day and read as something crossing the ring rather than one of the days making it up. `Ring` swells the day under the pointer, grows its neighbours less (`magnify`, a Gaussian — no corner anywhere, and every kink in that curve is a day that snaps as you cross it) and pushes the neighbourhood aside (`spread`, zero under the pointer, peaking at `SIGMA_PUSH` where the room is wanted, back to zero by `REACH` so the rest of the ring never moves). It grew _inwards_ for a draft, on the argument that the outer tip is the datum and pushing it out makes a hovered empty day look like a booked one — true, and the wrong trade: growing away from the centre reads as the day coming up to meet you, inwards read as a smudge. Length costs nothing and is generous (`GROW_OUT` 32, tip four units inside the month ticks); width is the expensive one and a test ties `PUSH` to it, though the two are no longer one-to-one — see the ink budget below.
- **The bulge snaps to the slot centre and springs there; it does not follow the pointer.** `pointerAt` tracked the pointer's exact fractional place in the year for a draft, on the argument that a quantised bulge lurches a slot at a time. What it actually did was land the full bulge on one mark only when the pointer sat at that mark's midpoint — anywhere else the two marks either side split it and neither reached full size, so the day the readout was naming looked no different from its neighbour. `pointerAt` is now a `useSpring` on `day + 0.5`, which fixes _which_ mark is the subject and keeps the movement continuous; `SLIDE_SPRING` is critically damped, because overshoot in size is a pop and overshoot in position is the magnifier running past the day it is naming. `slideTo` goes the short way with `ringDelta` (31 December to 1 January is one slot, not 364) and `jump`s instead when the bulge is down — arriving on the ring cold, or the keyboard picking it up — since sliding to it would sweep a swell across two months of a ring nobody was pointing at.
- **`FALLOFF` lives in `YearView`, not in `YEAR`.** The bell is geometry and is tested; the three exponents are how hard the drawing leans on it. They are the three parts of the effect and they are ordered: length is the gentlest (`1.4`) and carries the _reach_, so two marks each side visibly come along; width is steep (`4`) and carries the _focus_; light is steepest (`3.5`) and carries the _name_. With the bulge locked to a slot, those two steep channels are what make the subject unmistakable — length alone cannot, because a wide bell necessarily gives the first neighbour 70% of it.
- **Light is what an empty day gets _instead_ of a colour, never over one.** `white` is zero for any mark with `count > 0`: a day with events already says what it is, and washing it to white to announce a hover spends the only information this face carries on a highlight the growth has already given. An empty day has nothing to say with its fill, so the magnifier lights it — grey to very nearly white. The _selection_ is the exception and is full white whatever it carries, because it is not a hover: it is where the dial will land and where the unroll leaves from.
- **The ring is 78% ink — the hard ceiling on the magnifier's width.** 4.4 units of stroke in a 5.65-unit slot leaves 1.25 units of black each side, and a closed ring conserves it: `spread` returns to zero at both ends, so the total gap is fixed and all `PUSH` decides is _where_ the air comes from. Five marks at roughly double width need about sixteen units and the neighbourhood can lend ten, which is why `PUSH`/`SIGMA_PUSH` are 1.7/3.0 and not the old 0.9/1.15: the borrowing has to happen four days out and beyond, where every mark is dark and at its resting width and a crowded pair reads as nothing. The old pair took it all from the two slots either side, which opened a three-unit hole beside the hovered day and overlapped the marks at one and two days out by 1.2 units — a weld, visible as a bar. Past this, thicker means either a thinner `DAY_WIDTH` or black keylines with the swell drawn centre-last; there is no third option, and arithmetic decides it rather than taste.
- **The marks are a canvas because they move.** They were one `<path>` per colour in the SVG, which is right for a drawing that never changes, and this one changes every frame: the bulge rides `pointerAt` and `amount`, both springs. Both are **motion values, never state** — 365 SVG nodes re-diffed at 60 Hz is exactly the cost the canvas exists to avoid. The _day_ stays React state, because the readout and the listbox name it and it only changes once per slot crossed. `REACH` is cut where both curves are already invisible, so the loop can run all 365 without an exponential each — and it scales with the two sigmas: at 4.5 against a `SIGMA_PUSH` of 3 the tail was still most of a slot when it was cut, which is a mark that jumps as the pointer passes five days away from it.
- **The day-crossing tick cannot come from `setHover`.** React bails out of an identical value, so by the time state has settled a move inside one slot is indistinguishable from one that crossed into the next — and a cue per pointer event is not a tick, it is noise. `ticked` is a ref, written in the handler. It fires `slide`, the quieter of the two gated drag cues, on the same `tickSound` / `tickHaptics` channels: crossing a day is the same event as crossing a detent. A slow read is one tick per day and a fast sweep is a rip, which is what a finger along a comb does and is right for a ring of 365 teeth. The keyboard's cursor deliberately does **not** tick — `useTypingSound` already answers the arrow key.
- **The year's interior held a daylight figure for one draft, and it is not coming back.** Radius inside the marks was time of day, and sunrise and sunset drawn round the year is the one picture a grid cannot make. Filled it was a coffee stain; as two hairlines it was quiet and still interesting — and interesting is the problem: it is never what you came to a calendar to find out, and the readout wants the room. The dial's rim band stays; that one annotates a day you are actually looking at.
- **The year ring's centre prints a line the user wrote, not a figure the app computed.** A year-scale summary (busiest month, longest empty run) was the obvious thing to put there and is the wrong thing: the dial's interior answers a day because you are living in it, and nobody opens a year to be told which month was busy. `settings.yearQuote` is the whole feature, capped at `YEAR_QUOTE_MAX` in `sane()` and shown **only at rest** — pointing at a day is a question and a quote is not an answer to it. It is `ink-3`, the same tone as the date above it (`ink-4` is the ticks and the disabled, and 12.5px of it on true black is a line you can see is there without being able to read it). What keeps it subordinate is the italic and the gap.
- **`store.setYearQuote` caps but deliberately does not `trim()`.** It runs on every keystroke, and trimming there eats the space between two words the moment it is typed. `sane()` is the boundary that trims, because it runs on load and on restore where the value is already finished.
- **The ring answers a search with the same engine the life grid does, one face over.** `scoreEvent` filters the events and the survivors go through the same `dayTally` the marks are already built from, so the ring can never light for a query the palette's list would not have found. A matching day keeps its colour and grows one step; a day that missed falls to the grey an empty day already carries — **white was not available**, because on this face it already means the selection and the hovered empty day, and one signal cannot mean two things. The chip takes the subtitle's own slot (query, days lit, a way to clear it) and the quote is suppressed while a query is lit, for the reason the quote is only ever shown at rest: typing a question is not rest either. `App` holds the query, so it outlives ⌘P closing and is the same string the life grid threads — one field, two faces.

### Manifesto

- **`/manifesto/` is the argument, and it borrows one line, so it attributes it.** "You are a worm through time" is the opening of the Hiss incantation, from _Control_ — the life view stated in seven words, which is why it also heads the life grid's `BirthPrompt`, and it is credited in both places. Anything else this page quotes gets the same treatment. The page is deliberately islandless: a manifesto that ships React costs more to load than the product it describes.
