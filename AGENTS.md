# Repository Guidelines

## Project Overview

**circal** = calendar where day view is single dial — web recreation of Raycast macOS app _Radical_. One revolution = one day, clockwise 0.25°/minute. Events = arcs, elapsed day = ramp of light around rim, hand = current minute.

Four views, one idea at four scales: **dial** (`⌘D`) = one day, **week strip** (`⌘E`) = seven of the same face at one rotation, **year ring** (`⌘Y`) = one revolution per year, one mark per day, **life grid** (`⌘L`) = every day you get — one dot each, birth date to expectancy, one viewport. All four draw days in day order, which is what makes the moves between them geometry rather than decoration. Day ⇄ life = _zoom_: dial collapses onto dot of day it showing, grid wave radiates out from it. Day ⇄ week = _zoom_ too, the same move one step less far: the strip's face for that day **is** the dial, about four times smaller, so the dial scales and translates onto it. Year ⇄ life = _unroll_: a year in day order round a circle **is** a row of the life grid rolled up, so ring straightens onto that row and back. Everything else crossfades — a day is neither a magnified year nor a rolled-up one, and a week is neither a magnified year nor a row of the life grid.

`Clock` setting picks only what face _called_, never geometry: `12h` puts noon top, labels `12 · 1…11` twice with AM/PM captions; `24h` puts midnight top, labels `00 · 1…23`. Switch = 180° rotation plus relabel, so event arc has same length and sweep either face. Also governs **every printed time** — readout, agenda, sidebar, palette, editor — so `splitTime` / `formatTime` / `formatTimeShort` all take `Clock` and any surface printing one must thread it.

No account, no sync, no server-side state. User events live in
`localStorage` under `circal.v1`. Ships as Cloudflare Worker serving
static assets plus **exactly one route** — `/api/feed`, CORS proxy for ICS
subscriptions, because no calendar host sends CORS headers. Adding second
route? Stop: that different product.

`README.md` covers user-facing keyboard table and feature tour — this file covers parts you need to _edit_ code safely.

## Architecture & Data Flow

```
src/pages/index.astro   static HTML shell  (src/pages/manifesto.astro = prose, no island)
  └─ <App client:only="react" />        ← the ONLY island in the project
       ├─ useStore()   → { events, calendars, feeds, settings }   (persisted)
       ├─ useState ×5  → location{day,view}, sidebar, editor, palette, settings
       ├─ useNow()     → ticking Date, minute-aligned
       ├─ useReminders() → the minute tick → `Notification`, when switched on
       └─ actions: ShellActions (one useMemo object)
            ├─ TopBar / Sidebar / CommandPalette / Settings  receive `actions` whole
            └─ Dial / EventEditor / YearView / LifeView      receive narrow callbacks

  Settings travel as one `settings: Settings` prop, never field by field.
```

- **`src/lib/` = domain layer**, mostly pure. Dependency direction one-way: `time.ts` and `fuzzy.ts` (base, import nothing) ← `recur.ts` ← `dial.ts`, `events.ts`, `sun.ts`, `moon.ts`, `ics.ts`, `quickadd.ts` ← `describe.ts`, `life.ts`, `remind.ts`, `store.ts` ← `feeds.ts`, `backup.ts`. Components import via `@/lib/*`, never reimplement geometry or date maths locally. **Every module here already has a test file** — `tests/<module>.test.ts`; change one, add the case there.
- **Store = only source of truth for persisted data.** `App.tsx` holds _view_ state only. Mutations go through `store.*` — never `setState` copy of event. Settings-only mutations (`setSecondZone`, `setPlace`, `addFeed`) called straight from `Settings.tsx`, not routed through `ShellActions`, because shell has nothing to update for them. `removeCalendar` is the exception that is _also_ called from there: it is a calendar action, and removing a subscription is the one way a calendar leaves from the settings panel.
- **Two event lists, and two _keys_.** `snapshot.events` = what user wrote; `snapshot.feeds[calendarId]` = what subscription mirrored. `App.tsx` concatenates into `visible` for rendering, and _only_ that. Nothing writes to `feeds` except `lib/feeds.ts`, nothing exports it, event whose calendar has `feed` opens read-only. `feeds` is a **read model**: it is assembled from one `circal.feed.<id>` key per subscription and is the one `Snapshot` field `write()` never serialises.
- **`dayAgenda(events, calendars, day)`** = single read path onto a day: expands recurrence, clips to day, packs overlapping events onto concentric lanes. `Dial` and `CenterPanel` render from its output; the sidebar reads `occurrencesOn` directly, for the mini-month's dots only.
- **Units.** Everything inside dial = _minutes since local midnight_ (`0…1440`). `CalEvent.start`/`end` = **epoch milliseconds**, `end` **exclusive**. Nothing downstream of `dayAgenda` reasons about `Date`.
- **Day and view = URL.** `?d=YYYY-MM-DD&v=year|life`, written through `go()` in `App.tsx`: `push` for deliberate jump, `replace` for arrow stepping. `go` reads current location from ref, not from render closure — two `go` calls in one tick would clobber each other. `v` omitted for day view, validated against `VIEWS` on way in.
- **Panels take `settings` whole, not one prop per field.** `Dial` reads thirteen, `Settings` fifteen; threaded individually, adding one boolean meant editing six files — `Settings` interface, panel's prop interface in `types.ts`, `App.tsx` forwarding, panel's destructure, `backup.ts`. Object = same bargain already struck for `actions`: one prop, shell has nothing to forward. Panels destructure on first line of body, so bodies read exactly as before. `LifeView` was the last holdout at four fields and converted the moment it wanted a sixth. `zonePlace` = one exception, stays own prop — shell derives it from `settings.secondZone` via `placeForZone`, so not a setting.

## Development Commands

```sh
pnpm install
pnpm dev        # astro dev — http://localhost:4321. NO /api/feed here
pnpm dev:worker # astro build && wrangler dev — the only way to exercise /api/feed
pnpm test       # vitest run — two TZ-pinned projects
pnpm test:watch # vitest
pnpm verify     # THE gate: format:check && lint && check && test && build
pnpm format     # prettier --write . (run this, never hand-format)
pnpm deploy     # astro build && wrangler deploy
```

`pnpm verify` = only quality gate; run before declaring work done. Individual steps: `pnpm format:check`, `pnpm lint` (eslint), `pnpm check` (astro check / tsc), `pnpm test` (vitest), `pnpm build`.

## Git & Commits

Commit **regularly** — one commit per coherent change, not one per session. Commit
touching dial geometry, store schema, and a doc in same breath cannot be
reverted, bisected, or reviewed.

- **Conventional Commits**: `<type>(<scope>): <imperative summary>`, scope
  optional. Types: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`,
  `build`, `ci`, `style`, `revert`.
- Subject ≤ 50 chars where fits, hard cap 72. Imperative mood, lowercase
  after colon, no trailing period.
- Scope = area, not filename: `dial`, `center-panel`, `store`,
  `events`, `time`, `sidebar`, `palette`, `editor`, `styles`.
- **Body only when _why_ not obvious** from diff — rendering
  artefact worked around, schema bump, reverted decision. Wrap at
  72, bullets `-`, issue refs last (`Closes #42`).
- Never: AI attribution trailers, "this commit does X", emoji, restating
  filename scope already names.
- Run `pnpm verify` before committing. Gate is per-commit, not per-branch.

## Code Conventions & Common Patterns

**Imports** — always `@/*` alias (`@/lib/events`, `@/components/react/types`), never deep relative paths out of directory.

**Formatting** — Prettier, `printWidth: 100`. `prettier-plugin-tailwindcss` sorts Tailwind classes automatically, including inside `cn()` and `cva()`. **Never hand-sort class strings**; run `pnpm format`.

**Styling** — Tailwind v4, config-less; theme lives in `src/styles/global.css`. Use token utilities, not raw hex:

| Utility                          | Token                             | Use                                     |
| -------------------------------- | --------------------------------- | --------------------------------------- |
| `bg-void`                        | `#000000`                         | canvas, true black                      |
| `bg-surface` / `bg-surface-2`    | `#131315` / `#1d1d20`             | popovers & cards / controls inside them |
| `border-hairline`                | `rgba(255,255,255,.08)`           | every divider                           |
| `text-ink`                       | `#ffffff`                         | only pure white                         |
| `text-ink-2` / `ink-3` / `ink-4` | `#8e8e93` / `#5c5c60` / `#2e2e31` | secondary / numerals / ticks & disabled |
| `text-accent`                    | `#a3d9e4`                         | default calendar colour                 |
| `text-danger`                    | `#ff5a5a`                         | destructive only                        |

`fill-*` and `stroke-*` variants exist too, used in SVG. Component classes: `.label` (uppercase 11px mono, app's label voice), `.caption` (12px sans at `ink-2`, the prose voice — anything that reads as a sentence), `.kbd`, `.fade-y` (mask both ends of scroll area), `.fade-b` (bottom only, proportional — for short list whose first row must stay crisp), `.no-scrollbar` — pair fade with `.no-scrollbar` on every scroll region, apply fade **only when list actually overflows**; permanent fade on list that fits reads as rendering fault. Chrome greyscale by rule: **colour belongs to events**. Never read `calendar.color` or `event.color` directly — call `colorOf(event, calendars)`, resolves event's own override first, falls back to its calendar. Presets live in `PALETTE` (`src/lib/events.ts`): ten digital pastels, high value and moderate saturation so two can share a dial at 14-unit stroke.

**New chrome must reuse `ui/primitives.tsx`** — `Kbd`, `FieldRow`, `IconButton`, `ActionPill`, `Segmented`, `Switch`, `Toggle`, `Select`, `DateField`, `NumberField`, `ColorPicker`. Do not hand-roll a button. `FieldRow` = modal row grid shared by the event editor, the calendar card and the settings panel; three modals with three row grids is three products. `Toggle` = `Switch` plus own text label, for settings sitting two and three to a row. `DateField` = native `input[type=date]` under face of your choosing — `openDatePicker` lives beside it, because clicking field of date input opens nothing in Chrome or Safari. `ColorPicker` takes an optional `fallback`: pass it for an _event_, where `""` means "follow the calendar", and omit it for a calendar, which has nothing above it to inherit from.

**Touch targets grow, they are not padded.** Every control in `primitives.tsx` that is mouse-sized carries a `pointer-coarse:` variant that makes it finger-sized — 40px for `IconButton` and `ActionPill`, 36 for a `Segmented` item, 34 for a position cell, 30 for a swatch. Grown rather than given an invisible 44px hit area, because these sit two and three to a group at a 2–3px gap: a box wider than the pitch reaches past its neighbour's centre and DOM order decides the tap, which is worse than a small target that is honest about where it ends. `Switch` is the one exception and does take a 44px `::before` — its knob is placed at hardcoded offsets, so the track cannot move. Mouse layout must come out byte-identical; check a new control at 360, 390, 430 and 768 for overflow.

**State sync — hard convention.** `react-hooks/set-state-in-effect` active, rejects effect copying props into state. When new props must reset local state, use React render-phase adjustment pattern (three existing sites: `Sidebar.tsx`, `EventEditor.tsx`, `CommandPalette.tsx`):

```tsx
const [seeded, setSeeded] = useState(day);
if (seeded !== day) {
  setSeeded(day);
  setDisplayMonth(new Date(day.getFullYear(), day.getMonth(), 1));
}
```

**Effects for external systems only** — `window` listeners, `ResizeObserver`, timers.

**Hotkeys** — `useHotkeys({ "mod+k": fn }, enabled?)`. Combo format: optional `mod+` (⌘ or Ctrl), optional `shift+`, then lowercased `e.key` (`k`, `escape`, `arrowleft`, `t`). `shift+` part of combo whenever Shift held, printable keys included — without it `⇧⌘Z` and `⌘Z` same string and redo becomes undo. Handlers skipped while user typing in input unless combo carries `mod` or is `Escape`. `enabled` is how a modal switches the shell off — see the gotcha.

**Modals** — `const dialog = useFocusTrap<HTMLDivElement>(open)` on the `role="dialog"` element. Three dialogs, one hook, no `<Modal>` wrapper: the palette is a combobox, the editor a form, settings a sheet, and they share this behaviour and nothing else.

**TypeScript** — `strict`, no `any`. Prefix intentionally unused bindings with `_`.

**Comments** explain _why_, never _what_. Most non-obvious decisions here already carry one; read before changing line.

## Runtime/Tooling Preferences

- **Node ≥ 22.12.0**, **pnpm 11.2.2** (pinned via `packageManager`). Not Bun, not npm — `pnpm-lock.yaml` and `pnpm-workspace.yaml` authoritative.
- `pnpm-workspace.yaml` **not** monorepo marker; holds `allowBuilds` whitelist for native deps (`esbuild`, `@tailwindcss/oxide`, `lightningcss`, `sharp`, `workerd`). Add to it if new dep needs build script.
- Animation = **`motion`**, not `framer-motion` — `import { motion, useReducedMotion } from "motion/react"`, always honour `useReducedMotion`.
- Chrome icons = `lucide-react` at `size={14}`–`15`, `strokeWidth={1.75}`. The **calendar marks are a separate vocabulary** — 247 Phosphor `bold` paths vendored as data in `ui/marks.ts`, no dependency. Two vocabularies, two jobs: lucide is the app talking, Phosphor is the user choosing. Nothing in `ui/icons.tsx` may use lucide and no chrome may use a mark.
- **No state-management library**, no UI-component library; `clsx` + `tailwind-merge` back `cn()` in `src/lib/utils.ts`.
- Fonts self-hosted via Fontsource (Geist / Geist Mono). No external requests at runtime.

| `at("2026-03-08 09:30")`                 | local `Date`. **Never `new Date("2026-01-01")`** — parses as UTC |
| `ms(stamp)` / `day("2026-03-08")`        | epoch ms / local midnight                                        |
| `event({ start: "…", title: "…" })`      | full `CalEvent`, all 16 recurrence fields defaulted              |
| `calendar()` / `rule()` / `byDay("1FR")` | `Calendar` / `Recurrence` / `WeekdayRule[]`                      |
| `MemoryStorage`                          | `Storage` stand-in; `.quota = 0` makes `setItem` throw           |
| `show(dateOrMs)`                         | `2026-03-08 09:30 Sun` — the one way an instant is printed       |

**Three matchers, and instants MUST use them** — they print aligned actual/expected columns with `(missing)` / `(unexpected)` / `(out of order)`, because a 40-instance RRULE diff as raw epoch integers is not a diff:

```ts
expect(instants).toBeInstants(["2026-03-08 09:00", "2026-03-15 09:00"]);
expect(instants).toOccurOn(["2026-03-08", "2026-03-15"]); // days only
expect(occ.start).toBeSameInstantAs("2026-03-08 09:00");
```

**Scope = domain layer only** — `src/lib/*` plus worker's pure guards. No DOM, no jsdom, no component tests. Snapshot of SVG path = change-detector failing on every legitimate geometry tweak; dial verified by eye. `feedback.ts` / `keys.ts` need real `AudioContext`, tuned by offline measurement, not asserted. Four open items in `TODO.md`'s correctness table are DOM-shaped for exactly this reason.

**Store and feeds tests need `vi.resetModules()` + `await import(…)`.** `snapshot`, `lastRaw`, `hydrated`, `past`, `future` are module-level and deliberately survive a page reload — which is what a static import would share between tests. That dynamic import = sanctioned exception to static-import rule; `tests/store.test.ts`'s `freshStore()` is the pattern, copy it. `store.subscribe` is exported so the cross-tab and seeding paths can run without React; `withWindow()` there stubs the one `addEventListener` it needs.

**Test the invariant a `why` comment already names.** Most non-obvious lines in `src/lib/` carry one; that comment is the contract worth pinning. Every test must be able to fail on a plausible bug — never plumbing, source text, or a default equalling itself. Table-driven: `it.each` with `$name` templating so a failure names the case, `expect.soft` so every row reports.

**`pnpm verify` still proves nothing about how it _looks_.** Visual change verified by driving it: `pnpm dev`, exercise the path (create event, drag ring, ⌘P, switch face, step days), screenshot. Anything touching `/api/feed`, service worker, or manifest needs `pnpm dev:worker` — `astro dev` serves neither Worker route nor PROD build.

## Gotchas

- **`dayKey()` deliberately local-time.** `toISOString()` shifts day west of UTC, exactly where day-keyed store breaks. Never swap it in.
- **`Face.tsx` draws a day; `Dial.tsx` makes one editable. The split is by _question_, not by size.** Everything that answers "what does this day look like" is in `Face` — geometry, rings, arcs, labels, the band-replaces-the-ramp rule — and everything that answers "what did that gesture mean" is in `Dial`. So `Face` takes `svgRef` and the pointer handlers rather than owning them: the capture belongs to whoever reads the coordinates. Every ring outside the arcs is opt-in and **off by default**, and a `Face` given no `onGrab`/`onHover` renders no hit strokes at all — which is the whole of a read-only face. Add a switch to the dial and it goes in `Face`'s props only if it changes what is _drawn_.
- **Every id inside the face comes from `useSvgId`, and that is a rule about how many faces exist.** `url(#…)` and `<textPath href>` resolve to the _first_ matching id in the document, so a hardcoded gradient id is correct exactly while there is one face on screen and silently wrong the moment there are more. The glow, the now-hand's gradient, both band masks and every arc label already mint their own; anything new that needs a `#` reference does too.
- **The week strip is read-only, and that is what keeps `<Face>` honest.** Seven faces of drag targets is seven chances to edit the wrong day, and the dial is one keystroke away — so `WeekView` passes no `onGrab`, which means no hit strokes are rendered at all, which means the strip costs 7 × 0 pointer paths rather than 7 × 19. `onHover`/`onFocus` name the day for the shared readout and nothing else. A face is a real `<button>`: **seven tab stops is an order somebody can use**, so this view needs none of the `sr-only` listbox machinery the year ring (365) and the life grid (30,000) do — the same argument the life grid's three milestone buttons make.
- **The strip's elapsed ramp is on today alone, and its rim is on every face.** A past day's ramp is a complete bright ring answering "all of it", which is a question nobody asked, at the cost of shouting down the arcs next to it — so `elapsed` and `hand` are both `d.today`. Which leaves six faces with nothing to place their arcs against, hence `Face`'s `track`: one circle at `DIAL.TRACK`, at the ramp's own floor, so on today the ramp reads as that rim lighting up. It is the one stroke on the face drawn **translucent rather than opaque** — `TRACK_WIDTH` is three units, two fifths of a pixel at strip size, so the rim exists only as the antialiased fraction a browser rounds it into and an opaque grey has no fraction to give. Nothing overlaps it, so there is no alpha to compound.
- **Day ⇄ week scales _and translates_; it does not use `transform-origin`.** The panel already carries one — the life dot — and the dial has to land on its face whatever that origin happens to be. Under `scale(s)` about origin `o`, a point `c` lands at `o + (c - o) * s`, so putting the panel's centre on the face's centre `f` needs `t = f - o - (c - o) * s`. `App.face` solves it once; `weekZoomScale` supplies `s` and is tested against the thing that actually matters, which is that the dial's drawn diameter comes out equal to `layout.size`. One eased tween rather than `ZOOM_STEPS`' geometric ladder: this is a zoom of about four times, not of two orders of magnitude, and a ladder over that distance reads as a stutter.
- **`flow.current` is reassigned wholesale, so `face` has to be carried across it.** Both `go()` and the popstate handler build a new `ViewFlow` object, and a field written into the old one by an effect would be dropped on the next view change — hence `faceFrame`, a ref of its own that both writers copy forward. Add a field to `ViewFlow` and you must add it in three places: the initial `useRef`, `go`, and popstate.
- **⌘W is not available to any web page**, in Chrome, Safari or Firefox — it closes the tab and the keydown is never delivered, unlike ⌘D / ⌘Y / ⌘L / ⌘P, which are merely menu equivalents and which this app already overrides. The week is **⌘E**. It is not a mnemonic and does not need to be: the `Segmented` control prints the chip, which is how every view key here is actually found.
- **The strip's readout lives outside the scroll container.** Inside one it centres itself on the content, which is wider than the window the moment the seven do not fit, and the sentence walks off the side. Same reason the selected face is `scrollIntoView`d on arrival rather than left wherever Monday put it, and not smoothly: a strip that slides in from Monday every time it opens is an animation the view did not earn.
- **The three parts of the strip are one group, centred together.** Seven circles in a row are necessarily about a seventh of the width tall, so in any landscape window there is a great deal of black under them — and a readout pinned to the foot of the panel is not the strip's readout, it is a caption for the window. `weekLayout` returns `groupTop`/`groupHeight` covering captions + faces + readout; the leftover height stays outside the group, which is where it belongs.
- **`angleAt` and `minutesAtPoint` exact inverses** and must stay so. Both take `Clock`, differ only by `origin()` — minute sitting at top (720 for `12h`, 0 for `24h`).
- **`arcPath` draws full turn as two half-arcs**, because single elliptical arc whose endpoints coincide renders nothing. Removing branch makes whole-day arc vanish.
- **Gradient built from overlapping strokes must be opaque.** Elapsed ring = chain of arcs, translucent ones compound alpha wherever they overlap — every join paints bright bead, trail reads as row of tick marks. On true-black canvas opaque grey identical to translucent white, so `Face.tsx` ramps _colour_ (`grey(level)`), uses butt caps between segments, rounds only two ends of whole run.
- **Now-hand stops at `DIAL.HAND_INNER` (205).** Hand through centre crosses readout and agenda — lot of ink spent on time readout already prints. It a spoke: pip on track at exact minute, fading out along `userSpaceOnUse` gradient before centre panel. If panel grows, `HAND_INNER` must clear its furthest corner — with totals line on, lowest thing sits ~135 units below centre and 113 out from it, so corner = 176 and 29 units in hand.
- **Centre = one display with four moods, ordered.** `CenterPanel.tsx` resolves `span` first — range being dragged, else arc under pointer — then today's time, then date. Drag and hover print _same_ thing because same question, so share branch rather than each growing one. Size change = CSS `font-size` transition at 140 ms on `var(--ease)`, matched to arc's own stroke-width transition: arc thickening and clock shrinking into its span = one movement, splitting the two curves makes it read as two events.
- **Headline row = first _timed_, non-past occurrence, only on today.** All-day event = context, never next thing, never `running` either — `Now … ends in 10h 4m` = countdown to midnight dressed as appointment. Headline drops start time (ring is where start time lives), spends width on name and wait, also why `untilText` rounds _down_: countdown overstating time you have is worse than no countdown. Under `IMMINENT_MS` dot takes ring rather than pulse — pulse already means "running", one signal cannot mean two things.
- **Hovered occurrence added back to card even when ended.** Today's card filters to `occ.end > now`, so without exception, pointing at morning arc printed span with no name beside it. Costs one row of shift while pointer on past arc — honest position for it.
- **`totals` measured against two different windows on purpose.** Booked = whole revolution — six o'clock run is time spent — while free is only `WAKING`, because "nineteen hours free" not an offer. They do not sum to anything, nobody adds them. `WAKING` lives in `events.ts` beside `freeGaps`; palette's slot search and this line must mean same thing by the word.
- **`totalsAt` places line against _stage_, not dial.** `center` = only one rendered inside panel's column, under card; other eight = `flex` layer at `inset-0` with `p-4`, so corner = _window's_ corner — black a circle in landscape window never reaches. `CORNERS` in `CenterPanel.tsx` maps them, deliberately has no `center` key: that position not corner of anything.
- **Ring drag accumulates sweep; never measures from grab.** `Draw` holds `{ from, at, sweep }` and `onRingMove` sums `wrapDelta` per pointer event, exactly as arc's drag does. Measuring from grab caps new event at twelve hours and turns range inside out past that, because `wrapDelta` takes short way. Sweep clamped to `[-from, 1440 - from]` — clamping _sweep_ rather than resulting instant makes range stop dead at midnight and follow pointer back moment it turns, instead of unwinding overshoot first (same reason as `clampDelta`).
- **Full revolution = all-day event, `draftEvent` decides that.** Any span of `MINUTES_PER_DAY` or more becomes `allDay` with instants snapped to day's two midnights, so ⌘N, palette, ring gesture all agree. `CenterPanel` prints `All day` in readout while such drag live, because gesture should say what it about to make — note arc vanishes on release, since `EventArc` draws nothing for all-day event.
- **More than one revolution = that many all-day days, same function.** `Math.round(span / MINUTES_PER_DAY)`, so the dial's exactly-1440 sweep (its own clamp) stays one day and the year ring's `n × 1440` becomes `n`. All-day `end` is `addDays(startOfDay(day), days)` and **not** `base + n × 1440 minutes`: a day is not always 1440 minutes long, so a span across a spring-forward landed `end` at 23:00 on the last evening instead of the midnight after it — and `end` is exclusive, so the last day of a trip fell off the dial. Latent at n=1 before the year ring existed; the fix is the same either way.
- **Whole turn drawn closed — second rule from same fact.** `capInset` shortens arc by half a stroke at each end so painted length = duration — but once two ends meet, that inset = notch at midnight, and circle with notch reads as rendering fault. `GhostArc` returns `<circle>` for full-day range, `EventArc` drops inset at `to - from >= 360` (timed event running through whole day = any multi-day event's middle).
- **A day's query looks back exactly the event's own duration, and that is the whole multi-day fix.** `occurrencesOn` scanned a flat day back, so anything longer than ~48h existed on its first two days and then vanished — every holiday a feed delivers is that shape, and `lifeDensity` was already colouring days the dial denied. The overlap test is `start + duration > dayStart`, so the window is exact in _milliseconds_ (no DST reasoning; the old `addDays(dayStart, -1)` was a day-arithmetic guess at it). `lookbackCap` bounds it because the lookback _is_ the recurrence window: `Infinity` for `never` (a one-off costs one instant however wide the window), a year for ordinary frequencies, a **day** for `secondly`/`minutely`/`hourly` — `startsBetween` keeps the _earliest_ instants it finds, so widening a minutely rule's window answers with last week's and the day vanishes instead of gaining copies.
- **`dayIndex`/`dayCount` live on `Occurrence`, and `spanLabel` is the one voice for them.** `continuesBefore`/`continuesAfter` say only _that_ a span runs past the day, so a five-day holiday printed an identical row on all five. `Day 3/5` replaces the time column in `CenterPanel` — on the third morning neither a clock time from three days ago nor "Now" is the answer. `dayCount` is measured from `end - 1`, because `end` is exclusive and a one-day event must read `1 of 1`.
- **The headline row does _not_ get the span column, and that was measured.** `DAY 2/4` costs `Sleeper train` most of its letters in the interior's width. Its wait already reads `ends in 45h 34m`, which is the multi-day fact; the non-lead row below prints the position. Keep `!lead`.
- **The editor's Date row is two dates, and the second names the _last day covered_, inclusive.** `lastDay = startOfDay(new Date(draft.end - 1))`. Every edit that touches the far end is then a day-shift of `end` (`daysBetween(lastDay, picked)`), which needs no all-day branch: a timed span keeps its clock time, an all-day one keeps its exclusive midnight. `handleEndTime` anchors on `lastDay` too — anchoring on the start's day collapsed a multi-day span the moment one of its times was retyped. Both fields always show; hiding the only control that reaches a state is worse than printing the same day twice.
- **Arc labels live _inside_ the stroke, and that is geometry, not taste.** `LANE_STEP - ARC_WIDTH` = 13 units of black between two lanes, and the hour numerals come down to 333 just outside the first, so a label _beside_ an arc works on the outermost lane and nowhere else. Inside the 14-unit stroke it is 11px of mono with 3.1 units of arc either side of it, identically on every lane, and it costs no radius — which is the "do not add a ring" rule again. It is also `inkOn(color)`, black on the event's own pastel at ~10:1, the strongest pairing this face has; grey on black beside the arc would be the weakest.
- **The label's budget is glyphs measured against the _paint_, never minutes and never the centre line.** `arcLabel` takes the arc's painted ends — the span less any seam a neighbour claimed — because the round caps put half a stroke back past `head`/`tail`, and a label handed the `capInset`-shortened span forfeits 14 units on every arc, which is every half-hour event on the face going anonymous (it did). Mono means the width is arithmetic: no `getComputedTextLength`, so no layout read per arc per frame of a drag. Where the gate lands in minutes is a _consequence_ — a word from about 45 minutes, a stub from about 30 out at the rim, nothing on the inner lanes — so a duration threshold would label an event at the rim and crop the same event two lanes in.
- **A glyph takes its up-vector from the path's direction, so the bottom half is drawn backwards.** `arcPath` grew a `back` flag: the same arc traced anticlockwise from `to` to `from`, which is invisible on a stroke and the whole difference between a readable label and an upside-down one. `arcLabel` reverses whenever the arc's midpoint is between 90° and 270°; the flip has to land somewhere and at three and nine o'clock the text is vertical either way. Derived from the _drawn_ angle, so both faces get it for free.
- **The label keeps full alpha on a dimmed arc.** Ink here is the _absence_ of light, so dimming it alongside the body takes both towards the black behind them and the name disappears at ~1.5:1. Left alone it softens from about 10:1 to 4.8:1 as the arc recedes, which is the hierarchy the dimming was asking for. In `hover` mode it is mounted at `opacity: 0` rather than mounted on hover: it arrives in the same beat the stroke grows by 3, and text popping in on a growing arc reads as a wobble.
- **`Escape` abandons gesture in flight**, from `useHotkeys` inside `Dial` rather than shell's: `setDraw(null)` and `setAdjust(null)`. Drag = one thing here you can start by accident, and before this only way out was to let go, which committed it. Pointer stays captured on purpose — both move and up handlers bail on missing gesture, so release that follows does nothing, no cue because nothing happened.
- **Lane packing face-independent.** `dayAgenda` takes no `Clock`: both faces put one day on one revolution, so two events collide on screen exactly when they collide in time.
- **`CalEvent.color` = override, not the colour.** Empty string means "follow the calendar", default every event should stay on, so recolouring calendar still moves them. Only `colorOf` knows precedence.
- **A task is an explicit `CalEvent.task`, never "`end === start`, therefore a task".** A degenerate span is an arithmetic coincidence and typing data by one is how a five-minute event dragged to nothing silently becomes a to-do. The flag comes _with_ `end === start`, though, which is what makes the rest free: the dial's existing sub-cap dot-collapse already draws a pip at the right minute, `freeGaps` drops a zero-width block on its own, and `dayLoad` sums nothing. Two things did need a line each — `occurrencesOn` measures the day-overlap against `Math.max(duration, 1)`, or a task at exactly midnight is thrown away by an exclusive `end`; and `packLanes` returns a task untouched, so a pip neither buries nor is buried by the meeting it happens during. **Undated tasks are deliberately not modelled**: a list with no day on it is a different product wearing this one as a skin.
- **`doneKeys` is a list of `instantKey`s, for the reason `exdates` is one.** A repeating task is ticked one occurrence at a time, and a boolean on the series would tick every Monday at once. Always the datetime form — the day-only form `exdates` also carries exists because EXDATE has two RFC value types, and nothing outside this app writes these. `Occurrence.done` is resolved once in `occurrencesOn`, because `dayAgenda` is the one read path onto a day and a list lookup is not a renderer's job. **A tick asks no `EditScope` question**: per-occurrence is the only thing it could mean.
- **Filled while it stands, hollow once it is done — on every surface.** The pip on the rim and the tick target in the interior are the same two shapes, so the mark you press and the mark you see on the face are one mark. That is the opposite of the checkbox convention and it is deliberate: on this face ink is _light_, so an emptied pip reads as spent. What keeps it unambiguous in the list is that the strike through the name is the primary signal there and the pip is only the control. **`CenterPanel`'s row is therefore a `div` with two buttons**, not one button — a control inside a control is not a thing HTML has.
- **A task's readout is one instant, not a span.** `peekedTask` splits out of `peeked` so pointing at one prints `01:15 DUE` rather than `01:15 – 01:15 · 0m`, which is three ways of saying nothing. It still shrinks the clock (`aside`, not `span`), because the readout is answering about something other than now and that is what the size change means.
- **A task's ICS is a VEVENT with no DTEND, plus `X-CIRCAL-TASK`.** §3.6.1 requires DTEND to be strictly later than DTSTART and the same section says a DATE-TIME DTSTART on its own ends when it starts — so the spec-legal spelling of a zero-length event is to omit the property. `buildEvent` reads the flag _before_ it computes `end`, because the hour-long fallback for a missing DTEND has to stay for everybody else's VEVENTs: reading _those_ as zero-length would collapse every unterminated meeting onto the rim. A VTODO would have been the other option and it is worse — circal models the half of VTODO that has a day and a minute, and a consumer that ignores the `X-` lines still shows a task at the right time on the right day.
- **`readEvent` lets `end === start` through only for a task.** Everything else with no width is a corrupt record — it draws as an arc of the whole day or as nothing — so the guard is `task ? end < start : end <= start` rather than a blanket loosening.
- **Reminders never catch up, and the window is one minute wide because of it.** `dueReminders` fires only what comes due in `[target, target + 60_000)`; a notification for a meeting that started an hour ago (tab asleep, lid shut) is worse than none, which is why the test is "due this minute" rather than "not yet fired". It also **floors `now` to its minute**: `useNow` fires a few milliseconds _after_ `:00`, and an unfloored window starts at `10:17:00.09` and misses every event sitting exactly on `10:17:00.000`, which is all of them. All-day occurrences never fire (no minute to count down to), tasks do (a to-do with a time is the thing most worth a nudge), and a ticked one does not.
- **`Notification.requestPermission()` is called from the settings switch and nowhere else.** Chrome and Safari only honour it inside a user gesture, and `useReminders` runs off a timer — so the hook checks `permission === "granted"` and otherwise does nothing at all. The switch only goes _on_ if the answer came back granted, or the panel would be showing a promise the browser will not keep. The reminder's `tag` is the occurrence key, so the platform collapses a duplicate; `fired` is the in-memory belt for the same reason, since React invokes an effect twice in development.
- **`Settings` schema-versioned.** `SCHEMA` in `src/lib/store.ts` bumped when stored value changes _meaning_ rather than shape (went to `2` when `clock: "24h"` stopped meaning noon-at-top face). Stale schema resets settings to defaults, keeps events.
- **One validator, three readers.** `recur.ts` owns what a legal rule is — the RFC range tables and `readRecurrence`, unknown → `Recurrence`. `backup.readRecurrence` (untrusted JSON), `store.hydrateEvents` (fields a blob predates) and `ics.readRecurrence` (RRULE strings) have three different _jobs_ and share those rules; they used to each decide for themselves, and disagreed — backup clamped `interval` at 999 where ics had no ceiling and the store range-checked nothing. Two consequences worth keeping: **the exdate/rdate lists are read before the frequency**, because an RDATE-only series is real (`repeats()` says so) and a bare `NEVER` for `repeat: "never"` is how a `.json` round trip used to lose every date a producer named; and `hydrateEvents` keeps its identity fast path, so it asks about _shape_ and only hands the rule over when the shape is wrong.
- **`MOD`, in `ui/primitives.tsx`, is the only place a modifier is spelled.** `useHotkeys` has always accepted `metaKey || ctrlKey`, so the chips were the one Mac-only part of the app. Read from the platform at module scope — the island is `client:only`, so nothing can disagree — and only ⌘ is translated: ⇧, ↵ and ⌫ are printed on the keys themselves, and `Ctrl Shift N` across four segments costs the top bar something else. It is 40px against ⌘'s 18, which makes the left group 67px wider, so **`TopBar`'s two measured thresholds are a pair** (readout 1220/1450, wordmark 1430/1660) written as whole class strings — Tailwind reads the file as text, and a class it cannot see is a class it does not emit. Anything joining that group re-measures both, on both spellings.
- **Settings is a near-full-screen overlay flowing balanced columns, not a 420px scroll.** `columns-[320px]` on the scroll area, each `Section` a card with `break-inside-avoid`, so a new group spends width before it spends scroll — the panel only ever grows, and a setting below the fold is a setting nobody finds. Consequences: a column is 320px, so every inline row inside a `FieldRow` must `flex-wrap` (a two-toggle row overflows a card at phone width otherwise), and the last row of each section takes `last` because the card's own border is the boundary.
- **`.label` is a label voice; a sentence uses `.caption`.** 11px mono uppercase at 0.18em tracking is legible as three words and hostile as prose, and `text-ink-3` is ~3.1:1 on black (`ink-4` ~1.5:1 — decorative only, never text). `.caption` is 12px sans at `ink-2`; add `tabular-nums` where it prints a time or a count. Inline spans that _name_ a control beside it stay `.label text-ink-3` — they sit at the same weight as the row label above them, and mixing the two voices inside one row reads as a row that has come apart.
- **Store hydration lazy, at first `subscribe`**, not module scope; `load()` and `write()` swallow `localStorage` errors on purpose (private mode / quota must not brick app) — but both then call `notify(…, "error")`, because a silent failure is indistinguishable from success and that is how a day's events disappear. `load()`'s case is the sharper one: it starts the app **empty**, which is exactly what a first run looks like, so the notice is the only thing telling the two apart. `readFeeds` is the one catch that stays silent, and says why: a corrupt payload is a cache miss the next pull replaces.
- **Every action derives from `fresh()`, never from module's `snapshot`.** `fresh()` re-reads blob when another tab wrote since we last looked. Deriving from in-memory snapshot loses other tab's events wholesale in window before its `storage` event arrives.
- **Undo in-memory and session-scoped**, cleared on an inbound `storage` event _only when the base actually moved_: undoing onto a base another tab moved past would resurrect what it just deleted, but a background tab's **feed pull** writes the same key and used to cost the foreground tab all sixty steps — a loss the user cannot attribute to anything they did. `baseSignature()` is the comparison (events + calendars minus their `feed` + settings); `undo`/`redo` also carry today's `feeds` across rather than restoring the recorded ones, because a feed is a live mirror and never part of an undo step. `commit(next, false)` opts a change out of history — settings and feed pulls do.
- **A feed payload never shares the blob.** One `circal.feed.<id>` key each, budgeted: `FEED_BUDGET` (2M stored characters) split equally between the subscriptions, re-divided on every pull. Inside `circal.v1` a mirrored calendar is unbounded and competes with your own events for one ~5MB origin quota, so one fat subscription made every later save fail — quota is per origin, which is also why the cap is a shared total and not "1MB each" five times over. Over budget, `trimFeed` keeps recurring events first (a rule is bytes that describe years) then nearest today, and the calendar's meta line says `1,228/4,000 cached`; a refused `setItem` drops the key and says `Not cached — no room`. Both messages are under twenty characters because that line is one `.label` wide and truncates. Migration out of a legacy inline `feeds` field runs in `hydrate()` — shared by `load()` and `fresh()` because either can be first to see a blob — and rewrites the blob immediately, so it happens once. Deliberately **not** a `SCHEMA` bump: a bump resets settings, and where a payload is stored is not something a setting means.
- **`feedCache` is not an optimisation you can drop.** `fresh()` runs on every action and re-reads every feed key; without the id → `{ raw, events }` map, a single 300-event subscription re-parses on every nudge of an arc. It is also what makes `sameFeeds` able to tell a real change from a re-read, which is what stops `fresh()` handing React a new snapshot for nothing.
- **`seed()` only runs when no stored blob exists**, anchors on today's local midnight.
- **A VEVENT with no UID gets a _derived_ one, never a generated one.** `derivedUid()` in `ics.ts` is FNV-1a over DTSTART/DTEND/SUMMARY/LOCATION/RECURRENCE-ID, formatted `<base36>@circal.local`. It was `crypto.randomUUID()`, which meant a new id on every parse: `feeds.ts` builds each event's key from the uid, so every pull remounted every arc and hover, selection and the arc under the pointer all dropped. UID is required by RFC 5545, so this only fires on a feed nobody can fix.
- **`zonedToUtc` brackets the wall time with two candidate offsets** — the one in force a day before and a day after — and takes the pre-transition one when neither or both read back. That resolves a spring-forward gap to the instant _after_ it and a fall-back ambiguity to the _first_ of the two, in every zone. The earlier two-pass version converged from the naive UTC reading, so which side of a gap it landed on depended on the sign of the offset: Berlin was right and Los Angeles was an hour early.
- **The all-day toggle remembers the times it had, and never the span.** `timedSpan` in `EventEditor.tsx` is a ref holding `{ startMin, endMin }`, captured on the way into all-day and reapplied to the current first and last day on the way out; without it, off → on → off reset every event to 9–10am and silently discarded times the user had set. Two clock times rather than a duration, because the span in _days_ belongs to the Date row now and a stored duration would overrule it — and the toggle itself carries the span across (`end: addDays(lastDay, 1)`), since flipping a switch must not delete four days of a five-day trip.
- **`<input type="time">` banned here** — renders in _browser's_ UI locale, not app's. Use `TimeField` in `EventEditor.tsx`, backed by `parseClock` (accepts `10:45 AM`, `10:45am`, `1045`, `9p`, `13:00`).
- **Quick-add reads the sentence right to left.** `parseQuickAdd` in `lib/quickadd.ts` peels a duration, then a time or dash-range, then a date off the _end_ of the line; whatever is left is the title, because the title is the only free-text field and always the prefix. Order between the parts therefore does not matter — `lunch 1pm tomorrow 45m` = `lunch tomorrow 1pm 45m`. Duration is attempted before time (`1h30` = 90 minutes, `130` = 01:30 — only the unit tells them apart) and date last, so a bare number _in a sentence_ is an hour rather than a day of the month. A range carries a dash and only a dash: `to` appears in titles ("go to gym") far more often than in times, and a parser that ate it would eat the title.
- **`parseQuickAdd` returns `null` unless the line names more than a title, and it invents nothing.** A bare word is a search and a bare date is a jump — the palette already answers both, and that rule is the whole reason a create row does not appear under every query in the app. A day with no time is an **all-day** event, because that is what was said; a duration with no start takes `defaultStart` (next quarter hour on today, 9:00 on any other day), which is ⌘N's own rule, imported rather than copied. It creates and closes with no review step, so the row prints the resolved span before you press Enter.
- **The palette's whole-query parsers live in `lib/quickadd.ts` and split three ways.** `parseDate` (jump), `parseSlot` (the free-time search — the only form in which a bare number means minutes) and `parseDurationToken` (unit required, what the scanner uses). They were private to `CommandPalette.tsx` and untested, which is exactly why composing them into a sentence was not the "wiring" it looked like.
- **A repeat is claimed before the date, and always carries a word of its own.** `parseRepeat` reads `daily` / `every 2 weeks` / `every other friday` / `weekdays` / `every mon/wed/fri`, and the scanner tries it _first_ on each pass: `every friday` ends in a weekday, so a date matcher reaching it first would take the weekday, leave `every` in the title and produce an event that happens once. The converse rule is why a bare weekday is never a rule — `party friday` is one party, and reading it as fifty-two is the worst mistake this parser could make.
- **A weekday rule moves the first instance onto a day the rule generates.** `gym every monday` typed on a Wednesday starts on the Monday. Without it the seed is a day the rule skips, so the arc you just made vanishes off the face as it saves — `daysOfPeriod` generates from the rule, not from the seed. Only when no date was named: an explicit `2026-09-14` is an instruction and outranks the tidying.
- **`RepeatSpec` carries only what the editor can spell** — frequency, interval, `byDay`. No `until`: an end date would have to eat a _second_ date out of the same line and nothing in the sentence says which of the two is the last one. A rule typed in the palette is therefore always a rule you can still edit afterwards.
- **`in` is the switch between a length and an offset, so it is deliberately not in `FILLER`.** `dinner 2h` is a two-hour dinner; `dinner in 2h` starts two hours from now. Sweeping `in` up as a connector — the obvious tidy-up, since the word was being stranded in the title — leaves the length reading in place and _removes the evidence_: a two-hour dinner at the default hour, with no `in` left to explain why. `parseOffset` is claimed before the duration matcher for the same reason, or `2h` is taken out from under it.
- **Everything after `in` is the offset, greedily, and a length goes in front of the name.** `in 1h 30m` is ninety minutes from now — reading it as "in an hour, lasting thirty minutes" is the trap, because that spelling of ninety minutes is completely normal. So both together is `45min dinner in 1h`, which is why `parseQuickAdd` also claims a **leading** duration, from the left, after the right-to-left pass (a trailing one still wins, and the title is never left empty). `in` in front of anything that is not a duration stays a word: `dinner in Rome`, `coffee in a bit`.
- **An offset names a clock; a date still names the day.** `dinner tomorrow in 2h` is tomorrow at now-plus-two-hours: `fromNow` sets the day only when nothing else did, and a named day keeps its date while `fromNow % MINUTES_PER_DAY` supplies the minutes. Unnamed, the offset rolls the day itself — 23:20 plus two hours is tomorrow at 01:15 — and an explicit clock time outranks an offset, because a line carrying both was edited half way.
- **An offset lands on the quarter hour** (`snap(minutesOfDay(now) + offset, 15)`), nearest rather than next, which is also what makes `now` mean the quarter you are _in_: at 10:07 the next one is eight minutes away and "in eight minutes" is not now. Every machine-chosen time in this app sits on the dial's own grid — `defaultStart` does, a drag does — and 19:07 on a 15-minute face reads as an accident.
- **The palette ranks with `fuzzyScore`; it does not filter with `includes`.** Letters must appear in order but not adjacently (`dsgn rev` finds "Design review"), and **one** query character is forgiven from four characters up — which covers a wrong letter and a transposition alike, since both leave a clean subsequence once the offender is dropped. Sort is score first, then the old nearness-to-the-day tiebreak; an empty query scores everything `0`, so the list's own order survives. Command rows keep their hand-written order until there is a query, because "New event first, calendars last" _is_ the answer to an empty box.
- **Two things in `fuzzy.ts` are corrections, not decoration.** The run bonus _rises_ through a run (`RUN * n`), because flat it scored three adjacent letters the same as three word-initials and `run` ranked "Roll up now" over "Morning run" — a whole word is not an initialism. And the scan restarts from every word start, because greedy alone lets the first letter take the earliest place it fits: `run` matched the `r` inside "Morning" and then had to reach for the rest. Both are cheaper than a dynamic program over every candidate on every keystroke, which is what the eight rows on screen do not justify. A hit outside the title is charged a **penalty** (`FIELD_PENALTY` in `CommandPalette.tsx`), never a multiplier — a score can be negative, and halving a negative promotes it.
- **No `backdrop-filter` on element also carrying `.fade-y`** — Chromium paints blur over box far larger than element, appears as grey rectangle mid-dial (see comment in `CenterPanel.tsx`).
- **Your lightcycle band replaces elapsed ring; does not join it.** Both live on `DIAL.TRACK` at `DIAL.TRACK_WIDTH`, and `elapsedSegments` returns `[]` whenever band has half left to draw (`place && (daylight || moonlight)`, computed once as `band`). Second band on own radius _next to_ track was first attempt, read as one line accidentally doubled. Deliberately no `DIAL.SUN`.
- **Second zone's band = different place, so it does get own rim.** `DIAL.ZONE_BAND` (424) sits 21 units outside track, 13 inside zone numerals it belongs to, and `SunBand` takes `radius` for exactly this. Halves = `zoneDaylight` / `zoneMoonlight` — independent of yours, because point of ring is comparing two places, comparing them half-drawn not a comparison. Coordinates come from `placeForZone(secondZone)`, resolved in `App.tsx`; `null` (`UTC`, aliases like `Asia/Calcutta`) means no band, no switches offered.
- **Lightcycle bands = one sanctioned break in "chrome is greyscale".** They data about the day, not chrome, so warm-but-desaturated for day, dim violet for night, neither may compete with event arc. Use same opaque-segment technique as ring they replace, same alpha-compounding reason.
- **`light(m)` in `SunBand` must stay continuous through zero.** Returns signed light — positive sun, negative night — and civil-twilight shoulders reach exactly `0` at horizon so warm band and violet band meet without either starting on step. Every discontinuity in that function = visible edge on rim; shoulders used to begin at `0.04` and band began with hard line. 288 segments (five minutes each, eight-unit chord) makes ramp stop looking stepped.
- **Two halves = draw-time filter, not argument to `light`.** Curve computed for whole day either way, segment loop drops half switched off, so half that stays keeps exact shape it had beside other. Yours default on, because band _is_ track; with both off elapsed ring comes back rather than leaving rim empty. Second zone's default off — caption annotates ring already there, band is another ring. `night` = old name for `moonlight`: `migrateSettings()` in `store.ts` carries stored one across, `readSettings()` in `backup.ts` does same for backup.
- **`DIAL.ZONE` (446) fixes `PAD` (30).** Crop leaves 470 units of radius; 15-unit numeral centred on `ZONE` reaches 453, caption beside topmost one runs up to 131 units further right — eight units short of crop at worst anchor angle. Anything further out gets cropped: move `PAD` before you move `ZONE`, keep `ZONE_BAND` _inside_ `ZONE`, because caption runs horizontally outwards from numeral and would otherwise cross band.
- **Zone caption hangs off topmost of four marks**, to its right, never beneath. Beneath, collided with hour numeral below it and ran off viewBox at three o'clock. Four marks 90° apart, so one always within 45° of top, where horizontal room is.
- **Zone ring measured against viewer, never against UTC.** `delta = zoneOffset(now, zone) + now.getTimezoneOffset()` — caption reads `Tokyo +7`, because you are origin of this dial and "GMT+9" makes reader do subtraction. Also only form staying right in weeks when one of two zones changed for DST and other has not.
- **Read-only events = `disabled` fieldset**, not prop threaded through every control. Cascades to swatch buttons and `Select`s nested two components deep, which nothing else would reach. Title input sits outside it, carries own `disabled`.
- **A calendar may be made, renamed, recoloured and deleted, and deleting one keeps its events.** `store.removeCalendar` _moves_ the user's own events to the first calendar still standing and returns `{ into, moved }` so the toast can say where they went — a calendar is a label, and deleting a label is not a way to ask for a year of appointments. Two invariants make that always possible: the last calendar that is _not_ a feed cannot go (return `null`; the card disables its verb and says why), and a feed's payload lives in `feeds` so removing a subscription is still a wholesale drop. `App.calendarRemoval` mirrors the same rule so the verb is disabled rather than failing — if you change one, change both.
- **A mark is one field in two vocabularies, told apart by alphabet.** `Calendar.icon` and `CalEvent.icon` are each a Phosphor name (`[a-z0-9-]+`) or a literal emoji, and `isIconName` is the whole discriminator — no prefix, so the stored value reads as itself in a backup and in devtools. `""` is the plain colour dot on a calendar and "no mark" on an event, **and so is a name this build does not carry**: `CalendarMark` falls through rather than rendering nothing, and neither `readCalendar`/`readEvent` nor the hydrators drop an unknown name, because a backup that has been through an older build must not come back with the mark missing. `firstGrapheme` is what keeps a flag, a skin tone or a ZWJ family one character — `[...s][0]` gets all three wrong.
- **`markOf` is deliberately not `colorOf`, and its third argument is why.** Colour _must_ inherit: every event needs one, so `CalEvent.color` is an override on a required field. A mark is optional at both levels, and a face where forty arcs have all picked up the same three glyphs says nothing the colour was not already saying — so `markOf(event, calendars, inherit = false)` returns the event's own and stops there unless asked. The argument is `settings.inheritMarks`, which is **off**; on, a calendar's mark becomes a default its events take, which is the useful reading for one-calendar-per-kind-of-thing. The default on the parameter matches the default on the setting, so a caller that forgets gets the conservative answer.
- **Shape and colour are read apart.** `CalendarMark` takes whatever colour the caller resolved — `calendar.color` where a calendar is named, `colorOf(event, calendars)` where an event is — so an event can borrow its calendar's glyph and still wear its own colour, and neither answer implies the other. Two deliberate abstentions: the event editor's _header_ dot is the event's colour swatch and gets no mark, and **`CenterPanel` has none at all** — its dot is `4.5–5.5 × u`, which is about five pixels, and a glyph there is a smudge while a legible one would widen every row's leading slot inside a panel whose corner has 29 units of clearance to `HAND_INNER`.
- **A mark on an arc costs two glyphs of the label's budget, and never the name.** `arcLabel` takes the mark, prices it at `ARC_MARK_GLYPHS`, and rides it along **only** when what is left still clears `ARC_LABEL_MIN` on its own — a tight arc drops the glyph and keeps the word, because a symbol shared with everything on one calendar is worth less than the last two characters of a name. The pair is centred as a unit: `startOffset` pushes the text out by half the mark's slot, the glyph sits at the _start_ of that slot so all the slack lands between it and the first letter, and both flip through the bottom half with the path. `MarkGlyph` is the SVG-native renderer for exactly this — `CalendarMark` answers a `<span>` for an emoji and a dot for nothing, and neither is legal inside an `<svg>` or wanted on an arc that already carries its colour.
- **247 icons, and the number is measured.** All 1,512 Phosphor bold paths are 621 KB raw / **206 KB gzipped** — more than the entire rest of the app — so "just ship them all" is a picker that costs more than the product. These 247 are 118 KB / 43 (37 brotli), they are the fifth of the library a calendar ever wants, and the emoji field covers the long tail at zero bytes and in colour. If the set ever must be complete, the only honest shape is a lazy chunk _plus_ an eager core: a mark has to render on the first frame of a cold load, and a dot that pops into an icon half a second later is worse than a smaller set.
- **The paths are vendored, and that is not an optimisation.** `@phosphor-icons/react` ships every icon as a component carrying all six weights inline — four times the weight of the one this app draws. Bold only, as data, is the whole library's worth of choice at none of the price. Measure before adding an icon library here; the number is the argument, not the taste. To add a mark, copy the `bold` entry out of `@phosphor-icons/react/dist/defs/<Name>.es.js`; the viewBox is 256 units and the paths are unmodified MIT.
- **One `MarkPicker`, and `noneLabel` is the only thing the two callers differ on.** The calendar card and the event editor ask the same question and `""` is the same empty string in both — it just stands for "a plain colour dot" on one and "follow the calendar" on the other. Search matches on bare letters (hyphens and spaces stripped from both sides), so `first aid`, `firstaid` and `aid` all find `first-aid`; `fuzzyScore` is deliberately not used, because its subsequence match is tuned for command titles and ranks `bird` over `barbell` for `b`.
- **The mark grid has no fade, and that is a rule about what a fade is for.** A fade says "the list continues", and it pays for that hint by dimming its own last row. Good trade over prose or an agenda, where a half-legible row is still placed by the ones above it; bad trade over a grid of glyphs, where the dimmed row is precisely what you are trying to compare. Tracking scroll position so the fade lifted at the bottom was the first fix and it solved the wrong problem — it was wrong in the middle too — so the hook that did it is gone with it. Search is the real answer to a list of 247. `.fade-b` survives on `CenterPanel`, gated on row count, where it sits over text.
- **The calendar card is a `CalendarEditor`, opened from two places and owned by neither.** The sidebar's pencil and ⌘P's `New calendar…` / `Edit …` rows both go through `actions.newCalendar` / `actions.editCalendar`; the shell holds `{ id }` and resolves the `Calendar` from the store every render, so a rename from another tab updates the card and a deletion closes it. The palette rows are not decoration: the pencil is a pointer affordance and the sidebar is not on screen at all on a phone.
- **The sidebar is `inert` when closed, not `aria-hidden`.** It is held mounted for 180 ms while it leaves, and `aria-hidden` over live tab stops is a keyboard user tabbing into controls nobody can see. `inert` takes the focus and the accessibility tree together, which is the one thing "this column is closed" actually means.
- **`push` against `drawer` is measured, not a breakpoint.** The dial is height-bound on any stage wider than it is tall, so taking `SIDEBAR_W` off the width there costs the instrument _nothing_ — the face does not even shrink. The moment the stage would become width-bound, every pixel the column takes comes out of the face, and `rowWidth - SIDEBAR_W < rowHeight` is that condition. It is not "is this a phone": an iPad in portrait is 1024 wide and still cannot afford it, and a half-screen desktop window flips over exactly where it starts to hurt. Measured on the **row**, never on `main` — `main` is already the pushed width, so asking it would shrink the stage, flip to drawer, un-shrink, and oscillate. The pre-measurement frame is invisible because the sidebar starts closed.
- **The drawer lives inside the row, under the top bar, and that is why it has no close button.** The button that opened it is still on screen and still reachable, so a header of its own would be a second verb for one action. It is modal in effect — it covers the whole face — so it takes `role="dialog"`, a focus trap and `tabIndex={-1}` for the trap to land on, and Escape. It is **not** in `busy`: `busy` gates the hotkeys because ← under an open editor steps the day out from under unsaved work, and a drawer has no unsaved work. `shaded` is the other question — "is the instrument reachable" — and that is what the ambient timer and the dial's ⌘⌫ ask.
- **The mini-month's dot row is always mounted, empty or not.** Rendered only when a day carried something, the cell's `flex-col` re-centred and the numeral rose by half a dot on exactly the days that had events — so the month read as a ragged line and the shift, not the dots, was the loudest thing in the grid. `h-[3px]` unconditionally. Any cell whose contents are conditional has this bug waiting in it.
- **The sidebar has no agenda, and that was a decision rather than a tidy-up.** The column printed the selected day's occurrences two hundred pixels from the dial's interior printing the same ones, which is the same fact twice and it was the fact this 260px column had least room for. What is left is what the interior cannot do: navigate to a day (the mini-month), manage the calendars, and one complication. If an agenda ever comes back it needs an argument the interior does not already answer.
- **The moon lives in the sidebar, and it is the one thing here that draws something the calendar does not contain.** Not on the face: every radius the dial gains costs `PAD` and legibility, and unlike the lightcycle band the moon is not a fact about the _day_. It reads the _selected_ day, which is what earns it — arrowing through a week walks the moon through its week. `moonPhase: "off"` by default, because chrome does not appear unasked.
- **`Aperture`'s bites are exactly the moon's own radius, and that equality is the whole mechanism.** A disc occulted by an equal disc leaves a lune, which is the shape a crescent moon is; an end that merely tapers to a point cuts a _wedge_, which is not. It follows that the journey is `4r` end to end. The bites clip the **disc only** — never the sky — so the slot is free to be whatever shape reads best; punching them out of the window itself was the first version and it made the ends two moon-sized scoops that read as machinery. And the disc is driven by `apStandoff(illumination)` rather than linearly in phase: linear is what real complications do and it is why they show a crescent close to twice as full as the sky's, which is forgivable on a wrist and not two centimetres from a caption printing the true figure.
- **`light(m)`'s rule again, for the moon: `Minimal` draws the terminator as an ellipse of `rx = r|1 − 2k|` over the lit half**, filled with the sky below half and with the moon above it. `k = 0.5` collapses it to nothing, which is exactly the straight edge a quarter moon has — so the one function covers all eight phases with no branch per phase.
- **The shell's hotkeys are two registrations, split on `busy`.** Escape is always live — it belongs to whatever is on top — and everything else is off while a panel is up: ← stepping the day under an open editor is the same bug as ⌘Z undoing behind one, and "is the user typing" does not catch it, because focus on a button inside a dialog is not typing. A panel that wants one of those keys keeps it for itself: the palette closes on its own ⌘P, since the shell's copy is off while it is open.
- **Escape's order is panel → life run → drawer → lit grid → ambient, and the life run is in the shell for exactly that reason.** `useHotkeys` fires every registration; there is no precedence between them. So the year ring can keep its own `setSpan(null)` — nothing else on the shell's list is live in that view — but a run drawn across a **lit** life grid is the natural way to use the field, and a local handler there would abandon the drag and clear the thread in one press, which is the two-things-per-key bug this list already argues against. Hence `LifeViewProps.draw`/`onDraw`: `App` holds the run, so it can put it at the front of the queue. The field's own handlers then bail on `!draw` — the dial's "both handlers bail on missing gesture" rule — so a pointer still down and still moving cannot re-arm what Escape just dropped, and `Field` clears the run on unmount for the reason `Dial` clears its preview.
- **`useFocusTrap` finds the opener by `[role=dialog]`, not by its own ref.** React commits a child's `autoFocus` _before_ it attaches the parent's ref, so a ref-based "is this focus inside me" test recorded the dialog's own first field as the thing that opened it, and Escape restored focus to a detached node. One document `focusin` listener for every trap, refcounted, for the same ordering reason: a dialog mounted only while open (the editor) does not exist when the button that opens it takes focus.
- **A trap's restore runs from a passive cleanup, by which time the dialog's nodes are gone** and focus has fallen to `body`. So restore fires on `body`-or-still-inside and checks `isConnected` — anything else moved focus deliberately and knows better than the trap does.
- **`sun.ts` returns minutes since local midnight, does not clip.** Place far from viewer legitimately produces negative sunrise or sunset past 1440; `Face.tsx` samples inside `[0, 1440]`, lets rest fall off face.
- **Place chosen by city, never typed.** `settings.place` carries IANA zone it was picked by, and `placeForZone` = only thing turning zone into coordinates — so picker can always show what band is drawing. `store.parse()` drops stored place with no `zone`: band settings panel says is off is worse than no band. Coordinates come from `zone.tab`, so they name zone's principal city; couple of minutes of sunrise error at worst, finer than band draws.
- **Icons and `og.png` = only unhashed assets, so `CACHE` in `sw.js` ships them.** Everything Astro builds content-hashed; `public/` not. Worker serves `public/` stale-while-revalidate, so installed client gets _old_ icon one more time after change unless `CACHE` bumped. Bump it in same commit touching an icon.
- **`sw.js` keys a navigation by its own URL, and that is a two-page fix.** It used to `cache.put("/", …)` for _every_ navigation, which was correct while there was one route and wrong the moment there were two: reading `/manifesto/` once overwrote the cached app shell, so the next cold offline launch booted the manifesto instead of the dial. Offline it now tries the requested page first and falls back to `"/"`, so an uncached path still boots something. Adding a third page needs nothing; changing this back needs a very good reason.
- **`icon-192.png`, `icon-512.png`, `apple-touch-icon.png` rasterised from `icon.svg`** — `rsvg-convert -w N -h N public/icon.svg -o public/icon-N.png` — and `public/og.png` (1200×630) rendered in browser, because it sets type in Geist and Geist Mono and no rasteriser here has them: mark at icon's own stroke proportion, `circal` at 104px/500 and `-0.035em`, tagline in mono at 22px/500 uppercase and `0.2em` tracking on `--ink-2`. No build step for any of them; edit SVG, re-render, bump `CACHE`.
- **Favicon's `r=11` / `stroke-width=2.4` chosen at 16px, not by ratio.** That radius puts both stroke edges on whole pixels where circle otherwise smeared across three, and anything thinner antialiases to grey instead of white. Re-render at 16px before changing either.
- **The top bar has three measured breakpoints and a fourth segment moved all of them.** The date readout is absolutely centred on the _bar_, not on the space the two button groups leave, so everything the left group gains comes straight out of the readout's clearance — and the wordmark is what yields, every time, because it is the only thing up there that is identity rather than information. Wordmark gone below **1430px** (1080 at two segments, 1180 at three), readout gone below **1220px** (was 820), and the `‹ Today ›` stepper gone below **480px**, where the three groups stopped fitting a phone at all. The stepper is the right thing to drop because it is the one control with another route to it — the drawer's mini-month, a face in ⌘E, a date typed into ⌘P — where hiding a view or the drawer's own button would cost something with no second way to reach it. All three measured against the longest header `formatDayHeader` produces (`Wednesday · Sep 30`); anything added to that group has to re-measure all three, and the check is a sweep from 360 to 1600 looking for an overflow or a collision, not a spot check at two widths.
- **`lib/feedback.ts` builds its `AudioContext` inside `onPointerDown`, never at module load.** Context made outside user gesture starts `suspended` and stays there, so first drag of session would be silent; also re-`resume()`s on every cue, because backgrounded tab comes back asleep.
- **Every cue = one mechanism: 3 ms noise impulse struck through bandpass resonators, one impulse per hit time.** `SOUNDS` in `feedback.ts` = whole instrument — `step`/`slide` = single hits, `opened`/`created`/`deleted` = same thing hit two or three times 50–100 ms apart, pitch _order_ carrying meaning (up finished, down removed). Earlier draft used oscillators for long cues and they sounded like another app's notification; do not reintroduce tone here. Each hit gets own contact transient scaled by how hard it lands — without one, later hits read as hiss with resonance on it.
- **`level` = gain _into_ narrow resonance, not peak.** Most of a 3 ms impulse's energy never gets through, which is why multi-hit cues carry levels above 1. Offline peaks at the shipped `LEVEL` of 1.35: `step` 0.43, `slide` 0.20, `created` 0.42, `deleted` 0.42 — and `opened` 0.28, which is its `Synth.peak` directly, since `renderVoice` normalises the sum and `LEVEL` never touches a voice. Retune by rendering into `OfflineAudioContext` and measuring — and measure **in a stream**, sixteen clicks at 45–110 ms, which is the only condition a drag cue ever occurs in. One click rendered on its own is not that condition, and the difference is not academic: see the hour detent below.
- **The contact is the sound; the resonance table is colour.** A Q=8 bandpass passes about 1% of a 3 ms noise burst while the `contact` highpass passes nearly all of it, so the click leads its own resonators by **13.6 dB** — the frequencies in `SOUNDS` are a tint, not a tune. Measured proof: `step` and `slide` are an octave apart on every partial and come out 6.9 dB apart in level and **3.6%** apart in spectral centroid. This instrument speaks in level. Anything that needs to be told apart here has to be told apart by how loud it is, or by _when_ it lands.
- **The exciter is seeded (`BURST_SEED` = 43), and that is a bug fix, not tidiness.** The burst is ~130 samples, and a resonator hears only its own passband: at Q=8 and 1950 Hz that is bandwidth × duration ≈ 0.7, so **one degree of freedom** — each resonance is excited by very nearly a single coin toss. `Math.random()` tossed it once per page load, because the buffer is cached for the session, which put 4.2 dB of peak and **30 dB** of tonal balance between one reload and the next: `step` was a dull 1950 Hz knock in one session and a bright 4200 Hz tick in the next, switching only on refresh. 43 is measured rather than chosen — of the first 400 seeds it is the one whose band energy at every resonance in `SOUNDS` sits nearest the ensemble mean of a random draw (within 1.8 dB at both 44.1 and 48 kHz, against a median 4.0 and p90 6.1 for a random session), so it is the burst the table was tuned against, every time. Per-click level repeatability (0.1 dB across a drag) is unchanged; that is what caching was ever for.
- **A drag has one click, and the hour is deliberately not accented.** There were two more cues — `stepHour`/`slideHour`, a deeper notch every fourth step, on the theory that a dial should be countable by ear. Two things killed it. It never worked: the first version accented with timbre and ring length and measured **1.3 dB in a stream** against a click-to-click spread of 0.1 dB, which is a fifth of the way to audible, and it sat there unnoticed for months. And when it was retuned to a genuine 4 dB plus a 14 ms rebound it was still the wrong feature — the centre of the face prints `9:00 – 11:30 · 2h 30m` for the whole gesture, so the accent was a second answer to an answered question, on a channel already firing fifteen times a second. **Do not add it back.** If a drag ever needs a second signal, the readout is the one that already works.
- **Only `gated` cues rate-limited.** `step`/`slide` can fire dozens of times a second and share one `MIN_GAP_MS`; one-shot cues bypass it deliberately, since `opened` lands within milliseconds of a drag's last click, exactly the gap that limit exists to swallow.
- **Keyboard = second instrument, in `lib/keys.ts`, one mechanism all way down: every key = sum of damped sinusoids, no noise anywhere.** That the point — recorded switch = broadband hiss with resonance on it, and screenful of that = fatigue. Voice = `Synth` (`layers`, `length`, `peak`); `render` sums layers and scales _sum_ to `peak`, because two partials add to somewhere between 1.0 and 1.5 depending where phases land and guessing that is how one key ends up twice its neighbours. **No asset, no fetch**: eight buffers rendered on first keystroke of session, at device's own sample rate, in well under a millisecond.
- **Two letter clicks = Radical's, refitted from its bundle** — 2600 → 200 Hz over 8 ms, and steady 2325 Hz, both with 1.4 ms time constant, nothing above 3.5 kHz in either, fitted to spectral correlation of 0.96 against originals. Parameters rather than asset on purpose: exact at any device sample rate, and free. Do not "improve" one by adding noise transient — that precisely the difference between this and a clack.
- **All three big keys were recordings first (Everglide Oreo board) and all three lost.** Space = 1820 → 140 Hz at τ 2.0 ms, letter click lower and longer; it was click over 145 Hz partial ringing 14 ms first, on theory bar needs tail to sound like bar, and tail read as boom next to clicks this dry. Delete starts at 1500 rather than 2600 and glides less far, so reads as duller than letter rather than brighter — taking character away should not sound like typing one; recorded one's _release_ measured 1.8× its press (0.115 against 0.064), exactly why it sounded like key that could not make up its mind. Return lands twice, and once layer could start late that clunk was reachable from parameters, which took last asset out of app.
- **Late layer = how key lands twice, belongs in buffer — never in caller.** `Layer.at` (seconds) offsets contact inside one voice: `render` measures that layer's glide, decay, 0.2 ms attack from its _own_ start. One buffer per voice keeps keystroke one `start()`, and only way gap between two contacts scales with `playbackRate` — scheduled separately, jitter would move pitch and leave gap behind. Return's contacts 9 ms apart; 14 ms was first draft, read as two separate keys.
- **`CLICKS` alternates strictly; never picked at random.** Two-item bag chosen randomly repeats about half the time, and repeated keystroke = one artefact alternation exists to prevent. Radical itself picks randomly, gets away with it only because ±8% of `playbackRate` hides repeat; both kept here, jitter _and_ strict alternation.
- **Levels = one family across both instruments, every key a multiple of `LETTER_PEAK` (0.24)** — just under the dial detent's measured 0.27, because typing happens hundreds of times to a drag's once. Space and Return 1.1×, delete 0.92×; letter release 0.275× its press, space 0.32×, delete 0.30×, Return 0.42× because its let-go is the sound of the thing having happened. Nothing is baked anywhere, so `LETTER_PEAK` moves the whole keyboard and keeps every ratio. The 0.27 it is measured against is `step`'s, which is now the _quiet_ half of the detent pair — the hour's 0.43 is an accent four times a drag, not a working level, and the keyboard is not compared to it.
- **`useTypingSound` listens on `window`, reads `e.code`, not `e.key`.** "Anything being typed" = property of document, not of component, so one pair of listeners covers palette, editor, settings panel, anything added later — no field knows about sound. Physical key makes the noise, so shifted `2` and `@` = one key. Bare modifiers, `⌘`/`Ctrl`/`Alt` combos, `date`/`range`/`checkbox`/`radio` inputs and `SELECT` all silent: select arrowed through rather than typed into, combo = command, which panels announce for themselves. Held-key map cleared on `blur`, because field losing focus mid-hold never sees its `keyup` and stale entry would fire on that key's next press.
- **Auto-repeat makes no sound: `if (e.repeat) return`.** One press = one sound however long finger stays down, both what keyboard physically does and only thing that actually fixes held arrow machine-gunning. Rate-limiting repeats instead was first attempt, failed — 30 ms repeat interval clears any floor short enough to pass fast typist's digraphs, and `MIN_GAP_MS` (18) exists only for those. Verified with 40 trusted `autoRepeat` events: two sounds, press and release.
- **Panel arriving says `opened`, from effect keyed on panel's own flag** (`paletteOpen`, `settingsOpen` in `App.tsx`), not from cue at each call site — four call sites between ⌘P, top bar, and palette handing over to settings, and they would drift. Audio = external system, which is what effect is for. Channels come from ref updated in its own effect, so flipping Sound while panel open does not re-announce it, and `actions` need not depend on them. Refs never written during render in this repo.
- **`onRingMove` and `onArcMove` bail when snapped minute has not changed.** That makes clicks countable — one per fifteen-minute step rather than one per pointer event — and drops re-render `pointermove` would otherwise cause. `cue()` has own 22 ms floor for same reason, since fast flick crosses steps faster than ear separates them.
- **Arc's drag accumulates `wrapDelta` per pointer event; never measures from grab.** Two ring positions do not say which way round circle pointer went, so delta measured from grab flips sign moment drag passes twelve hours. Summing short hops instead lets drag cross midnight as many times as it likes.
- **Minimum duration clamped on `delta`, not on resulting instant** (`clampDelta` in `Dial.tsx`). Clamp end and overshoot banked: arc then lags by however far pointer ran past limit before it starts following back. Clamp delta and it stops dead, releases instantly — and since sound fires only when delta changes, clamped arc goes quiet, which is feedback saying "this is as short as it gets".
- **Press on arc that never changed delta = click.** `onArcUp` opens editor when `delta === 0`, also whole implementation of read-only arcs: subscription's occurrence gets `grip: "none"`, `clampDelta` pins it to zero, press falls through to opening. No separate `onClick`.
- **⌘⌫ deletes the arc under the pointer, and the key lives in `Dial.tsx`.** The dial owns the hover, so it owns the press — the same argument Escape's gesture-abandon makes. What a delete _means_ is still the shell's: `onDelete(occ)` goes up, a one-off goes straight through `store.remove`, and a repeating one gets the same `ScopeDialog` a drag gets, in danger colour. It is off while `covered` (the shell's `busy`), because the editor has a ⌘⌫ of its own and two handlers on one press delete two different events; it is off mid-gesture, because the drag in flight is about to write to that same arc; and it never fires on a subscription's occurrence. It **always toasts** — the editor's Delete is two deliberate presses inside a modal, this one is a single keystroke, and a destructive key with no receipt is a key nobody presses twice.
- **⌘ held at the grab duplicates instead of moving, and the modifier is read once.** `Adjust.copy` is fixed at `onArcDown`: a ⌘ let go halfway through would turn a duplicate into a move of the thing being copied, which is the one outcome nothing undoes in a single step. Only for `grip === "whole"` — a duplicate is a move of a copy, so an end grip is a resize whatever is held down, and `grip: "none"` means a subscription's arc is never copied either. While copying, `onArcMove` **withholds `onPreview`**: the original has to stay exactly where it is, and the thing that follows the pointer is `copying`, which is the draft's own `FaceGhost` channel in the event's own colour. Nothing is written until the release, and the release asks **no `EditScope` question** — the three scopes exist to say which occurrences an edit reaches, and a duplicate reaches none of them.
- **A duplicate carries the whole event, rule and all, and `duplicateOf` (`store.ts`) is the one place that says what "the whole event" means.** The deltas apply to the event's own instants, which is the reading a plain drag already has, so ⌘-dragging one occurrence of a weekly standup gives back a weekly standup an hour later. Three fields deliberately do not travel: `seriesId`/`seriesKey` name a relationship to another event and two events cannot claim one occurrence, and `doneKeys` are ticks against work done once. Three that _must_ travel **with the shift** rather than beside it: `until` bounds a start, and `exdates`/`rdates` name instants — a series moved an hour later and handed its old keys fires on every day the original skipped. A day-form key is re-emitted as a day, which is what carries a whole-day exclusion across a drag that crossed midnight.
- **⌘P duplicates through the editor, and that asymmetry is the point.** A gesture named a time, so the drag writes and toasts; the palette named none, so an unmodified copy would land exactly under its original and the toast would be the only evidence of it. `actions.duplicateEvent` seeds `setEditor({ id: null, draft })` and commits nothing until Save, so Escape leaves no orphan. It goes to the original's own day first: an editor over a face that cannot show what is being edited is a form.
- **A palette row's second verb is `Row.alt`, on ⌘↵ and on the foot of the panel.** A row can only name one target, so a per-event action has to hang off the event's own row — a `Duplicate …` row of its own would either double the result list or guess which match it meant. ⌘↵ falls through to _nothing_ when the highlighted row has no `alt`, because running the primary instead would make one modifier mean "duplicate" on one row and "open" on the next. The foot is fixed height and always present for the same reason the mini-month's dot row is: a strip that appears would move the list under the pointer.
- **The intro is not a reveal. Every element of the face animates itself, and `introDelay` is the whole schedule.** One rule — an element is delayed by _where this face puts it_ — asked of a tick, an hour, an event arc and a segment of the elapsed ramp alike, so the day assembles in day order because the day **is** the order. There is no timeline object anywhere and nothing has to be kept in step with anything else; a ring added later gets its place for nothing. A first version masked the whole instrument behind a rotating conic gradient, which is one line of CSS and reads as a wipe: nothing has mass, nothing arrives, and the ordering the geometry already contains is thrown away and re-imposed from outside.
- **The delay is an _angle_, not minutes since midnight, and that is what makes it work on both faces.** The hand starts at the top, which is midnight on the 24-hour face and noon on the twelve-hour one. Keyed to the clock, a twelve-hour face begins assembling at the bottom and spends the first half-turn out of step with its own hand — verified by eye, which is the only way this could have been caught.
- **Three CSS classes and `pathLength="1"` carry all of it** (`global.css`). `.intro-draw` and `.intro-arc` normalise the dash arithmetic to the path's own length, so a half-hour tick and a six-hour arc take the same easing and read as one gesture; `.intro-pop` lands what has no length to draw, about `fill-box` so a numeral grows around itself rather than around the dial. `backwards` fill is load-bearing on all three — without it an element is fully drawn for the whole of its own delay, which is every element visible on the first frame. An arc's **group** carries the fade and its **body** carries the draw, because the body's own opacity is `0.42` on a past arc and a keyframe ending at `1` brightens every morning event on the way in and then drops it.
- **The hand is the one part that is not CSS, and it is a rotation of the same `NowHand`** — so when the shell puts `intro` down there is nothing to hand over. It turns once at a constant rate, in step with the assembly because both are linear in `INTRO_SWEEP_MS`, then springs on to the current minute **carrying the turn's velocity**: no seam between a hand travelling at a rate and a hand running out of momentum, and about four degrees of overshoot, which is what stops the whole thing reading as a diagram. Written as SVG's own `rotate(deg cx cy)` **attribute**: `motion`'s `style` route resolves `transform-origin` against the element's own bounding box, which for a spoke is out on the rim, and the hand swung about its own middle and left the face. Same trap `NowHand` documents one level down.
- **`INTRO_MS` carries 950 ms of slack past the settle, and it is not padding.** Dropping `intro` is what takes the rotation off; a spring is still a fraction of a degree from home when its `visualDuration` is up. Measured: 1.6° at 3.0 s, which is four pixels of snap at the rim.
- **`circal.intro` is its own key, and `App` puts `intro` back down after `INTRO_MS`.** Not a setting: a `SCHEMA` bump resets settings, and replaying the arrival at somebody who has used the app for a year is the opposite of an introduction — and nobody chose it, so it is not a preference either. Marked seen the moment it _starts_, because a reload halfway through an animation is not a request to watch it again. The shell drops the flag on a timer because ⌘Y, ⌘L and ⌘E each unmount the dial, and a boolean left true would replay the whole thing on the way back. Off under `prefers-reduced-motion` and **not** marked seen there, so turning the preference off still gets you one; Settings hides `Play again` in that case rather than offering a button that plays nothing.
- **Year ring commits on _release_, and that is what makes a drag possible there.** `onPointerDown` used to call `onSelectDay` and leave for the dial, which left no room for a gesture. Now the press starts a `Span`, and `onUp` reads `sweep === 0` as a click (name the day, go) and anything wider as a range (`onCreateSpan` → an all-day draft). Exactly the dial's arc rule — a press that moved nothing opens rather than writes — and the reason `locate` returns `{ day, onRing }` rather than `null`: a hover needs the radius gate, a captured drag does not, because the angle is the whole question once the ring is in hand.
- **Year sweep clamped to `[-from, days - 1 - from]`, never rolled into the next year.** Rolling would have to commit a day to change the `year` prop, and committing is what leaves this view — the same argument the arrow keys already make. Sweep is accumulated per pointer event with `ringDelta` for the dial's reason: two positions on a ring do not say which way round the pointer went.
- **One notion of "the event about to exist", on both faces: the range under the pointer, else the draft in the open editor.** White and translucent while it is being drawn (there is no colour to show yet), its own colour once the editor has one. The shape is identical across the release _and_ the save — the dial's ghost path is byte-identical to the arc that replaces it — which is what stops either handover looking like the drawing having been thrown away. Drawing the drag and then nothing was the first version, and the range visibly reverted the moment the modal arrived.
- **Each face draws it in its own units, and clipping is the face's own question.** `YearView` takes `{ from, to, color }` in dates and lights those days as days that _carry_ it — `markRadius(count + 1)` in its ink, no white overlay. `Dial` takes instants, because a draft can sit on another day entirely once its date row has been edited: `drafted` clips to the day with `minutesOfDay` at each end rather than elapsed milliseconds (a day is not always 1440 minutes long), returns `null` for a draft that does not reach the day, and 0…1440 for one whose middle covers it. An **all-day draft gets no arc at all**, for the same reason a saved all-day event gets none.
- **No preview for an event that already exists.** `App.pending` is `null` unless `editor.id === null`. An existing event already has its arc and its marks; a second set drawn over them is the same event twice, and once the editor's time rows move it the two disagree on screen. Previewing an _edit_ would mean replacing the arc rather than adding one, which is what `onPreview`/`DragPreview` already does for drags.
- **The editor's live draft rides on `EditorTarget.live`, not on state of its own.** Five fields (`DraftMark`), reported from the one `patch` in `EventEditor` and folded in by `App.trackDraft`, which **returns the same target when none of them moved** — React bails out of an identical state value, so typing a title costs no render, no canvas repaint and no SVG diff. On the target rather than beside it because that is the only lifetime that could be right: a preview outliving its modal is a mark nothing can clear, and there are six `setEditor(null)` sites that would each have had to remember. Readers fall back to `target.draft`, which is the seed and is correct until the first change.
- **`patch` in `EventEditor` merges off the render's own `draft`, not through the updater form.** The shell has to be told the same value the field is about to show, and a prop cannot be called from inside an updater — those must stay pure. Safe because no handler there patches twice in one event; a handler that ever needs to must merge both partials into a single call.
- **`colorOf` takes `Pick<CalEvent, "color" | "calendarId">`.** A draft is not an event yet and has no id; widening the parameter to what the function actually reads is cheaper than minting a fake one, and it keeps colour precedence in exactly one place.
- **A drag on a repeating arc asks the same `EditScope` question the editor does, and nothing is written until it is answered.** `App.adjustOccurrence` holds a `PendingAdjust` (the occurrence and the dial's two minute deltas) and **re-arms `preview`**, because the dial drops its own on pointer-up: without that the arc springs back to where it started and jumps again on the answer, which reads as the gesture having failed. Cancel is then just dropping the preview — there is nothing to undo. `"all"` puts the deltas on the event's own instants (the seed moves, every occurrence follows); `"one"` and `"future"` measure from `occ.start`/`occ.end`, which are the occurrence's real instants and not the clipped ones. A one-off is written on release with no question.
- **The notice after a drag is measured against what was actually written.** The series' own new seed for `"all"`, the occurrence's for the other two. A multi-day event's clipped occurrence notifies either way, deliberately: its visible ends are not the event's instants, so the dial could not step the day itself and an arc leaving the face without a word reads as a deletion.
- **`ScopePrompt.tsx` owns the question; `ScopeChoices` is the shared body.** The editor renders it in its own footer (the edit is already on screen and a modal over a modal is a stack nobody can read); the dial gets `ScopeDialog`, a card that has to print the event and its new span because the gesture is over and the card covers the readout. Two copies of a three-way question drift into two vocabularies. `ScopePrompt.tsx` is in `eslint.config.js`'s `no-autofocus` exemption for the same WAI-ARIA reason the palette and editor are.
- **`src/lib/recur.ts` is somebody else's specification, not this app's idea.** It is RFC 5545 §3.3.10 read down the expand/limit table: a period is expanded into candidate days by the BY\* parts, given a clock, narrowed by BYSETPOS, then bounded. Verified against every worked example in §3.8.5.3. Do not "simplify" a branch without checking that suite again — most of them exist for exactly one example.
- **The seed is an instance only when the rule generates it.** RFC calls DTSTART the first instance but also requires it to be synchronised with the rule; the two readings differ only for a rule that contradicts its own seed. This editor can _write_ that contradiction (deselect the weekday the event is on), and an event that then refuses to leave that day is a bug the user cannot fix. A synchronised rule generates its seed anyway.
- **A rule naming a date some months lack simply does not fire there.** The 31st, 29 February, a fifth Friday — §3.3.10's invalid-instance rule, and the only answer that does not invent a date the sender never wrote.
- **COUNT is walked into `until` on the way in; the model stores one bound.** `countedUntil` in `recur.ts`, called from `ics.ts`. Counting is by the _rule_, before EXDATE — RFC subtracts exceptions from the generated set, so an excluded day still spends one of the count. A count past `WALK_CAP` is read as unbounded on purpose: over-running a bound shows occurrences that should have stopped, guessing one too early deletes them, and only the second loses data.
- **`exdates` and `rdates` are local keys in two forms** — `YYYY-MM-DD` for a whole day, `YYYY-MM-DDTHH:mm:ss` for one instant — which are exactly EXDATE's own two RFC value types. Local, because every other day-identity here is (see `dayKey`).
- **Every entry point is capped.** `MAX_INSTANTS` (512) per call, `WALK_CAP` (2000) periods per COUNT walk. A `SECONDLY` rule names 86,400 instants a day and a feed is not obliged to be reasonable; truncating is visible in a way a frozen tab is not.
- **EXDATE and RDATE are the properties collected as lists.** Both legitimately appear on several lines of one VEVENT, and a flat prop map keeps only the last — a series quietly gaining back every occurrence it was told to skip. Hence `Block { props, exdates, rdates }` in `ics.ts`.
- **RECURRENCE-ID is an override _event_, not a patch on the series.** `seriesId` + `seriesKey` on `CalEvent`; `occurrencesOn` builds the index once per query and skips any generated occurrence an override claims. A separate event because that is what it is — its own time, title, place and colour, possibly on a different day from the one it replaces. `feeds.ts` must give it an id including the recurrence-id, since it shares its parent's UID.
- **`RANGE=THISANDFUTURE` is resolved in `fromIcs`, not in a consumer.** `linkThisAndFuture` runs once every VEVENT has been read and turns the flagged override into the tail of a split series — the same shape `splitRule` and `store.splitSeries` already model, because that is what the range means. It lives there because `feeds.ts` and `backup.ts` each link overrides themselves, and one of them getting it wrong is a series that draws twice. Five things it has to get right, and only three were obvious. Chained splits **fold left**: the second cut is measured against the first cut's tail, since by then that is the series generating the instant. The promoted tail takes `uid#recurrence-id` and drops its `recurrenceId`, or it collides with its parent in both consumers' key maps. Without an RRULE of its own it inherits the parent's rule with `splitRule`'s **partitioned** lists (merged with any of its own), or the days the sender skipped come back. An **ordinary** override past a cut is re-pointed at the tail, exactly as `store.splitSeries` does it — left on the head it suppresses nothing and the day draws both. And a cut landing at or before the series' first instant makes the tail **absorb** the head and keep its uid, which is `effectiveScope`'s "folds `future` into `all`" one layer down.
- **`EditScope` is asked at the press, never offered as standing controls.** Three answers, `"one" | "future" | "all"`, and the scope belongs to the moment of committing rather than to the event: a one-off has one possible meaning and is never asked. `EventEditor` holds a `pending: "save" | "delete"` and swaps its footer for the question — replacing the row of verbs, not stacking above it, because two rows of verbs with one of them inert is a footer that lies. Escape backs out of the question, a second press closes. The three used to be two permanent buttons ("Skip this one", "Only this one") in the editor's body, which asked a repeating event's question of every event that had one and never asked it of Delete at all.
- **"This and all future" is two series, and `splitRule` (`recur.ts`) is the whole decision.** Head takes `until = at - 1` (inclusive, bounds a _start_), or its existing bound when that is earlier — a split cannot extend a series. **The exdate/rdate lists must be partitioned, not copied**: `until` bounds the generated set only, so an RDATE past it still fires and one left on the head fires from both halves, and a future EXDATE not carried over resurrects a day the user had already skipped. `store.splitSeries` is one commit — two would be two ⌘Z presses for one edit, and the state between them is a series that has lost its future — and it **re-points overrides past the cut at the new series**: `seriesKey` still names the instant, so an override left on the head suppresses nothing and the day draws both it and the tail's own arc.
- **Splitting at the series' own first occurrence is "the whole series".** The head would generate nothing, so `effectiveScope` in `App.tsx` folds `future` into `all` there — one live event rather than two, one of them dead.
- **`store.remove` takes the overrides with it** (`e.id !== id && e.seriesId !== id`). An orphaned override is an ordinary event sitting on the day it used to replace, with nothing left to explain it and no surface that can find it.
- **An `Occurrence.key` is `${event.id}@${instantKey(start)}`.** An event can appear more than once on a day now (an hourly rule, a BYHOUR list), so the day alone no longer identifies one.
- **The full recurrence shape is filled in at `store.parse`, not guarded for at every read.** A blob written before it has no `interval`, and `undefined` reaches the maths as `NaN` — a series that fires on no day at all. `hydrateEvents` covers `events` _and_ every `feeds` array, and returns the same object when nothing is missing, because `parse` runs again on every cross-tab write. No `SCHEMA` bump: nothing stored changed meaning.
- **The editor refuses to flatten a rule it cannot spell.** `isExpressible` in `EventEditor.tsx` gates the controls; `describeRule` prints a sentence instead. Snapping BYSETPOS or BYWEEKNO onto the nearest checkbox is how an import quietly becomes a different meeting.
- **Editor's Date row must call `showPicker()` itself.** Row = transparent `input[type=date]` stretched over label, and Chrome and Safari open calendar only from indicator that input is hiding — clicking field opens nothing. `openDatePicker()` in `EventEditor.tsx` wraps call, because it throws outside user gesture and does not exist in every browser rendering the field.
- **Life grid = canvas, and that not an optimisation.** Thirty thousand dots = thirty thousand DOM nodes: mount alone costs best part of a second and nothing can be animated afterwards. `drawField` in `LifeView.tsx` batches field into one `Path2D` per distinct colour, issues one `fill` each, walks one `Date` per year with `setMonth(0, 1 + doy)` — which rolls over, so day 59 = Feb 29 or Mar 1 as that year decides.
- **Field drawn once, into offscreen canvas; visible one only blits it.** That makes reveal affordable: frame of wave = one `drawImage`, one radial gradient in `destination-in`, one arc, about 4 ms, rather than thirty thousand arcs. Both canvases sized by `devicePixelRatio` and drawn in CSS pixels — at half coordinates a two-pixel dot is grey smear. Offscreen canvas filled _before_ handed to its ref, because `react-hooks/immutability` rejects mutating value already living in one.
- **Nothing following pointer drawn on that canvas.** Hover, selection, today's halo = SVG circles in overlay; hover repaint of field would cost every dot. Field rebuilt only for new box, span, density, search, or _day_ — why `LifeView` derives `todayKey` and memoises `today` from it, rather than passing ticking `now` into anything but percentage readout.
- **Today's dot takes its event's colour when it has one.** Drawn outside colour batch (only dot with different radius), and skipping density lookup there was real bug: every event on today — including all-day one, obvious thing to try — was invisible. What marks day as today = accent halo in overlay, not fill.
- **`lifeLayout` picks how many lines a year gets, per box.** Year on one line = 372 columns wide, and in landscape window that makes cell twice as wide as tall: dots merge sideways into dashes. `SPLITS` in `lib/life.ts` tried in order, one leaving biggest dot wins — desktop lands on two lines of 27 weeks, phone on four or six, neither ends up with dots it cannot see. Splits always whole weeks, so week group never cut in half.
- **A year of the life grid = `linesPerYear` rows, columns = real Monday-to-Sunday weeks.** A row is a year only at the one-line split; at the desktop's 27-week split a row is half a year, and on a phone a quarter or a sixth. Column = `jan1Offset(year) + dayOfYear`, so year starts as many blank slots in as its 1 January is deep into its week. That makes any seven adjacent columns a week — also why months cannot be a gap: month not whole number of weeks, so it a tonal band drifting along row instead (`TONE` in `LifeView.tsx`, alternating on `getMonth() % 2`). Band pair is deliberately narrow and was retuned once already: six alternations across fifty-odd columns sits near the dot pitch, so widening the contrast stops reading as months and starts reading as vertical striping down eighty rows. Coarser bands are not the escape either — `SPLITS` cuts a year into one to six lines, so a half-year band _is_ a line at 27 weeks and the striping merely turns horizontal.
- **The grid ends by fading, never by a mark.** Expectancy = guess, and red ring on last day = claim about a date; the last `FADE_DAYS` (7) ramp to black through `smoothstep` instead, event colours included — sole thing allowed to dim a colour, because it the grid running out rather than distance. **A count of days, never a share of the span.** First attempt was a tenth of the life and it was wrong: any share big enough to see is years of it, the last decade goes grey, and the softness stops reading as an edge condition and starts reading as data about your seventies. Seven dots = smallest thing unmistakably a fade and not a ragged row. Ramp quantised to `FADE_STEPS` and every colour built once per (base, step): `dim` mints a string per call and this loop runs thirty thousand times. Greys get own numeric-keyed table since they all but a handful of the dots.
- **`lifeCellAt` = exact inverse of `lifeDotX`/`lifeDotY`** and must stay so, including week gaps and line split. Snaps to nearest dot rather than requiring hit inside one: at four pixels a dot smaller than pointer's own uncertainty.
- **`lifeDensity` counts dated events and yearly repeats, nothing else.** Daily or weekly rule has no end date and fires more often than grid can distinguish, so would paint every remaining day of a life one colour and say nothing. Hover tip = exception, uses `occurrencesOn`, because that a question about one day.
- **Searching the life grid = same engine twice, never a second matcher.** `scoreEvent` in `lib/events.ts` (title, then location and notes at a penalty, over `fuzzyScore`) = the whole of "does this event match" for both the palette's ranking and the grid's thread, so a day can never light for a query the list would not have found. `LifeView` hands the events that score non-null to `lifeDensity` — the same call the field itself is built from — so a searched day and a carrying day agree about spans and about which recurrence rules a grid this size honours. Grid shows _every_ match; palette list caps at eight, so the thread is legitimately wider than the list.
- **The life grid's keyboard is a listbox of one _year_, rebuilt as the cursor leaves it.** The year ring's shape — one `sr-only` `role="listbox"`, `aria-activedescendant`, the canvas draws the cursor — but 365 options is a list and thirty thousand is a wall, so the options are the days of `cursorDay`'s calendar year, clipped to the span. A row of this grid already is a calendar year, which is why the year is the unit the labels speak in. The canvas is `aria-hidden`: it is the half of the picture that cannot be read out, and two nodes describing one field is a field described twice. ← → step a day, ↑ ↓ a week (the columns are real weeks, so seven days is straight up or down), Page a year, Home/End the two ends of the life; all of them `stopPropagation`, because in this view ← → belong to the shell and step the year. The keyboard's ring and the pointer's are **one** ring and **one** `DayTip` — `active = hover ?? cursor` — since two marks on that field at once is two cursors.
- **Every option's label comes off `density`; only the active one is counted.** `density` is exactly what the field is painted from, so a label that reads it agrees with the picture by construction. `dayTally` runs for the cursor's day alone — expanding recurrence 366 times to fill a list nobody reads straight through is a frame spent on nothing, and the one day somebody is standing on deserves the tip's own answer.
- **A search takes the colour channel whole.** Under an active query, a day that did not match loses its event colour: `SEARCH_TONE` (past 0.13, future 0.06) is the only thing left, hits keep their colour at `radius * 1.55`, drawn in a second `Path2D` batch after the field — `Path2D` carries no radius, so two radii = two maps. Horizon survives on purpose: a thread with no lived-against-left is a pattern rather than an answer.
- **The loupe is a magnifier, not a zoom, and the difference is the view's whole invariant.** Thirty thousand dots at four pixels is legible as a picture and illegible as a day, but pan-and-zoom turns the life into a map and a map of your life is a worse idea than a picture of it. So the eighty years never move: the year under the pointer is drawn a second time, large, on a card over the field. The other candidate was a fisheye in place, and it is wrong here for a reason the year ring is not — a ring is one-dimensional and closed, so `spread` conserves its own slack, where a grid pushed aside in two axes either overlaps rows or opens a hole, and its columns stop being real weeks. Distorting the cartogram means the picture you are reading is no longer the picture.
- **The loupe is the grid's own cell arithmetic at `colsPerLine = 7`, transposed — and that is arithmetic, not taste.** At the desktop split a line of the field already spans the whole width, so a year magnified in the field's own orientation gains nothing across and has nowhere to go down. Turned on its side it is `LOUPE_COLS` (54, always the wider of a year's 53 or 54, or the strip wobbles as the pointer crosses a year) rather than 372, and the pitch comes out four or five times the field's. A column _is_ a week, so there is no week gap — the field's gap groups seven columns that are one, and here one column already is. `loupeCell(d).row === mondayOffset(d)` is the claim, and it is the tested one.
- **`LOUPE_GAIN` is a coverage correction, not a preference.** The field's dot covers about `0.36` of its cell (`π·r²` over `pitchX · pitchY` at the desktop split); the loupe's covers `π · 0.4²` = `0.50` of a square one. Same `TONE`, forty per cent more light per unit area, and the plate came out bright enough to compete with the event colours — which is the one thing this grey channel may not do. `0.36 / 0.50`. The _ratio_ inside `TONE` is untouched, so past still reads against future and the month band still drifts; only the absolute light moves.
- **The loupe writes the field's own `hover`, and that is what makes it a control rather than a picture.** Pointing at a big dot moves the small one's ring and the tip; pressing opens the day; dragging draws a run of days and hands it to the editor, which is the one thing a four-pixel field cannot be asked to do at all. So the card is the one surface here that has to _keep_ the hover when the pointer leaves the canvas — hence one `onPointerLeave` on a wrapper around the pair, never on the canvas, and hence a blank cell inside the loupe is ignored rather than clearing (crossing one would drop the card out from under the pointer). `loupeLayout` returns `null` when the cells would not beat the field's own dot by `1.8`, or would be under five pixels: a second picture the size of the first is worth none of the room.
- **The card hangs in the half the pointer is not in, on two thresholds.** `sideFor` flips to the top past `0.62` of the field and back below `0.5`, because a single line across the field flips 150px of chrome for every pixel of jitter across it — this is `DayTip`'s own flip with hysteresis, since the card is not a tooltip. `DayTip` then takes an `avoid` band and moves to the other side of the pointer when it would land on the loupe, and only when that other side is actually clear. Both the band and the keyboard's `aim` are the reason `locate` returns its point even for a miss: which half the pointer is in is a question the blanks between years can answer as well as a day can.
- **The card waits `LOUPE_DWELL` before it arrives, and that is the difference between a tool and a flicker.** It is the largest thing in this app that appears without being clicked, so a pointer crossing the field on its way to the top bar must not throw a hundred and fifty pixels of chrome up behind it. `asked` is its own flag rather than a reading of the hover, because the hover changes every four pixels and the wait must not restart for that; `wake()` early-returns once asked, so field → card → field never re-dwells. **The keyboard skips it entirely** — `aim` sets `asked` directly, since the dwell exists for a pointer that was going somewhere else and a keypress never is. Arriving is `LOUPE_IN` and leaving is `LOUPE_OUT`, two thirds of it: things go faster than they come, and a card that lingers is in the way of the thing it was magnifying.
- **A drag on the life grid is the year ring's gesture at the next scale out, through the same `onCreateSpan`.** Press, drag, release: a press that never left its day is a click and names the day, anything wider is a run of days and therefore a multi-day event, and the shell hands both faces' answers to the same `openDraft`. The anchor is a **ref** and only the resolved `LifeRun` is state — a render per pixel of a gesture whose visible output is already `draw` is a render for nothing. `draw` itself lives up in `LifeView` because the **strip** prints it (`RunChip`), which is where a sentence about the whole grid goes and is the slot the search chip already takes; the hover tip is suppressed while a run is live, because a card naming one of the run's two ends is a second answer to a question that has one.
- **A run is drawn as bands, never as dots, and `CellBand` is why that is affordable.** A run of days is contiguous in reading order, so it is always at most three rectangles — the tail of the first line, every whole line between, the head of the last — which means dragging the entire life costs three `<rect>`s instead of thirty thousand arcs on a canvas that would have to be rebuilt per pointer move. One private `cellBands` serves both surfaces and each reads the answer in its own axis: `lifeBands` gets rows of days, `loupeBands` gets weeks of weekdays, clipped to the year on screen. The transpose again.
- **The life grid lights `pending` too, which is the rule the other two faces already keep.** White and faint while the run is being drawn (there is no colour to show yet), the draft's own colour once the editor has one, so the handover to the modal does not look like the range was thrown away. `run` refuses a `pending` that misses the span outright — `lifeRange` clamps rather than declining, so an event edited onto 1850 would otherwise light the birth dot.
- **The query lives in `App`, not in the palette, and outlives it.** ⌘P closes and the field stays lit, because the answer is drawn at eighty years and wants reading. Palette reports every keystroke through `onSearchLife` and only while `view === "life"`; App clears on palette _open_ via the render-phase adjustment pattern (a child cannot setState a parent during its own render, which is what the reset-on-open would otherwise be). `Escape` peels layers in order: panel, then the lit grid, then ambient.
- **The palette drops its `backdrop-blur` while threading.** 2px is wider than a dot: blurring is sanding off the answer the query just lit, on the surface the query is searching. Scrim thins to `black/35` at the same time.
- **Life grid's box measured by shell, not by view.** `App.tsx` observes `main` and resolves `lifeStage(...)` from it, because zoom needs day's dot in screen coordinates _before_ grid exists — dial has to know where it going. Also why `LIFE_META_H` = constant and readout strip given exactly that height in CSS: shell subtracts it to find field's origin, and strip growing by two pixels would land dial two pixels off every dot.
- **Day ⇄ life = zoom, year ⇄ life = unroll, day ⇄ year = crossfade.** `PANEL` in `transitions.ts` holds all of it, `AnimatePresence` keys one panel per view. Dial scales down onto dot of day it showing (`transformOrigin` = _style_, so already right on frozen render of panel that leaving) while grid's wave leaves that same dot; back other way, wave collapses onto it and dial grows out of it. Exiting panel gives up pointer events at once — for best part of a second it still on top of incoming one, and click landing on view you just left = bug you cannot see.
- **`exit` is a variant label, so the panel must be handed the whole table.** `initial` and `active` are resolved during render and passed as objects (see the frozen-props rule below) — but `exit="exit"` is a _label_, and a label with no `variants` prop resolves to **nothing at all**, silently, with no type error and no lint. That is exactly what happened: `variants` was dropped when the other two came off labels, and for two months every panel exit did nothing — the dial popped out instead of shrinking onto its dot. Objects outrank the table, so `variants={PANEL}` costs nothing and is what keeps `exit` alive. Verified by measuring the leaving panel's `transform` across the flight, which is the only way this is visible.
- **Zoom's scale keyframes geometric, not linear.** Apparent size linear in scale, so plain `1 → 0.008` tween hangs at full size then disappears in three frames. `ZOOM_STEPS` = five keyframes each a third of last, on `ease: "linear"`, with uneven `times` so smallest step gets longest slice — that the settle. Wave's own curve near-linear for same reason in reverse: every ease-out crossed window in 120 ms then crept.
- **Leaving element cannot read new view from its props**, because frozen at its last render. `ViewFlow` therefore a _ref_ (`flow` in `App.tsx`, `{ from, to, day }`, written by `go()` and by popstate handler): motion resolves dynamic `exit` variant when exit starts, and `usePresence` fires then too, so both read `.current` and get truth. `usePresence` also holds life view mounted until its wave collapsed — `safeToRemove()` called by animation's `onComplete`, and immediately when no wave to run.
- **The year ring owns both halves of the unroll, and the shell only keeps out of its way.** `YearView` is the one with the ring's geometry and both ends have to agree on it to the pixel, so it draws the ⌘Y → ⌘L and ⌘L → ⌘Y flights itself on a canvas and holds its own unmount open with `usePresence` — same contract `LifeView` has with the zoom. `PANEL`'s two unroll branches therefore neither fade nor scale: the canvas is already showing you the whole thing and a fade over it only takes contrast off it. `stage` = null (no birth date, box too small) falls the pair back to the crossfade, and the `!canUnroll` arm of the presence effect is what stops that hanging the panel forever.
- **`unroller` is an honest unroll, not a fly-to-target.** At `t` the days sit on a circle of curvature `(1 - t) / radius` while the arc _length_ eases from the ring's circumference to the row's width, so they stay on one curve the whole way. Lerping 365 positions straight to their destinations instead scatters particles at a line. `1 / k` is not a number at `t = 1`: the point is written as `sin θ / k` and `(1 - cos θ) / k`, which tend to `s` and `0`, and there is a guard below `1e-9`.
- **The unroll's easing is not `EASE`, and cannot be.** Angle still subtended falls as roughly `(1 - t)²` — curvature merely halved is still a semicircle — so nearly all the _visible_ straightening is in the first half of `t`. On `EASE`, which spends two thirds of its travel in the first quarter of its time, the ring was a line 150 ms in and the move was over before the eye found it. `UNROLL_EASE` leans the other way. For the same reason the life grid arrives on a **0.44 s delay**: the ring is the same greys the grid is, so against thirty thousand dots the whole movement is invisible and it has to happen on black.
- **A year is not always one row, so the unroll settles onto the true dots.** `lifeLayout` splits a year across up to six lines, so the straightened ring is only ever the first of them. From `SETTLE_FROM` the days blend off the flattening curve onto `lifeDot`'s actual answer; both curves are continuous, so it still reads as one movement instead of unroll-then-rearrange. 1 January's dot is the anchor and `length` is measured to 31 December's when the two share a line — the desktop case, where the ring lands on exactly the row it becomes with neither end to reel in.
- **The year ring's keyboard is a listbox, not 365 tab stops.** The month grid this replaced put every day in the tab order, which is a wall. The marks live on a canvas and cannot carry a name each, so the semantics live in an `sr-only` `<ul role="listbox">` with `aria-activedescendant` — one stop, arrows inside it, and the ring draws the cursor with the same magnifier the pointer gets. Arrows move a **cursor**, Enter chooses: naming a day here `goDay`s to the dial, so a listbox committing on every arrow press would fall out of the view on the first one. The cursor is clamped at both ends of the year, because rolling into the next one would have to commit. ← / → still step the _year_ whenever the ring does not hold focus; inside it they belong to the ring, which is why `onKeyDown` calls `stopPropagation` (`useHotkeys` listens on `window`, and React's root bubbles to it).
- **The year face shares the dial's crop, and `YEAR.MONTH` is `DIAL.ZONE` on purpose.** Same 1000-unit space, same `polar`, same `VIEW_BOX`, so ⌘D ⇄ ⌘Y is one object relabelled rather than two drawings of different sizes. `faceToPanel` reproduces `xMidYMid meet` for anything drawn _beside_ the SVG — the unroll's canvas — because a few pixels off on the first frame of a transition between two exact positions is the one error you cannot hide.
- **`markRadius` has fifty-eight units of travel because the interior is empty.** The ring _is_ the face, and at the twenty units it started with a year read as a hairline round a hole. An empty day still gets a mark (`DAY_STUB`), which at render size is a square, which is the dot the same day is in the life grid — a ring with holes in it stops being a year. Today is a pip inside the ring rather than a brighter mark, for the reason the life grid haloes its dot: a day's colour is its events', and being today is not one of them. `DAY_INNER`/`DAY_OUTER` were pulled in from 336/396 to leave the magnifier somewhere to go, and `TICK_INNER` clears `DAY_OUTER + GROW_OUT`.
- **The hover is a magnifier, and it grows _outwards_.** At 0.99° the day you are pointing at is smaller than the pointer, so a highlight that only changed colour left you counting teeth — and a fixed bar drawn over the ring was four times the mark it was pointing at on a one-event day and read as something crossing the ring rather than as one of the days making it up. `Ring` swells the day under the pointer, grows its neighbours less (`magnify`, a Gaussian — no corner anywhere, and every kink in that curve is a day that snaps as you cross it) and pushes the neighbourhood aside (`spread`, zero under the pointer, peaking at `SIGMA_PUSH` where the room is wanted, back to zero by `REACH` so the rest of the ring never moves). It grew _inwards_ for a draft, on the argument that the outer tip is the datum and pushing it out makes a hovered empty day look like a booked one — true, and the wrong trade: one day is magnified at a time, it is unmistakably the magnified one, and the readout is printing its count in words at that exact moment. Growing away from the centre reads as the day coming up to meet you; inwards read as a smudge. Length costs nothing and is generous (`GROW_OUT` 32, tip four units inside the month ticks); width is the expensive one and a test ties `PUSH` to it, though the two are no longer one-to-one — see the ink budget below.
- **The bulge snaps to the slot centre and springs there; it does not follow the pointer.** `pointerAt` tracked the pointer's exact fractional place in the year for a draft, on the argument that a quantised bulge lurches a slot at a time. What it actually did was land the full bulge on one mark only when the pointer sat at that mark's midpoint — anywhere else the two marks either side split it and neither reached full size, so the day the readout was naming looked no different from its neighbour. `pointerAt` is now a `useSpring` on `day + 0.5`, which fixes _which_ mark is the subject and keeps the movement continuous; `SLIDE_SPRING` is critically damped, because overshoot in size is a pop and overshoot in position is the magnifier running past the day it is naming. `slideTo` goes the short way with `ringDelta` (31 December to 1 January is one slot, not 364) and `jump`s instead when the bulge is down — arriving on the ring cold, or the keyboard picking it up — since sliding to it would sweep a swell across two months of a ring nobody was pointing at.
- **`FALLOFF` lives in `YearView`, not in `YEAR`.** The bell is geometry and is tested; the three exponents are how hard the drawing leans on it. They are the three parts of the effect and they are ordered: length is the gentlest (`1.4`) and carries the _reach_, so two marks each side visibly come along; width is steep (`4`) and carries the _focus_; light is steepest (`3.5`) and carries the _name_. With the bulge locked to a slot, those two steep channels are what make the subject unmistakable — length alone cannot, because a wide bell necessarily gives the first neighbour 70% of it.
- **Light is what an empty day gets _instead_ of a colour, never over one.** `white` is zero for any mark with `count > 0`: a day with events already says what it is, and washing it to white to announce a hover spends the only information this face carries on a highlight the growth has already given. An empty day has nothing to say with its fill, so the magnifier lights it — grey to very nearly white. The _selection_ is the exception and is full white whatever it carries, because it is not a hover: it is where the dial will land and where the unroll leaves from.
- **The ring is 78% ink, and that is the hard ceiling on the magnifier's width.** 4.4 units of stroke in a 5.65-unit slot leaves 1.25 units of black each, and a closed ring conserves it — `spread` returns to zero at both ends, so the total gap is fixed and all `PUSH` decides is _where_ the air comes from. Five marks at roughly double width need about sixteen units and the neighbourhood can lend ten, which is why `PUSH`/`SIGMA_PUSH` are 1.7/3.0 and not the old 0.9/1.15: the borrowing has to happen four days out and beyond, where every mark is dark and at its resting width and a crowded pair reads as nothing. The old pair took it all from the two slots either side, which opened a three-unit hole beside the hovered day and overlapped the marks at one and two days out by 1.2 units — a weld, visible as a bar. Past this, thicker means either a thinner `DAY_WIDTH` or black keylines with the swell drawn centre-last; there is no third option, and arithmetic decides it rather than taste.
- **The marks are a canvas because they move.** They were one `<path>` per colour in the SVG, which is right for a drawing that never changes, and this one changes every frame: the bulge rides `pointerAt` and `amount`, both springs. Both are **motion values, never state** — 365 SVG nodes re-diffed at 60 Hz is exactly the cost the canvas exists to avoid. The _day_ stays React state, because the readout and the listbox name it and it only changes once per slot crossed. `REACH` is cut where both curves are already invisible, so the loop can run all 365 without an exponential each — and it scales with the two sigmas: at 4.5 against a `SIGMA_PUSH` of 3 the tail was still most of a slot when it was cut, which is a mark that jumps as the pointer passes five days away from it.
- **The day-crossing tick cannot come from `setHover`.** React bails out of an identical value, so by the time state has settled a move inside one slot is indistinguishable from one that crossed into the next — and a cue per pointer event is not a tick, it is noise. `ticked` is a ref, written in the handler. It fires `slide`, the quieter of the two gated drag cues, on the same `tickSound` / `tickHaptics` channels: crossing a day is the same event as crossing a detent. A slow read is one tick per day and a fast sweep is a rip, which is what a finger along a comb does and is right for a ring of 365 teeth. The keyboard's cursor deliberately does **not** tick — `useTypingSound` already answers the arrow key.
- **The year's interior held a daylight figure for one draft, and it is not coming back.** Radius inside the marks was time of day, and sunrise and sunset drawn round the year is the one picture a grid cannot make. Filled it was a coffee stain; as two hairlines it was quiet and still interesting — and interesting is the problem. It is never what you came to a calendar to find out, and the readout wants the room. The dial's rim band stays; that one annotates a day you are actually looking at.
- **Life span = two settings, both can be stored wrong rather than merely missing.** `sane()` in `store.ts` = one clamp — `birth` not `YYYY-MM-DD` becomes `""` (shows prompt again) and `lifeExpectancy` pinned inside `LIFE_EXPECTANCY_RANGE` — and runs on `parse`, on `store.setLife`, and on `restore`, because `readSettings` in `backup.ts` only guarantees types.
- **The shell's clock ticks once a minute, and that is free rather than a compromise.** Nothing in circal prints a second: `splitTime` is `HH:MM`, `untilText` and `formatDuration` round to the minute, the hand is `minutesOfDay`. `useNow` aligns to its own period boundary, so `useNow(60_000)` in `App.tsx` fires at `:00` — the exact instant every one of those strings changes. Verified in the browser: `01:17 → 01:18` landed at `01:18:00.09`. It used to tick at 1 Hz and wake Dial, CenterPanel, YearView and LifeView 3,600 times an hour to redraw pixels that were already right. **A surface that genuinely needs finer than a minute asks for its own clock in the leaf that prints it, never by raising the shell's rate.** There is exactly one: `LifePercent` in `LifeView.tsx`.
- **`PERCENT_DECIMALS` is derived, not chosen, and moving it needs the table beside it.** One step of the life percentage's last digit is `span / 10^(decimals + 2)`: at six it is 25s on an eighty-year span and 47s at the 150-year maximum, which is a figure with six decimals on it that sits still — slower than the shell's own minute. At eight it is 0.25s, so it steps several times per tick of the one-second clock below and three in four values are never drawn; that is only honest on `requestAnimationFrame`, and a digit changing faster than it can be read is noise. **Seven is the only value inside five seconds across the whole of `LIFE_EXPECTANCY_RANGE`** (2.5s at the default, 4.7s at 150 years). `tests/life.test.ts` pins the bound rather than the arithmetic: it asserts the digit moves within five seconds on every span the app draws, within three on the default, and _not_ within one — the last being what keeps it from outrunning its own clock.
- **Milestones are three or four marks, and the count is the whole design.** `lifeMilestones` in `lib/life.ts` returns the round days inside the span (10,000 / 20,000 / 30,000) plus the midpoint — a default eighty-year life gets three. A thousand and five thousand are numbers that sound like milestones and are not: both land before anybody has a memory of the day, and both are already behind every user. Decades are **not** in the list; the rules and their labels already name them, and a dot on top of a rule is the same fact twice.
- **The midpoint is `floor(days / 2) + 1`, not the rounder-looking `ceil(days / 2)`.** The card's second paragraph makes an arithmetic claim — past this dot the half you can still spend is the smaller one — and on an even span `ceil` leaves one more day ahead than behind, which makes the sentence false. `tests/life.test.ts` asserts the claim, not the formula. A midpoint colliding with a round day is dropped rather than drawn twice: two marks on one dot is one mark that cannot be clicked.
- **The milestone ring is drawn in the SVG overlay; the hit area is a real `<button>` in its own layer.** Two layers, one `marks` array, because the ring has to sit under today's halo and the hover ring (a milestone is a property of the grid; those three are about where you are in it right now) while the target has to be above the canvas. The buttons are also **the grid's only focus path** — three tab stops is an order somebody can use, where thirty thousand dots is not. They cost those three days their click on the field, which is exactly what `Go to this day` in the card is for; it is not a courtesy.
- **The milestone prose lives in `lib/life.ts` beside the function, and it has no em dashes.** House rule for this app's long-form user-facing writing, asserted in `tests/life.test.ts` so a future paragraph cannot quietly reintroduce one. Code comments keep the repo's own voice; the ban is on prose the user _reads through_, which is the milestones and now the whole of `src/pages/manifesto.astro` (866 words, verified by reading the rendered page — the suite has no DOM and cannot reach it, so it is on you). A one-line caption in a panel is not long-form and is not covered.
- **`lifeMilestones` walks with `addDays`, so it has a `tests/west/` case.** A mark 10,000 days out crosses twenty US DST transitions; a millisecond walk would drift an hour off midnight and put the dot on the wrong day for every user west of UTC. Same rule as `dayKey` and `startOfDay`: touch a day-keyed function, add the western case.
- **The year ring's centre prints a line the user wrote, not a figure the app computed.** A year-scale summary (busiest month, longest empty run) was the obvious thing to put there and it is the wrong thing: the dial's interior answers a day because you are living in it, and nobody opens a year to be told which month was busy. `settings.yearQuote` is the whole feature, capped at `YEAR_QUOTE_MAX` in `sane()` and shown **only at rest** — pointing at a day is a question and a quote is not an answer to it. It is `ink-3`, the same tone as the date above it: `ink-4` is the ticks and the disabled, and 12.5px of it on true black is a line you can see is there without being able to read it. What keeps it subordinate is the italic and the gap.
- **`store.setYearQuote` caps but deliberately does not `trim()`.** It runs on every keystroke, and trimming there eats the space between two words the moment it is typed. `sane()` is the boundary that trims, because it runs on load and on restore where the value is already finished.
- **`/manifesto/` is the argument, and it borrows one line, so it attributes it.** "You are a worm through time" is the opening of the Hiss incantation, from _Control_ — it is the life view stated in seven words, which is why it also heads the life grid's `BirthPrompt`, and it is credited in both places. Anything else this page quotes gets the same treatment. The page is deliberately islandless: a manifesto that ships React costs more to load than the product it describes.
